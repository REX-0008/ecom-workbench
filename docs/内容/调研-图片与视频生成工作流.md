## 一、先给结论（三行以内）

1. **单次调用做成专用节点，整件事做成工作流**：图片可以是「一个提交节点 + 一份工作流」，
   视频**必须是**「提交 / 查询两个动作 + 一份工作流」，因为视频一次要跑数分钟，超过我们单节点
   默认 300 秒超时（`src/dispatch/dispatcher.ts:166`）。
2. **现有节点拿不到图**：`sys.http` 执行方把响应按文本读（`src/dispatch/executors.ts:127`），
   `sys.fs.write` 只写 UTF-8 文本（`src/dispatch/builtins.ts:68-78`）——**接通前必须先补「收二进制 / 存二进制」这一环**。
3. **成本量级**（阿里云百炼官方价，已核实）：图片 0.2 元/张；视频 720P 0.6 元/秒、1080P 1 元/秒，
   即 15 秒一条 9~15 元。视频重试一次就是一次钱，图片重试几乎不心疼。

## 二、两家分别怎么做（带出处）

### 2.1 n8n：把生成做成「应用节点里的一个 operation」

**OpenAI 节点的图像操作**（已核实，原文：
https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-langchain.openai/image-operations.md ）

原文的操作清单里，`Generate an Image` 的参数是：

> * **Model**: Select the model you want to generate an image.
> * **Prompt**: … The maximum length is 1000 characters for `dall-e-2` and 4000 characters for `dall-e-3`.
> * Options: **Quality**（HD，仅 dall-e-3）、**Resolution**（`1024x1024` / `1792x1024` / `1024x1792`）、
>   **Style**（Natural / Vivid）、**Respond with image URL(s)**、**Put Output in Field**（默认 `data`）

**OpenAI 节点的视频操作**（已核实，原文：
https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-langchain.openai/video-operations.md ）：

> * **Model**: Currently supports `sora-2` and `sora-2-pro`.
> * **Prompt**
> * **Seconds**: Clip duration in seconds (up to 25).
> * **Size**: 1024x1792 and 1792x1024 are only supported by Sora 2 Pro.
> * Options: **Reference**（可选参考图，二进制）、**Wait Timeout**（Time to wait for the video to be
>   generated in seconds. **Defaults to 300**.）、**Output Field Name**（默认 `data`）

**关键观察（推断，但依据很硬）**：n8n 的做法是「**在节点里等**」——`Wait Timeout` 默认 300 秒
就是它对视频的容忍上限。它不把「提交 / 查询」拆成两个节点。

**配套能力**（已核实）：n8n 的数据模型里二进制带类型，`image` 与 `video` 都是合法值：

```
packages/workflow/src/interfaces.ts:80
export type BinaryFileType = 'text' | 'json' | 'image' | 'audio' | 'video' | 'pdf' | 'html';
```

**真的要等很久时它怎么处理**：用 `Wait` 节点（已核实，原文
https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.wait.md ）：

> Use the Wait node pause your workflow's execution. When the workflow pauses it **offloads the
> execution data to the database**. When the resume condition is met, the workflow reloads the data
> and the execution continues.
>
> … For wait times **less than 65 seconds**, the workflow doesn't offload execution data to the database.
> Instead, the process continues to run …

恢复方式四种：`After Time Interval` / `At Specified Time` / `On Webhook Call` / `On Form Submitted`。
→ **n8n 有「跨请求存现场」的机制**；`On Webhook Call` 那一条正是给「外部服务跑完回调我」准备的。

### 2.2 Dify：没有图像生成节点，用「工具节点」或「HTTP 节点」自己接

**它的内置节点清单里没有图像 / 视频生成**（已核实，官方文档索引：
https://docs.dify.ai/_llms/en/cloud.txt ）。节点表只有 LLM / Knowledge Retrieval / Answer / Output /
Agent / Question Classifier / If-Else / Iteration / Loop / Code / Template / Variable Aggregator /
Document Extractor / Variable Assigner / Parameter Extractor / HTTP Request / List Operator / Tool Node /
Start / User Input / Trigger 系列 / Webhook / Human Input。

**它的模型默认项里也没有「图像生成模型」这一类**（已核实，原文
https://docs.dify.ai/en/cloud/use-dify/workspace/model-providers.md ）。`Default Models` 只有五项：
System Reasoning Model / Embedding Model / Rerank Model / Speech-to-Text Model / Text-to-Speech Model。

**本地 checkout 交叉验证**：在 `api/` 全目录搜 `text2image` / `TEXT_TO_IMAGE` **无命中**（已核实，
`grep -rniI "text2image|text_to_image" api/` 返回空）。⚠️ 注意：Dify 的模型运行时
（`graphon` 包）**不在本地 checkout 里**，所以「模型类型枚举里绝对没有图像生成」这一条**我无法核实**；
能核实的是「后端业务代码与前端都没有这个字样」。

**那它怎么出图**——两条路，都有官方原文：

1. **Tool 节点 + 插件**（已核实，原文
   https://docs.dify.ai/en/learn/tutorials/build-ai-image-generation-app.md ）：
   教程里配 Stability 的 API Key → 在 Tools 里 Authorize → Agent 的 Tools 勾上 Stability →
   提示词写 `Draw the specified content … using stability_text2image.`
2. **HTTP Request 节点自己接**（已核实，阿里云官方接入页
   https://help.aliyun.com/zh/model-studio/dify 原文）：

   > Q3：如何使用万相模型？ A：**Dify 没有提供万相模型相关的插件**，通过 Dify 的 Chatflow/工作流的
   > 节点可达到文生图/视频的功能。……下载我们写好的模板：万相-文生图 Demo.yml / 万相-文生视频 Demo.yml……
   > 模板使用的模型为北京地域的 `wanx2.1-t2i-turbo`（文生图）/ `wanx2.1-t2v-turbo`（文生视频）。
   > 你可以在 **STEP1 节点**修改模型，在 **STEP1 和 STEP3 节点**修改地域 API。
   >
   > 文生视频的时间一般在 **5 分钟以上**，请耐心等待。

   ⇒ **阿里云自己的官方方案是「多个 HTTP 节点串起来」，不是专用节点**。STEP1 提交、STEP3 查询，
   至少两个 HTTP 节点 + 中间等待。

**Dify 的 HTTP 节点强在哪**（已核实，原文
https://docs.dify.ai/en/cloud/use-dify/nodes/http-request.md ）：

> **File Detection** … 1. Content-Disposition analysis … 2. MIME type evaluation …
> 3. Content sampling — For ambiguous types, samples first 1024 bytes to detect text patterns.
> Text-based responses (JSON, XML, HTML, etc.) are treated as regular data, while **binary content
> becomes file variables**.
>
> **File Downloads** are automatically handled when responses contain file content. Downloaded files
> become available as **file variables** for use in downstream nodes.
>
> **Retry Settings** automatically retry failed requests **up to 10 times** with configurable intervals
> (maximum 5000ms).

⇒ 它能**自动认出二进制并落成文件变量**。这一条我们现在**完全没有**（见第四节）。

### 2.3 两家在这一点上的**冲突在哪**（先讲清，不综合）

| | n8n | Dify |
| --- | --- | --- |
| 有没有生图/生视频的专用节点 | **有**（OpenAI 节点里的 Image / Video operation） | **没有**（要 Tool 节点挂插件，或 HTTP 节点自己接） |
| 谁负责「等到生成好」 | **节点自己等**，`Wait Timeout` 默认 300 秒 | **不负责**——由工作流里的多个 HTTP 节点 + 等待串出来 |
| 二进制结果 | 有原生 `BinaryFileType`（含 `image` / `video`） | 有 file variable（自动按 MIME / 采样判定） |
| 超过一个请求生命周期 | 交给 `Wait` 节点（<65 秒不落库，≥65 秒存库） | 靠 HTTP 节点分次 + 变量传 `task_id` |

**这不是「各有优缺点」的口味问题**，而是两种产品结构决定的：
n8n 的节点是应用集成器，一个应用一个节点、操作做在节点内部最省用户的事；
Dify 的节点是 LLM 原语，非 LLM 的能力一律走「工具 / HTTP」，所以它连自家生态的万相都要用户自己拼 HTTP。

**我们不能两边都要**：要「一个节点内部等 300 秒」，就等于把视频的 5~15 分钟锁死在超时里；
要「像 Dify 那样拆成提交 / 查询」，就必须先有「存 `task_id` 并回查」的能力。
**我们该选后者**，理由是下一节那个硬约束，不是偏好。

## 三、我们的场景与两家的差别

| 差别 | 他们 | 我们 | 依据 |
| --- | --- | --- | --- |
| 单节点超时 | n8n 把等待放在节点参数里，允许 300 秒甚至更久 | **派发器单节点默认 300000 毫秒** | `src/dispatch/dispatcher.ts:166`（`timeoutMs: options.timeoutMs ?? 300000`） |
| 二进制 | n8n 有 `BinaryFileType`；Dify 有 file variable | **没有二进制概念**：`sys.http` 只 `res.text()` | `src/dispatch/executors.ts:127`（`const text = await res.text()`） |
| 落盘 | n8n 有 Read/Write Files from Disk | `sys.fs.write` 写 UTF-8 文本 | `src/dispatch/builtins.ts:68-78`（`writeFile(path, text, 'utf8')`） |
| 等很久 | n8n `Wait` 能存现场跨重启 | 「等待」节点**已具备**这个能力（存盘 + 恢复） | `src/nodes/flow/wait/node.ts` 头部注释：三种恢复方式，到点由宿主半恢复 |
| 端口类型 | — | 已有 `image` 端口类型与颜色，但没有 `video` | `src/workflow/model.ts:37`（`'data' \| 'text' \| 'image' \| 'number' \| 'any'`） |

**结论（推断，依据上面这些源码）**：
- 「等视频生成」不能塞进一个 HTTP 节点 —— 300 秒硬顶，而官方说 5 分钟以上；
- 我们有「等待」节点可以存现场，但它是给「等几小时」用的，轮询十几秒一次用它太笨重；
- 真正的卡点是**二进制**：图 / 视频拿到手之后存不下来、界面也显示不出来。这个问题不解决，
  讨论「接哪家」没有意义。

### 4.3 挑选标准（给用户选，不预设答案）

按影响从大到小：

1. **能不能国内直连** —— 连不上就别谈价格。阿里云百炼、火山方舟可直连（已核实两者都有国内地域）。
2. **计费方式能不能接受** —— 图片按张（一次多张，好控制）；视频按秒（15 秒一条就是十几元）。
   预算紧就先用图片跑通全链路。
3. **单次上限够不够用** —— 阿里云视频单次 **≤15 秒**（已核实）。要 30 秒以上的成片，
   只能「多段生成 + 拼接」，那是另一件事。
4. **要不要参考图 / 图生图** —— 商品一致性靠这个。`wan2.7-i2v`（图生视频）与
   `qwen-image` 的图生图都支持传参考图（已核实模型能力表里输入模态含 Image）。
5. **审核严不严** —— 电商场景大量「价格角标」「促销文字」，容易被拦；
   阿里云的 `DataInspectionFailed` / `IPInfringementSuspect` 两种拦截**已核实存在**。
6. **有没有现成密钥** —— 缺密钥就缺依赖，节点会显示「缺依赖」而不是报错到天上去。

## 五、推荐与理由（含取舍代价）

### 5.1 形态：单次调用做节点，整件事做工作流

按 `docs/机制-什么做成节点、什么写代码、什么做成工作流.md` §一 的三岔路判：

- **「把提示词发出去、拿回一个 URL 或任务号」** —— 碰网络 → **专用节点**（同 `sys.http` 那一类）。
- **「一次完整的生成任务」**（组装提示词 → 提交 → 轮询 → 下载 → 落盘 → 记台账）——
  是一串固定步骤，且**跨多个动作** → **整份工作流**。

再用同文件 §「什么该做成工作流（七问）」逐条对：

| # | 问题 | 我们的答案 | 结论 |
| --- | --- | --- | --- |
| 1 | 跨多个服务？ | 是（模型服务 + 我们的磁盘） | → 工作流 |
| 2 | 超过一个请求生命周期？ | **视频是**（官方说 5 分钟以上，我们单节点 300 秒上限） | → 工作流 |
| 3 | 需要失败补偿？ | 是（审核拦截要能改词重试、失败不能脏了台账） | → 工作流 |
| 4 | 需要重试 / 重放？ | 是（尤其视频，失败一次要能只重那段） | → 工作流 |
| 5 | 需要人工审批 / 等等事件？ | 图片要人挑（生成 4 张选 1 张） | → 工作流（用「等待」节点留人工点） |
| 6 | 流程常变 / 要业务配置？ | 是（换模型、调尺寸、改拼接方式） | → 工作流 |
| 7 | 高频低延迟？ | **否** | 不排除工作流 |

⇒ **六条答「是」、第七条答「否」**，判据一致指向工作流。这不是偏好，是七问算出来的。

**具体拆法（建议，不是定论）**：

| 用途 | 做成什么 | 为什么 |
| --- | --- | --- |
| 图片一次生成 | **一个专用节点**（`ecom.image.gen` 已有定义，`src/nodes/ecom/image-gen/node.ts`） | 同步接口，`wan2.6-t2i` 支持 HTTP 同步调用（已核实）；秒级返回，塞得进 300 秒 |
| 视频提交 | **一个专用节点**（提交，拿 `task_id`） | 异步接口，提交很快返回（已核实返回 `task_id` + `PENDING`） |
| 视频查询 | **一个专用节点**（按 `task_id` 查一次） | 只查一次，不阻塞 |
| 整条「生成 N 张图 / 生成 1 条视频」 | **一份工作流** | 提交 → 查 → 下载 → 落盘 → 记台账 是一串固定动作 |

**代价（写清楚）**：
- 视频要「提交一次 + 查询多次」，工作流里得靠**循环 + 延迟 + 跳出条件**拼轮询；
  我们的循环有 `breakConditions`（`src/nodes/flow/loop/node.ts:115`，条件类型照 Dify 的 `break_conditions`），
  拼得出来，但画布上会多 3~4 个节点 —— 这是「不塞进一个节点等」的必然代价。
- 视频的「等」如果用「等待」节点，会**多一条运行记录**（`flow.wait` 头部注释明写了这个代价）；
  如果用「延迟」节点，进程一直占着。两者都不完美，**这一条要用户拍**（见第七节）。

## 六、图片与视频的差别（分开讲，不合成）

### 6.1 图片

| 项 | 值 | 出处 |
| --- | --- | --- |
| 调用形态 | `wan2.6-t2i` **支持 HTTP 同步调用**（一次请求直接拿结果） | text-to-image-v2-api-reference |
| 耗时 | 文档未给固定值；`prompt_extend` 开启会**多 3~5 秒**（图片）/ **3~4 秒**（另一个版本原文） | 同上 |
| 结果数量 | 一次 1~4 张（`n`），默认 **4** | 同上 |
| 计费 | 0.2 元/张（北京） | wan2-6-t2i |
| 限额 | RPM 60（`wan2.6-t2i` 北京）/ 300（`wan2.6-image` 北京） | 同上 |
| 失败代价 | 1 张 = 0.2 元，重试几乎不心疼 | 由单价推 |
| URL 有效期 | 24 小时 | text-to-image-v2-api-reference |

**痛点（推断，基于上面的参数）**：不是「生成不出来」，是**量**与**一致性**。
- 量：一个商品要主图 + 详情图十几张，`n` 默认 4 会成倍花钱，必须显式 `n=1` 或按需设；
- 一致性：同一商品多张图要「看起来是一套的」，靠参考图（`qwen-image` 的图生图最多 10 张参考图，
  已核实于 https://help.aliyun.com/zh/model-studio/text-to-image ）；
- 审核：带「清仓价」「特价」这类文字容易被 `DataInspectionFailed` 拦。

### 6.2 视频

| 项 | 值 | 出处 |
| --- | --- | --- |
| 调用形态 | **只能异步**：`X-DashScope-Async: enable` 必须设，缺了直接报错「current user api does not support synchronous calls」 | text-to-video-api-reference |
| 耗时 | 官方：「文生视频的时间一般在 **5 分钟以上**」（Dify 接入页）；API 页写「通常为 1-5 分钟」 | model-studio/dify；text-to-video-api-reference |
| 时长 | `duration` **2~15 秒整数**，默认 5 | text-to-video-api-reference |
| 计费 | 720P 0.6 元/秒；1080P 1 元/秒 | wan2-7-t2v |
| 限额 | RPM 300；查询接口 RPS 20 | 同上 / text-to-video-api-reference |
| 一次几条 | **1 条**（`video_count` 固定 1） | text-to-video-api-reference |
| 失败代价 | 15 秒 1080P = 15 元；重试一次就再花一次 | 由单价推 |
| 轮询建议 | 官方建议「查询间隔如 **15 秒**」，并设最终超时（如 2 分钟标记失败） | text-to-video-api-reference |

**痛点（推断，基于上面的参数）**：全部集中在「**慢、贵、没中间态**」。
- 慢：5 分钟以上，比我们单节点 300 秒上限还长；
- 贵：一条十几元，用户会想「先试一条」，所以**必须有 5 秒 720P 的试跑档**；
- 没中间态：`PENDING` / `RUNNING` / `SUCCEEDED` 三个状态里前两个**什么都不给你**
  （已核实状态枚举），界面上「转圈 5 分钟」是必然的，所以**进度必须能看见**，
  不能像图片那样「点了一下、几秒后出结果」。

**一句话差别**：图片是**批量筛选**问题，视频是**等待与试错成本**问题。
所以两者的界面与工作流都不该共用一套：图片要「一次出多张、可挑选、可重生成单张」，
视频要「先试 5 秒、确认后再出成片、生成期间能看进度」。
