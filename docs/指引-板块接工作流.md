# 指引 · 板块怎么接工作流（唯一做法）

> 从 `AGENTS.md` 移出来（2026-10-26）：它只在「写新板块 / 改板块那条发起路」时用，不该常驻每次请求。
> 触发条件见 `AGENTS.md`「板块接工作流」那一节。
> 起点：提示词板块（2026-10-23）把这条路跑通了，本文记的就是它 —— **新板块照抄这个形状，不要再发明第二种**。

**板块不自己实现业务，业务落成工作流；板块只负责「给参数、启动、渲染结果」。**

另起一套的后果是同一件事有两种修法：改工作流不生效（界面那份没动），改界面也不生效（真跑的是工作流那份）。

## 一、标准形状（五步）

**① 板块里发起**：调 `runWorkflowWithOutputs(ref, inputs)`，**不要自己拼 fetch**。

```ts
// src/client/workbench/PromptBoard.tsx:376
void runWorkflowWithOutputs(
  { id: OPTIMIZE_WORKFLOW_ID, name: OPTIMIZE_WORKFLOW },
  { [OPT_IN_BODY]: instruction, [OPT_IN_TEXT]: material },
)
```

函数本身在 `src/client/workbench/dispatch-client.ts:966`，**永不抛异常**（网络失败、401、宿主没起都变成 `{ ok: false, error }`）。
它打的是 `POST /api/ecom-workbench/workflow/run`（`:976`），宿主半那一侧在 `src/index.ts:2251`。

**② 引用用编号**：`{ id }` 优先、`{ name }` 兜底（`src/index.ts:2253-2259` 的注释「**编号优先、名字兼容**」）。

编号来自存档文件的 `id` 字段（`提示词优化.json` 的 `"id": "wf-1bzlv0k"`）。
按名字调的坏处很直接：存档改名就断。名字仍然要传 —— 它显示在运行历史与错误提示里。

**③ 参数键必须与开始节点逐字一致**：宿主半只认开始节点声明过的字段，**多给的一律丢掉**
（`src/workflow/io-fields.ts:189` 的注释，实现在 `:197` 的 `resolveInputs`）。
少给不会报错，只会空着跑 —— 看起来像「模型在瞎写」，这类错最难查。
所以这三个名字要写成文件顶部的常量并配断言钉住（`PromptBoard.tsx:64-70`）。

**④ 结果从结束节点的 `fields` 取**：宿主半把结束节点声明的清单收成 `declaredOutputs`
（键 = 声明里的名字，值 = 那个节点/字段），前端拿到的就是 `r.outputs`。

> ⚠️ **已定、未实施**：产出改由**节点主动汇报**汇总；工作流存档里不再画结束节点
> （`flow.end` 节点本身保留在节点库）。旧路撤掉之前，本节描述的仍是现行行为。
> 计划见 `.scratch/工作台-模型与汇报/issues/05-运行历史与任务记录分工及主动汇报.md`，
> 延后项见 `备忘-延后开发功能.md` 第 11 条。

```ts
// src/client/workbench/PromptBoard.tsx:389-397
const outs = r.outputs ?? {}
const named = outs[OPT_OUT_TEXT]
const fallback = Object.keys(outs).map(k => outs[k]).find(v => typeof v === 'string' && v.trim() !== '')
const picked = typeof named === 'string' && named.trim() !== '' ? named : fallback
```

⚠️ 那个 `fallback` 只是兜底（存档以后多几个产出时不至于一片空白）；
**正常路径必须按名字取**，不能「第一个非空就算」。

**⑤ 判定成功要看两样**：`ok` 与 `aborted` **一起看**（`dispatch-client.ts:989-992`）。
宿主半的 `ok` 意思是「这份档读得出来、真的跑了」，**不是**「跑成功了」。
`ok: true` + `aborted: true` 等于「跑起来了，但中途有节点失败并中断」。

## 二、失败有五种，各自要分开说

PromptBoard 把失败按关键字归成五类（`PromptBoard.tsx:120-126` 的 `classifyFail`），
每类给「发生了什么 / 为什么 / 怎么办」三段（`:133-153` 的 `FAIL_TEXT`）：

| 类别 | 触发条件（关键字） | 该说的话 |
| --- | --- | --- |
| `missing-flow` | `没有这份工作流` | 还没建这份工作流；给出「开始声明什么、中间放什么节点、结束交什么」的建法 |
| `no-model` | `没有可用的模型` | dsh 里没选 provider 与模型，请求根本没发出去 |
| `timeout` | `超时` / `timedOut` | 等太久收口了；说清可以调超时或缩短输入 |
| `empty` | `空` / `没有返回` | **请求发了也回来了**，但里面没东西（与「没发出去」不是一回事） |
| `other` | 都不匹配 | 不猜；指向运行历史看日志 |

⚠️ 判据是**关键字匹配**，因为宿主半没给错误码（`PromptBoard.tsx:109-110` 的注释）。
匹配不到就落 `other`，**不许猜**成上面某一类 —— 猜错会让人去改错的地方。

前两种（没给参数 / 没给工作流）要在**发请求之前**就拦掉，省一次额度（`:362`、`:368`）。

## 三、谁负责什么

| 谁 | 负责 | 不负责 |
| --- | --- | --- |
| **板块**（`src/client/workbench/*Board.tsx`） | 收集用户输入、校验必填、发起、把失败翻成人话、渲染结果 | 不实现业务逻辑、不直连模型、不自己拼 `/workflow/run` 的请求体、不碰磁盘 |
| **工作流存档**（`workflows/<名字>.json`） | 业务步骤本身：开始声明收什么、中间怎么做、结束交出什么 | 不含界面、不含文案、不知道谁在调它 |
| **宿主半**（`src/index.ts`） | 读档、解析输入、调引擎、落现场、写运行记录与产出归档、把产出回给调用方（`:2251` 起 `/workflow/run`） | 不懂业务语义，不替板块挑字段 |
| **引擎**（`src/workflow/`） | 拓扑、变量替换、跳过语义、失败策略、循环/并行、暂停恢复 | 不认识「提示词」「商品」这类业务名词 |

一句话：**业务名词只出现在存档与板块里，宿主半与引擎只认字段名。**

## 四、写新板块时的检查清单

每条都判得出「做到没做到」：

1. **为这个功能建了一份工作流，而不是在板块里手写逻辑？**
   判据：板块里搜不到「模型调用」「网址」「选择器」这类实现细节。
2. **两份引用都给了？** 传的是 `{ id, name }` 而不是只有名字。
3. **参数键与开始节点声明的字段名逐字一致？**
   判据：把工作流存档里的 `fields` 抄出来，与板块常量逐个字符比对过。
4. **节点交出的东西是业务语言？** 是「改写结果」「商品列表」，不是 `out`、`result`、`data`。
   （当前由结束节点声明；产出改由节点主动汇报后，判据不变、载体变。）
5. **五种失败都分开说了？** 至少区分「没发出去」「发了失败」「发了但返回空」三类 ——
   这三类的修法完全不同。
6. **拿不到结果时的提示指向下一步动作？**（去设置里选模型 / 去建那份工作流 / 去运行历史看日志），
   而不是只说「失败了」。
7. **测试验的是「真的跑了那份工作流」，不只是界面渲染？**
   参照 `tests/prompt-optimize.mjs`：它真跑一遍，检查**派发出去的命令体**里两段内容都在、
   变量已替换、产出指向正确的节点（`:1-19` 的三条说明就是它守的东西）。
8. **板块没有依赖骨架的 `onRunWorkflow` 来实现功能？** 见下面例 2。

## 五、反面例子：什么算「另起一套」

### 例 1：同一件事只做一半 —— 运行历史与板块记录是两份、两个读者

`src/index.ts:1756` 那段注释是用户定案（m03841）的红线：

> ⚠️ **运行历史里没有它**：`rec.finish` 那份记录照旧只写「跑过什么」。
> 两份是**两个读者**：历史给人回看，板块记录给取数 / 总览板块列表。

这条本身没错（一份给人看、一份给板块读），但它点出了那个必须避免的坏做法：
**同一条流程只改一半就宣布完成**。板块从工作流转走的产出要落两份，
落一份的话另一个读者就看不到 —— 而两边都不会报错。

### 例 2：板块自己跑工作流，绕过唯一真正跑的那条路

`src/client/workbench/CollectBoard.tsx:303-305`：

> ⚠️ 不再走骨架的 `onRunWorkflow`（那是「弹条提示、结果看不到」的老路）。
> 这里的 SSE 是**唯一真正跑**的那条 —— 两边都发会把工作流跑两遍。

骨架那个回调在 `EcomWorkbench.tsx:319`，实现是「调 `runWorkflowFile` + 弹条提示」——
**结果拿不回来**，板块只能显示「已跑完」。用它对接功能，等于板块看不见业务产出，
只能再加一条自己发起的路，于是**一次点击跑两遍**（`FlowRunPanel.tsx:95` 记着这个真 bug）。

⇒ 判据：**一个功能只能有一条真正发起运行的路**。板块要结果就用
`runWorkflowWithOutputs`；要逐步骤进度就用 `FlowRunPanel` 那条 SSE（`GET /workflow/run-stream`，
宿主半在 `src/index.ts:1666`）。**不要两条都发。**

## 六、「跑了要留痕」别忘了

从板块发起的那次运行，如果希望它进运行历史 / 产出归档，宿主半的 `/workflow/run` 已经做了
（`src/index.ts:2266` 的 `runCollector`、`:2292` 的 `rec.finish`、`:2295` 的 `archiveOutputs`）。
**板块不需要自己再上报**。画布上那条路才需要 `POST /workflow/record`（`src/index.ts:2054`，
前端 `dispatch-client.ts:394` 的 `recordCanvasRun`）—— 因为它跑在浏览器里，宿主半看不见。
