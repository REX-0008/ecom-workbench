# 机制-什么做成节点、什么写代码、什么做成工作流

> 起因：用户 2026-10-14 提出要**改一条定义**（原话）：
>
> > 「我之前有点过分强调**节点尽量少**了，但是节点的原则应该是**服务于业务**的，
> > 如果业务本身相对固定（就是一串代码，连续动作），非得节点少的原则一定走工作流，
> > 那工作流就做成了**汇编语言**了。
> > 所以是否应该先定义到底**什么做成节点**，什么用**通用节点（在节点里面写代码）**。」
>
> 本文替掉旧的「节点应该尽量少，尽量通用」那条 —— 它在总纲里保留了原话与出处，
> 但**不再作为判据**（判据见下）。
>
> 状态：**已定，2026-10-14**。证据是 n8n 与 Dify 两家的**官方文档原文**（见 §2）。

## 一、判据：一句话三个岔路

**问：它碰外部世界吗？**

```
                     ┌─ 不碰（只吃上游、只吐下游）───→ 用通用节点写代码
它做什么？ ──────────┤
                     ├─ 碰（文件/网络/浏览器/命令）──→ 做成专用节点
                     │
                     └─ 是**一串固定的步骤**（原来那份 ts / bat）──→ 做成一份工作流
```

| 哪一类 | 判据 | 怎么落地 | 为什么 |
| --- | --- | --- | --- |
| **① 通用节点（写代码）** | **纯数据变换** —— 只吃上游、只吐下游，**不碰外部世界** | 一个 `code.js` / `code.python` 节点 + **改实例名 + 备注**说清它在干嘛 | 这种逻辑一变再变（页面改版、字段调整），做成专用节点要改代码、发版本；写代码改一处就完事 |
| **② 专用节点** | **碰外部世界** —— 文件、网络、浏览器、命令 | 做成节点（`sys.fs.*` / `sys.http` / `browser.*` / `code.shell`） | 这些要**管资源、要能失败、要看得见**（进程要收、连接要断、日志要读） |
| **③ 一串固定的步骤** | **业务本身固定**的连续动作（一份 ts / 一个 bat 干的事） | **整体做成一份工作流**；要复用时用「调用工作流」引它 | 见 §3 —— 拆成一堆小节点串起来就是**汇编语言**（用户原话） |

⚠️ **①②的分界不是「能不能」，而是「该不该」**：
Dify 官方文档把这条说得最清楚（原文）：

> *"Code runs in an isolated sandbox that blocks file system access, outbound network
> requests, and system commands. … Avoid reading system files, opening network
> connections, or running shell commands; **restructure your logic to work with the
> input variables and libraries available inside the sandbox instead**."*

**注意后半句** —— 它不是「不许你这么干」，而是「**把外部动作移出代码、变成节点**」。
这条与我们的判断一致。

⚠️ **反面例子（我自己犯的）**：做「巡查-qianchuan」时，我把「读 monitor.json」
写进了 `code.js`（用 `await import('node:fs')`）。理由当时成立（「文件不存在是正常情况、
要兜默认值」），但按本判据**它该是 `sys.fs.read` 节点** —— 那是**碰外部世界**那一类。
兜默认值该由**分支 + 一个 code 节点**来表达，不是塞进读文件的代码里。

## 二、依据：两家的界线**完全一致**（这是很强的信号）

| | n8n（[Code 节点文档](https://docs.n8n.io/build/code-in-n8n/using-the-code-node)） | Dify（[Code 节点文档](https://docs.dify.ai/en/cloud/use-dify/nodes/code)） |
| --- | --- | --- |
| **能做什么** | Node.js / Python；支持 Promise、npm 模块（自建时） | Python / JavaScript；预装常用库（json/math/datetime/re、numpy/pandas…） |
| **`code` 里不能碰** | 原文：*"You **can't access the file system or make HTTP requests**. Use the following nodes instead: **Read/Write File From Disk**、**HTTP Request**"* | 原文：*"blocks **file system access, outbound network requests, and system commands**"* |
| **碰外部世界的替代** | 用现成节点（Read/Write File、HTTP Request） | 用现成节点（HTTP Request 等）+ 沙箱预装库 |

**两家都把「文件 / 网络 / 命令」划在代码之外，并指向专用节点。**
两家独立的项目做出同一个选择，说明这不是偏好，而是**结构上的必然**
（代码节点跑在沙箱/受限环境里，而外部动作需要资源管理与错误可见）。

### ③「一串固定步骤」两家怎么做

| | 做法 |
| --- | --- |
| **n8n** | **子工作流**（[原文](https://docs.n8n.io/build/flow-logic/break-workflows-into-smaller-parts)）：「You can call one workflow from another workflow. This allows you to build **modular, microservice-like workflows**」；工具是 `Execute Sub-workflow` 节点 + `Execute Sub-workflow Trigger`。还支持「从已有工作流里**框选一批节点**抽成子工作流」。 |
| **Dify** | 没有独立的「子工作流调用」节点，但 **Iteration / Loop 的内部就是子工作流**（官方原文：*creates a **sub-workflow** that runs once for each array element*）。 |

→ 两家都承认「**流程可以是一个可复用的整体**」这件事。
**我们还没有这个能力**（见 §4）。

## 三、为什么「硬把固定流程拆成节点」是坏的（用户原话的展开）

用户说那样会「做成**汇编语言**」。具体坏在哪：

1. **节点数暴涨，画布变成一团线** —— 一份 100 行的 ts 若拆成 30 个节点，
   画布上就是 30 个框 29 条线，**看不出业务流程**（而画布的用处正是「一眼看出流程」）。
2. **每改一处都要动结构** —— 加一个字段、调一个顺序，就要在画布上连线。
   而这类「业务固定的脚本」**本来就不该每次改结构**。
3. **小事变多** —— 拆开之后每步都要想「上游怎么传过来、失败了怎么办」，
   而这些在小脚本里是一行代码的事。
4. **反而更难读懂** —— 用户的原始痛点（「llm 写的，看时忘了什么意思」）
   是**阅读问题**，解法是**实例名 + 备注**（n8n 的 Rename node / Notes），
   **不是**把代码切成更多块（切得越碎，越难看出它整体在干什么）。

**所以**：业务固定的一串动作 → **一份工作流**（整体看、整体复用），
而不是一堆节点。

## 四、我们还缺的能力（与③直接相关）

「一串固定步骤做成一份工作流」要能**被别处引用**，否则它只是一份孤立的工作流。
两家都有这个能力，我们**没有**：

| 要的能力 | 现状 | 用户 2026-10-14 的说法 |
| --- | --- | --- |
| **把一份工作流插进另一份**（当子流程） | ❌ 没有 | —— |
| **把一份工作流当成一个编组插进画布** | ❌ 没有 | 用户：「**编组其实就是为这个准备的**，我后面准备增加这个功能」（已记待办板 `planned`） |

⚠️ 这两条**是同一件事的两面**：插进来之后，既可以当「一个可展开的整体」看（编组），
也可以当「一个可调用的步骤」跑（子流程）。用户先提的是编组那一面。

**在它做出来之前**：一份固定流程做成的**独立工作流**，要跑就**单独跑**（或在别的工作流里
用 `code.shell` 去调 —— 但那绕开了画布，不推荐当常态）。

## 五、与旧原则的关系

**旧原则**（总纲 §「脚本拆分与浏览器基础」里，用户 2026-10-12 的原话）：

> 「节点应该尽量**少**，尽量**通用**；如果当前节点无法完成或完成过于复杂，则新建逻辑节点。」

**新判据**（本文 §1）。两者的关系：

- **「尽量通用」保留** —— 与 §1①（纯数据变换写代码）方向一致。
- **「尽量少」不再作为判据** —— 它只看**节点个数**这个表面数字，
  而正确的问法是「**这件事本身是什么性质**」。用户已明确指出：
  > 「节点的原则应该是**服务于业务**的」
- **旧原则保留原话与出处**（总纲里那段），因为它是**当时的决策记录**；
  但**判断新问题时用本文的判据**。

⚠️ 这条改动的**实际后果**（写清楚，免得以后有人按旧的办）：
做「脚本工作流化」时，**不要**为了「节点少」把那串固定步骤拆成小节点，
而是**整份做成工作流**。

## 六、判据的使用（两个具体例子）

### 例 1：巡查里的「① 读配置」

- 它碰外部世界吗？**碰**（读文件）→ ② 专用节点（`sys.fs.read`）
- 「文件不存在就用默认值」怎么办？→ 用**分支**表达（读失败 → 走默认值那条）
- 「解析 + 深合并 + 兜默认」呢？→ **纯数据变换** → ① 写代码（`code.js`）

**所以正确的拆法是**：`sys.fs.read` → （成功 / 失败两条）→ `code.js` 解析合并。

### 例 2：抖音表单下载（8 个模块、逐日循环）

- 「算日期区间」→ **纯数据变换** → ① 写代码
- 「点下载按钮 / 等 download 事件落盘」→ **碰外部世界** → ② `browser.*` 节点
- 「逐日重复」→ **循环**（`flow.loop`，调度器能力）
- **但整件事（打开 → 设日期 → 点击 → 落盘 → 校验归档）是一串固定的动作**
  → ③ **做成一份工作流**（不拆成一堆小节点串在画布上）

用户 2026-10-12 对它的界定仍然有效（而且**与新判据吻合**）：

> 「这个节点叫做**抖音表单下载**，他包含 8 个数据的下载，需要插入日期与板块。
> 但是他一个节点就只是**单日下载**而不是一个周期 —— **周期归循环**。」

⚠️ 但按新判据，「抖音表单下载」不该是一个**节点**，而是**一份工作流**
（名字可以就叫「抖音表单下载」）。这是本次定义改动带来的**主要修正**。

## 七、功能跨不过「产品边界」怎么办（2026-10-17 补）

⚠️ **上一节的例 2 有个前提被证伪了。** 它按「抖音表单下载 = 一串固定动作 → 一份工作流」写的，
但真做进去才发现：**那 7 个模块不是同一种动作**（2026-10-16 ~ 17 真机逐轮暴露）：

| 类型 | 模块 | 差异 | 我们现在的做法 |
| --- | --- | --- | --- |
| 普通逐日 | 直播、短视频自营/合作、图文 | 设一天 → 点「下载明细」→ 一个文件 | ✅ 能表达 |
| 要两步点击 | 交易、商品列表 | 点「下载明细」先弹下拉，再点「下载当前明细」 | ❌ 表达不了（见下） |
| 要前置切标签 | 搜索 | 先点「本店搜索词」标签，日期控件才出来 | ✅ 已补（脚本里自己判断） |
| **另一套完整流程** | 千川推广、推广商品 | **不逐日**：按 ≤7 天分段、点日历格子、每次导航后重选维度 | ❌ 根本没进来 |

**「一串固定动作」这个前提，在这里是不成立的** —— 它是四种动作。

### 判据之外的第二个问题：**我们的产品能不能表达它**

原来的规矩是「**两家都没有的就不做**」（§2）。这次出现的是一种**更硬**的情况：
**两家里有一家做了，但我们要照它做，得先给自己的产品加功能。**

### 证据（原文）

**n8n：核心节点里没有浏览器节点。** 它的 80 个核心节点全是数据/逻辑/文件/HTTP 那一类
（`Code` / `HTTP Request` / `Read/Write Files from Disk` / `Execute Sub-workflow` / `Wait` …，
来源：https://docs.n8n.io/llms.txt 的核心节点索引，2026-10-17 取）。
浏览器自动化在 n8n 里**是社区节点**，最常用的是 `n8n-nodes-puppeteer`。它的官方说明：

> `Operations`: Get the full HTML contents of the page / Capture the contents of a page as a PDF /
> Capture screenshot / **Execute custom script to interact with the page**
> （来源：npm 包 README，https://cdn.jsdelivr.net/npm/n8n-nodes-puppeteer@latest/README.md）

> **Capture Downloads**: When enabled, any files downloaded during script execution (**via clicks,
> direct downloads, etc.**) will be automatically captured and returned as binary data in the node output.

⇒ **n8n 对「点击后出菜单再点第二下」的态度是：不给你一个「第二下」的节点，
而是给你一个「在里面写脚本」的节点。** 复杂的页面交互**全部沉进脚本**，
节点的产物是「页面 HTML / 截图 / 下载的文件」。

**Dify：节点清单里根本没有浏览器节点。** 官方文档的节点表（https://docs.dify.ai/_llms/en/cloud.txt，
2026-10-17 取）只有：LLM / Knowledge Retrieval / Answer / Output / Agent / Question Classifier /
If-Else / Iteration / Loop / Code / Template / Variable Aggregator / Document Extractor /
Variable Assigner / Parameter Extractor / HTTP Request / List Operator / Tool Node /
Start / User Input / Trigger 系列 / Webhook / Human Input。
**没有浏览器节点，也没有「等待页面元素」这一类。**

### 两家的答案其实是同一个：「**细粒度交给脚本**」

- n8n：给一个能**执行自定义脚本**的浏览器节点，脚本里想点几下点几下。
- Dify：连浏览器节点都没有 —— 要浏览器就自己写成**工具/插件**（Tool Node），里面照样是脚本。

⇒ 我们把「点一下 → 等菜单 → 再点一下」拆成**画布上的节点**这条路，
**两家都没走**。它们把这种细粒度交互**收进一个「执行脚本」节点**。

### 这对我们意味着什么（建议，未定）

1. **`browser.download` 的「只有一次点击」不是缺陷，是它该有的边界** ——
   它的职责是「触发 + 等下载事件 + 落盘」，因为**下载事件稍纵即逝、必须一口气做完**
   （见该节点注释里引的 Playwright 原文）。
2. **真正的修法是「第一步点击」放到 `browser.act` 的 eval 里**（那本来就允许写脚本），
   点完菜单、再由 `browser.download` 去点第二下并接住下载事件。
   ⇒ 这样不用给任何节点加参数，**也不需要新节点**。
   ⚠️ 但源码里有实测警告：交易页的 `evaluate` 合成点击**不触发下拉**，
   源码因此改用 Playwright 真实鼠标 —— 所以这条**必须真机验**，不能靠推断。
3. **千川那两个模块该独立成一份工作流**（它连日期方式都不一样，
   属于 §3「一串固定步骤 → 一份工作流」那条的**真案例**）。

⚠️ 这三条**都还没做** —— 等用户定方向。写在这里是因为**判据里那句
「一串固定动作 → 一份工作流」本身就选错了粒度**，下次别再按它想当然。
