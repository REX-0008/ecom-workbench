# 机制-嵌套循环与循环控制

> 2026-10-19。写给**不看代码的人**：每一节先说「它做什么」，再给名字。
>
> 这份文档回答四件事：
> ① 两层循环怎么摆、每一层的变量怎么取；
> ② 「条件跳出」与「连续失败跳出」的区别（这是两个不同的参数，最容易混）；
> ③ 开始 / 结束节点怎么把参数喂进工作流；
> ④ 失败重试。
>
> ⚠️ **本文只记录事实，不写「该改成什么」**。
> 带「查证」标记的是读过源码/跑过测试的；带「推断」标记的是没查到执行器的部分。

## 一、循环能套循环了（2026-10-19 起）

**它做什么**：让「对每个模块」里再套一层「对这个模块的每一天」。
以前不行 —— 引擎会直接报错拒绝；现在允许，**最多 5 层**。

### 怎么摆

把内层循环**放进外层循环的框里**就行（不是连线，是「放进框」这个动作）：

```
② 循环 A：逐模块          ← 外层
    ②a 打开该模块页
    ②c 读已结算日
    ②e 算「这个模块要补哪几天」
    ③ 循环 B：逐日期        ← 内层，就摆在外层框里
         ④a 设日期
         ④b 点下载并落盘
⑤ 汇总
```

判断「是不是真嵌进去了」看一颗字段：内层循环的归属（`parentId`）指向外层循环。
**并列时它一样会跑**，症状只在真机上看得见（拿错页面）——所以这个判据不能靠「跑过了」。

### 每层的变量怎么取

| 写法 | 取哪一层 | 举例（外层 = 模块、内层 = 日期） |
| --- | --- | --- |
| `{{item}}` / `{{index}}` | **最内层**本轮的值 | 今天是哪天、第几轮 |
| `{{outer.item}}` / `{{outer.index}}` | **往外一层**那份 | 当前是哪个模块 |
| `{{outer.outer.item}}` | 再往外一层（几层都成立） | 第 3 层时才有意义 |

**为什么用 `outer.` 前缀，而不是把变量换个名字**：

- 老存档里所有 `{{item}}` / `{{index}}` **一个字都不用改**，意思还是原来那个 —— 这是硬判据（向后兼容）；
- 逐层拼出来自然就是 `outer.outer`，不必为第 3 层再发明一种写法。

⚠️ **没有外层时不会凭空多出一个 `outer`**：那样 `{{outer}}` 会从「找不到、原样留着 + 一条警告」
变成「替换成空串」—— 前者你查得到，后者是静默的坏值。

### 内层读外层的「数据」不是读变量

除了 `item` 这类**变量**，内层还要能取**外层某个节点跑出来的值**（比如「算这个模块要补哪几天」的输出）。
这条走的是「遍历哪个数据」里的**选节点 + 选字段**，规则是：

- 选的节点属于**内层**体 → 读内层**本轮**的值；
- 属于**外层**体 → 读外层**本轮**的值；
- 两层都不属于 → 读全局那张表。

⚠️ **归属层里没有，就是没有** —— 不往外回落。
回落读到的是「上一轮的残留」，症状是「数据莫名其妙对不上」，不报错、最难查。
这条有专门的测试钉着（`tests/loop-plan.mjs` 的 ⑦d 两条 ★★）。

### 结果怎么交回上一层

**只交上一层，不自动拼成嵌套数组。**

内层跑完给外层一个 `{ count, results }`；外层的「结果取哪个」（`result`）选到内层循环，
拿到的就是内层的这份输出。**不替你把「每层的结果」再套成一个二维数组** ——
要那样就在循环后面接一个代码节点自己拼。

### 层数上限 5，超了会明确报错

不是技术限制，是**防呆**：真要 6 层的人该先把工作流拆开。
报错文案会说清「第几层 / 上限几层」，不会只说一句「不支持」。

### 界面上的一个已知限制（不是 bug，是取舍）

右键菜单的「放入循环」**永远放进第一个循环**。
想让第二个循环成为内层，只能靠「从节点库拖到外层框里」（落点继承）。
执行期不拦 —— 存档里的归属对了就能跑。

## 二、循环怎么「提前停」——两个不同的参数

**它做什么**：让循环在跑完之前停下。**停下不算失败**，已跑完的轮次结果照常给出。

⚠️ **有两个参数，是两件事，别混**（代码里也分了两个字段）：

| | 「跳出条件」 | 「连续失败几轮就停」 |
| --- | --- | --- |
| 字段名 | `breakConditions` | `maxConsecutiveFailures` |
| 按什么停 | **你写的条件**成立 | **失败次数**攒够了 |
| 典型用法 | 「这一轮的价格低于 100 就停」 | 「连续 2 天失败就停这个模块」（照抖音源码） |
| 默认 | 空 = 不启用 | **0 = 不启用** |

### 「跳出条件」长什么样

形状与**「条件判断」节点完全一样**（同一个控件、同一批比较符、同一套左边来源）——
照 Dify 的做法：它的 `loop` 节点里 `break_conditions` 与 if-else 用的是**同一个 Condition 类型**
（`refs-projects/dify/web/app/components/workflow/nodes/loop/types.ts:45` 的 `Condition`、
`:88` 的 `break_conditions`）。

左边可以选：循环变量（`item` / `index` / `outer.item` …）、体内节点的输出、开始节点的输入。
（三种来源见 `src/workflow/if-condition.ts:120-137` 的 `resolveOperand`：
`kind: 'field'` 取节点输出、`kind: 'loop'` 取循环变量、其余当「开始节点的输入」。）

多条条件时有一个「怎么算成立」：**全部满足**（and，默认）或**满足任一**（or）。

### 「连续失败」的语义

**连续** N 轮有节点失败就停；**成功一轮就清零**。
不写「成功清零」那一行的话，「失败-成功-失败」会被当成「连续 2 次」——这是有断言守着的。

停下时：
- 已跑完的轮次结果**照常给出**；
- **被跳过的轮次会记在输出的 `skippedRounds` 里**，并附一句原因 ——
  否则看起来像「循环少跑了」，那是最难排查的一类。

### 两者同时配时会怎样

**谁先命中谁生效。** 两个都配是允许的。

### 每层各判各的

内层跳出**不影响**外层。这是「每层一份现场」的直接结果。

## 三、开始节点 / 结束节点：参数怎么进得来

**它做什么**：让一份工作流**能被外部喂参数**、**能把结果交出去**。

- **开始节点**（`flow.start`）声明「这份工作流要哪些输入」。三项：
  - **谁能启动它**（`type`）：手动执行 / 被另一个流程调用 / 定时（定时本轮只留位子）；
  - **输入项**（`fields`）：名字、类型、默认值、是否必填。
- **结束节点**（`flow.end`）声明「交出哪些值」，还能选「跑完才显示」还是「跑到这一步就显示」。

⚠️ **没有开始节点 = 这份工作流接不了外部输入。**
不接受「把参数发给第一个节点」那种兜底 —— 那会让「参数从哪来」变得不可见。

**能不能被别的流程调用，由开始节点的 `type` 决定**，不是设置项，也不由工作流类型标签决定。

### 组合层也必须自己有一个开始节点

这条不做，参数等于**静默丢掉**：跑另一份工作流时，节点的「传给它的输入」若一项都不填，
会把**本层这次拿到的输入**原样带下去；而「本层拿到的输入」来自本层自己的开始节点。
组合层没有开始节点 → 那个值永远是空对象 → 填什么都传不进去，而且**不报错**。

### 变量写在模板里的一个规矩

模板里的变量要写在**引号里面**（`String("{{modules}}")`）。
不写引号会拼出非法 JS，整个节点失败。

⚠️ 而没有开始节点时，`{{modules}}` 会**原样保留**成那 8 个字符 —— 这是有测试故意钉着的
（「有没有开始节点」两种情况都验）。

## 四、失败重试

**它做什么**：一个节点失败后**自动再试几次**，次数与间隔自己填。

- 两个参数：`retryTimes`（额外再试几次，**0 = 不重试**，硬上限 10）、
  `retryDelayMs`（两次之间等多久毫秒，0 = 立刻，硬上限 60 秒）。
- **优先级**：节点实例上填的 > 节点定义里的默认值 > 都没有 = 不重试。
- **与「失败处理」叠加**：继续 + 重试 2 = 先重试 2 次，还失败就按「继续」往下走。
- **重试期间不发「失败」** —— 还没判死刑；只有用尽之后才发一条。
  每次重试都打日志（第几次、还剩几次、为什么、隔多久）——「它自己悄悄重试了」
  在账单 / 重复提交这类场景下后果很大，必须能事前看出来。
- **用户点停止时不再重试。**

⚠️ **不做「按错误类型分类重试」**：源码只重试「效果未知」，那是因为它能返回结构化结果；
我们的派发结果只有一句错误文本，按字符串猜「值不值得重试」等于把不可靠的规则写进核心。
想区分就自己用 `code.js` / 条件判断去分。

## 五、与两家的对照（以及**我们没抄的那一块**）

### Dify：`loop` 与 `iteration` 是两类节点

Dify 的循环分两类，都在 `refs-projects/dify/web/app/components/workflow/nodes/`：

| 类型 | 关键字段 | 用途 |
| --- | --- | --- |
| `iteration` | `iterator_selector`、`is_parallel`、`parallel_nums`、`flatten_output`、`error_handle_mode` | 遍历一个数组 |
| `loop` | `loop_count`、`break_conditions`、`loop_variables`、`logical_operator` | 按次数循环 + 条件跳出 + 显式声明循环变量 |

字段出处（**查证**）：
`nodes/iteration/types.ts:9-22`（`IterationNodeType`）、
`nodes/loop/types.ts:76-92`（`LoopVariable` 与 `LoopNodeType`）。

### ⚠️ `loop_variables` 我们没做 —— 为什么

**Dify 的做法（查证到的部分）**：每一层循环**自带一份变量声明**
（`LoopVariable = { id, label, var_type, value_type, value }`，`loop/types.ts:76-82`）。
含义是「这一层循环里叫 `item` 的那个东西，是这层自己声明的」——
内层读 `item` 自然是内层那份，不需要额外语法。

**我们换成 `outer.` 前缀**，理由三条：

1. **老存档零改动**：所有既有的 `{{item}}` / `{{index}}` 一字不改、语义不变（硬判据）；
2. **不需要为每层起名**：Dify 那套要用户给每层变量起 `label`，
   而我们的循环本身就是容器，层数可以从归属链算出来 —— 让程序算比让人起名省事；
3. **任意深度都不用再发明写法**：`outer.outer.item` 天然成立。

**代价（说清，不藏）**：

- 变量名只能叫 `item` / `index`，**不能自己起名**（Dify 可以，叫 `order` 之类更可读）；
- 写到第 4 层时是 `outer.outer.outer.item`，**越长越难读**；
- **没有「这一层声明了哪些变量」这个清单** —— 用户得知道层数才知道能写几个 `outer.`
  （界面上选值时会列出可用项，所以不至于要背）。

### ⚠️ 哪些是**推断**，不是查证

| 项 | 状态 |
| --- | --- |
| Dify `loop_variables` 的**运行时行为** | **推断**。本机 Dify 的**后端执行器没有 checkout** —— `refs-projects/dify/api/core/workflow/nodes/` 下只有 `agent` / `agent_v2` / `datasource` / `human_input` / `knowledge_index` / `knowledge_retrieval` / `trigger_plugin` / `trigger_schedule` / `trigger_webhook`，**没有 `iteration` / `loop` 的 Python 实现**。所以「每层一份变量、运行时按层隔离」这条是从**前端类型与面板**推的，不是从执行器源码读的 |
| n8n `SplitInBatches` 的**实现细节** | **推断**。`refs-projects/n8n/packages/` 下只有 `core` / `frontend` / `workflow`，**`nodes-base` 没 checkout**。只能从文档说它是「批处理 + 回环」 |

### n8n 的循环长什么样

n8n 没有专门的「循环节点」。它的循环是 **`SplitInBatches`**：把数组切成批，每批跑一遍，
跑完回到自己。嵌套 = 把第二个 `SplitInBatches` 放进第一个的循环体里。

⚠️ 这与我们的形态**不同**：我们的循环是**容器**（归属在 `parentId` 上），不是回环节点。
所以「抄 n8n」等于换一套循环机制 —— 代价大且没好处。

### 两家对照表

| | n8n | Dify | 我们 |
| --- | --- | --- | --- |
| 循环是什么 | 一个节点（`SplitInBatches`），靠回环 | 一个容器 | 一个容器（照 Dify） |
| 嵌套靠什么 | 把内层节点放进外层循环体 | `loop_variables` 显式声明每层变量 | `parentId` 归属链 + `outer.` 前缀 |
| 能不能条件跳出 | 能（`noItemsLeft` 出口） | 能（`break_conditions`） | 能（`breakConditions`，照 Dify 的条件类型） |
| 每层变量能不能自己起名 | — | **能** | **不能**（只能 `item` / `index` / `outer.*`） |

## 六、改循环相关代码时怎么验

| 改了什么 | 必跑 |
| --- | --- |
| 循环的图运算（谁属于循环、首尾、层数、变量名） | `tests/loop-plan.mjs` |
| 循环的执行（每轮隔离、结果回传、跳出、重试、层数上限） | `tests/run-graph.mjs` |
| 循环节点的界面（`LoopNode.tsx`） | `npm run test dom-render` |

⚠️ **两处都是「纯逻辑可单测」的**（`src/workflow/loop.ts` 刻意不 import 派发器）。
改循环时**两个都要跑** —— `loop-plan` 管「算得对不对」，`run-graph` 管「跑得对不对」，
只跑一个漏得掉一半。
