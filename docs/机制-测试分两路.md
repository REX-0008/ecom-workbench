# 机制 · 测试分两路（源码路与产物路）

> 状态：初稿（2026-10-23）
> 起因：契约 P0 的自证失败暴露「本轮所有改动都没进 `lib/index.js`」，而两份测试验的正是产物
> 关联：`docs/指引-测试与验证.md`（跑法与判据）、`.scratch/工作台-模型与汇报/issues/04-提醒搬家与模型能力.md`

---

## 一、这件事要紧在哪

这个工程的测试**分两条路**，验的不是同一份代码：

| 路 | 谁走 | 验的是 | 什么时候需要重新构建 |
| --- | --- | --- | --- |
| **源码路** | 绝大多数测试 | `src/**` 的 `.ts` / `.tsx`（经 tsx loader） | 不需要，改完立刻生效 |
| **产物路** | `host-dispatch.mjs`、`schedule-notify.mjs` | `lib/index.js`（`npm run bundle` 打出来的） | **改完必须 `npm run bundle`，否则验的是旧代码** |

产物路的测试在文件头就写明了，出处：
- `tests/host-dispatch.mjs:25` → `await import("../lib/index.js")`
- `tests/schedule-notify.mjs:32` → `await import('../lib/index.js')`

## 二、为什么它们要走产物

因为它们要验的是**完整的 HTTP 路径**：真的起一个 `http.createServer`，打真的路由，看真的响应。
而路由是在 `apply()` 里注册的，`apply()` 的导出在产物里。走源码也能起，但那就不是「用户实际跑的那份」了。

**这个区分是必要的，不是多余**。P0 那个 bug（`/run` 每次都被判成取消）正是靠产物路才验得出来 —— 它只在真 HTTP 下复现。

## 三、代价：会产生「两条时间线」

2026-10-23 发生的事：

1. 后端改完 P0，自证时把 `src` 改回错写法，`host-dispatch` **仍然全绿**
2. 查原因：`lib/index.js` 停在 06:38，而那时 S1 / V / P0 都还没写
3. 也就是说：**那 6 条 P0 断言验的是几小时前的代码**

这不是谁的失误，是「产物路 + 没打包」必然产生的结果。

## 四、规矩（写死）

1. **动了 `src/**` 的任何文件，只要涉及宿主半（`src/index.ts`、`src/dispatch/`、`src/workflow/`、`src/schedule/` 等），
   跑全量之前必须先 `npm run bundle`。** 否则 `host-dispatch` 与 `schedule-notify` 的通过没有意义。
2. **打包由组长统一调度，一次只放一个**。执行角色不许自己跑（会与别的角色抢构建产物）。
3. **自证要用源码路的测试**（如 `agent-node`）—— 它能立刻反映 `src` 的改动，不需要等打包。
   产物路的断言用于「验真实路径」，不是用于自证。
4. **报「全绿」时要说明是打包前还是打包后**。这两句话的可信度不一样。

## 五、怎么快速判断某个测试走哪条路

看测试文件开头有没有这两行之一：

```js
await import("../lib/index.js")
await import('../lib/index.js')
```

有 = 产物路。没有 = 源码路。

`scripts/run-tests.mjs` 的 `needsTsx()` 就是按「有没有 import `../src/` 或 `../scripts/`」来判断要不要挂 tsx loader 的，
所以源码路的测试都能直接读到最新代码。

## 六、还有一类更隐蔽的「验的不是你以为的东西」

同一轮里还发生过两次：

| 现象 | 根因 |
| --- | --- |
| 测试退出码一直是 0，但断言其实是红的 | 测试文件末尾的收尾代码被误删，失败没被上报 |
| `prompt-optimize` 绿了，但前端那条 HTTP 路没验过 | 它验的是 `runGraph`（引擎层），不是板块调 HTTP 那条 |

**共同点：测试的「通过」不必然等于「那条路通了」。** 报验收结论时要写清「验到了哪一层」，
不要用「测试全绿」代替「功能可用」。

### 还有一类：测试**崩了**，看着像环境问题，其实也是红的

| 项 | 内容 |
| --- | --- |
| **现象** | 可选链只包到中间层，下层是 `undefined` 时直接抛 `TypeError`，而不是让断言失败 |
| **后果** | 测试进程崩了，**不产生干净的断言失败**。跑的人很容易把它当成「跑了但环境有问题」，然后重跑一次、或者干脆忽略 —— 它其实是红的 |
| **规矩** | `?.` 要包到**最后一个可能为 `undefined` 的那一层**。只要有一层可能没有，就要有对应的 `?.` |
| **出处** | 2026-10-23 我做「模型痕迹进运行记录」的自证时写的是 `failEv?.llm.finish` —— `llm` 整个字段不存在时抛 `TypeError: Cannot read properties of undefined (reading 'finish')`。改成 `failEv?.llm?.finish` 才是干净的断言失败。代码位置：`src\workflow\run.ts:1149`（失败分支取 `outcome.llm`；成功分支在 `:1140`，同一种写法） |

判断方法：自证的输出里出现 `TypeError` / `Cannot read properties` 这类**堆栈**，就不是「断言红」，
而是「测试没跑完」。先把它修成能正常跑到断言，再谈红不红 —— 否则你连自己钉没钉住那件事都不知道。
