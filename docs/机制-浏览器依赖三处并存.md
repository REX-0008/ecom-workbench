# 机制 · 浏览器依赖（playwright）为什么自己带一份

> 2026-10-22 核实。用户提问「dsh 本身就有 playwright，其他插件也依赖，我们是怎么做的」，
> 查完的事实与结论如下。**改这条前先读完**，否则会以为是冗余想删掉。

## 一、事实（逐处查过）

| 位置 | 有没有 playwright | 证据 |
| --- | --- | --- |
| dsh 安装目录 `resources/app.asar/dsh/node_modules` | **没有** | 194 个包里搜 `playwright|puppeteer` = 0；只有 `default-browser` / `default-browser-id` |
| dsh 的 `app.asar/node_modules` | 没有 | 20 个包，无 |
| `runtime/primary-runtime` | 没有 | 只有 node 24.21.0 / pnpm 11.28.5 / python 3.12.14 |
| `profiles/desktop/node_modules/playwright`（hoisted） | **有，v1.64.0** | pnpm 把我们的依赖提上来了 |
| `profiles/desktop/node_modules/@our/ecom-workbench/node_modules/playwright` | **有，v1.64.0** | 部署副本，插件私有 |
| 本机 `ms-playwright` 内核缓存 | 有 1.32 GB | **不是我们的脚本装的**（我们只搬两个 npm 包，不下载内核） |

**dsh 的 `dsh-browser-use` 包不是浏览器实现** —— 它自己的 README 原文：
> "This package adds **no model-visible tools or browser operations**."
它是一个**注册表**，具体能力由 provider 插件提供。

已装的其他插件（`dsh-browser-cdp` / `dsh-ops` / `ds-bot` / `dsh-m`）**都没声明 playwright**。
所以实际只有我们在用。

## 二、为什么要自己带

1. **我们确实需要它**：`browser.act` / `browser.download` 两个节点要驱动浏览器。
2. **分层要求**：驱动脚本跑在**子进程**里（playwright 的 CDP 连接会挂住事件循环，放宿主半会卡死 dsh），
   那个子进程要能 `import('playwright')`，就得有个能解析到的位置。
3. **部署形态**：插件是 `file:` 依赖，pnpm 把它**复制**进 `profiles/desktop/node_modules/@our/ecom-workbench/`，
   插件自己的依赖装在它自己的 `node_modules/` 里。`scripts/install-browser-deps.mjs` 只是**提前做**
   `pnpm install` 本来会做的事 —— 因为它不能直接跑 install（那会重写运行中的目录，违反单写入者红线）。

## 三、注意：我们**没有**下载浏览器内核

`driver.mjs` 连的是**用户已经在跑的浏览器**（`connectOverCDP`，端口 9222），
不是自己启动一个。1.35GB 内核不需要 —— 这是既有决策
（见总纲「浏览器层」条：`playwright` 的库要装，**1.35GB 内核不要**）。

代码里 `chromium.launch` 只有一处，是「由我们打开」那个备用模式。

## 四、现状（用户 2026-10-22 定）

**维持现状，不改。** 两处副本版本相同（都是 1.64.0），没有冲突风险；
换掉插件私有那份要改部署链路，收益只是几十 MB，不值得。
