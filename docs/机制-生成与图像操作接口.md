# 生成与图像操作接口

> 面向**界面那一半**（`src/client/workbench/`）。这一页写的每个形状都能在代码里找到出处，
> 出处一律写成 `文件:行号`。**改动代码后如果这里对不上，以代码为准并回来改这一页。**
>
> 相关：`docs/指引-板块接工作流.md`（工作流那条路）、`AGENTS.md` 的「列表类接口的键名约定」。

## 这一页管什么

内容板块「生成」这条链路的**三个对外接口**：

| 接口 | 用途 |
|---|---|
| `POST /api/ecom-workbench/generate` | 提交一次生成（含图像操作与遮罩） |
| `GET /api/ecom-workbench/gen-models?op=` | 模型下拉的数据源，可按操作过滤 |
| `resolveMentions()`（纯函数，直接 import） | 把提示词里的 `@[名字](节点id)` 解析成「正文 + 参考图」 |

配套的读接口（此处不重复细节）：`GET /generate/:id`、`POST /generate/:id/cancel`、
`GET /generate`、`GET /gen-logs`、`GET /artifact/:id`、`POST /channels/:id/test`。

## 一条贯穿全篇的约定：base64

**所有图片都走 base64 + JSON，不走 multipart。** 参考图、遮罩、素材上传、产物回读，四件事同一套形状。

出处：`src/schedule/materials.ts` 文件头（那条取舍的说明）、`src/index.ts:1633-1694`（`/generate` 的解析）。

### 代价：8 MB 上限、涨 1/3、超限是 500 不是 413

- 宿主读请求体有一条硬上限：**`size > 8 * 1024 * 1024` 就抛错**
  （`src/index.ts:822`，`readJsonBody`）。
- base64 比原始字节**多约 1/3**。所以原图 + 遮罩加起来的原始字节**实际别超过约 6 MB**。
- **超限时的表现**：实测发 9 MB 请求体 → `{"status":500,"text":"{\"error\":\"请求体过大\"}"}`；
  发 7 MB → 正常 200。**不是 413**（那条错误被最外层 `catch` 收成 500，
  见 `src/index.ts:3168-3169`），也**不是静默截断** —— 请求不会被部分读进去。
- 界面该怎么防：在选图那一步就比大小（`src/client/workbench/upload-file.ts` 里
  `MAX_UPLOAD_BYTES = 6 * 1024 * 1024` 是单张素材那条路的判据，数值可以参考），
  并且**遮罩与底图要合起来算**，不能各自判断。

⚠️ 只判单张会踩：底图 5 MB + 遮罩 4 MB，各自都「没超」，加起来超了。

## 一、`POST /api/ecom-workbench/generate`

### 请求体

出处：`src/index.ts:1633-1694`（解析）、`src/schedule/generate.ts:331-370`（`GenerateInput`）。

| 字段 | 类型 | 必填 | 不给 / 给错时的行为 |
|---|---|---|---|
| `kind` | `"image" \| "video" \| "text" \| "audio"` | 是 | 认不出的值**当 `image`**（`src/index.ts:1638-1639`） |
| `prompt` | string | 是 | trim 后为空 → 400 `提示词不能为空`（`src/index.ts:1644`） |
| `model` | string | 是 | 空 → 400 `要指定模型（model）`（`src/index.ts:1645`） |
| `op` | `"inpaint" \| "upscale" \| "superResolve" \| "caption" \| "angle"` | 否 | **认不出的值当没给**（`src/index.ts:1642-1643`）；不给 → 与加这个字段之前一字不变 |
| `channelId` | string | 否 | 不给自己挑「有能做的模型的第一个渠道」（`generate.ts:308`） |
| `size` | string | 否 | ComfyUI 那条路：只认 `1024x1024` 这种像素写法（`generate.ts:666-683`），`16:9` 这类比例**真算出宽高**，认不出来**任务失败**；网络模型那条路原样透传（`openai-gen.ts:83`），`auto` 不传 |
| `count` | number | 否 | 网络模型：`Math.max(1, Math.min(15, …))`（`openai-gen.ts:75`/`:128`）；ComfyUI 那条路**不认**（ComfyUI 那条路**填建 Latent 节点的 `batch_size`**，见下文「`count` 现在真生效」） |
| `seconds` | number | 否 | 网络视频：`Math.max(1, Math.min(20, …))`，缺省 5（`openai-gen.ts:197`） |
| `refs` | `{mime, base64}[]` | 否 | 空数组 / 缺项跳过（`src/index.ts:1650-1661`）；`mime` 缺省 `image/png` |
| `mask` | `{mime, base64}` | 否 | **形状与 `refs` 的每一项完全相同**（`src/index.ts:1664-1675`）；只走 ComfyUI |
| `negativePrompt` | string | 否 | ComfyUI 那条路**会填进工作流**（2026-10-26 修好；**两条判据**：标题 ∪ 字段名，见下文）；16 份里**有 2 处**可填的负向文本。网络模型走 OpenAI 编辑时有 `negative_prompt`（`openai-gen.ts:135`） |
| `source` / `canvasId` / `canvasNodeId` | string | 否 | 只写进生成记录（`generate.ts:717-719`） |

### 一个真实例子（局部重绘）

```jsonc
{
  "kind": "image",
  "op": "inpaint",
  "prompt": "把背景换成海边",
  "model": "local",
  "channelId": "ch-comfy",
  "refs": [
    { "mime": "image/png", "base64": "iVBORw0KGgo…" }   // 底图 → 填 ref_image_01
  ],
  "mask": {
    "mime": "image/png", "base64": "iVBORw0KGgo…"        // 遮罩 → 填 ref_mask
  },
  "canvasId": "cv-1bzlv0k",
  "canvasNodeId": "n23"
}
```

### 回包

```jsonc
{ "ok": true, "id": "20261026-110257-igpu", "task": { … GenerateTask … } }
```

- **`id` 就是这次生成的记录 id**（`generate.ts` 文件头：一次生成一条记录，一一对应）。
- 接口**立刻返回**，真正的活在后台（`submitGeneration` 在 `setTimeout(0)` 里起）。
- `GenerateTask` 字段见 `generate.ts:85-114`。`artifacts[]` 每项是
  `{ id, mime, bytes, url, width?, height? }`（`generate.ts:56-70`），`url` 直接能塞 `<img src>`。
- 轮询：`GET /api/ecom-workbench/generate/:id` → `{ ok: true, task }`；
  查不到 → 404 `{ ok: false, error: '没有这个任务：…' }`（`src/index.ts:1626-1631`）。

### ⚠️ 三条「静默」行为，这是最难查的一类

三条都属于「不报错、结果却不是你要的」，但**处置方式各不相同**（前两条是宿主故意不拦，第三条是值域校验的取舍）。

#### ① 带 `op` 但不给 `mask`：不报错，跑的是工作流自带的占位遮罩

内置的局部编辑工作流 `inpaint_qwen_image_api.json` 里，`ref_mask` 槽位**自带你一份占位图**：

```
299 号节点（`_meta.title = "ref_mask"`，`LoadImage`）inputs 是 {"image":"1111.png"}
289 号节点（`_meta.title = "ref_image_01"`，`LoadImage`）是也自带一份 025ebb6f….png
```

`applyBindings` 只在 `bindings.refMask` 有值时才改写遮罩节点（`comfyui.ts:255-261`）。
不给遮罩 → 那个节点保持 `{"image":"1111.png"}`（实测），**ComfyUI 照样跑完、任务 status 是 `success`**。

底图同理：不给 `refs`，`ref_image_01` 保持自带的那张。而 `pruneUnusedRefs` 只会把
**编号超出已上传张数**的 `ref_image_XX` 节点删掉（`comfyui.ts:386-400`），
`ref_image_01` 在 0 张时也会被删 —— 但它的下游 `ImageScaleToMaxDimension` 会跟着塌，
真正被留下的反而是那份占位遮罩（实测 0 张参考图时保留 16/25 个节点，`299` 还在、`289` 已删）。
**这一串连锁的结果比「用占位图」更乱，所以不给 `refs` 就别提交 `inpaint`。**

所以界面**必须自己判断**：`op === 'inpaint'` 时，`mask` 没给就不要提交。
宿主这边**故意不拦** —— 拦住就无法「用工作流自带的遮罩做演示」，但那个理由只对调试成立，
界面上没有一个用户会想要「我抹了半天，结果用了张占位图」。

#### ② 给了 `mask` 但工作流没有遮罩槽位：遮罩被上传、**却没有任何节点引用它**

实测（`i2i_flux2_dev_api.json` 这种没有 `ref_mask` 槽位的工作流）：

```
上传次数 = 2（底图一次、遮罩一次）
提交出去的 workflow 里引用遮罩 = false
任务结果 = 成功（有产出）
```

也就是说：**遮罩白传了，任务还成功**。原因：`applyBindings` 只认 `ref_mask` / `mask` / `ref_mask_01`
这三个槽位名（`comfyui.ts:257`），槽位不存在就没地方填；`pruneUnusedRefs` 只裁
`ref_image*` 系列（`comfyui.ts:386-400`），不管遮罩。

判据在界面：**选了 `op: 'inpaint'` 就该要求渠道那类工作流确实有遮罩槽位**。
宿主能提供的信息是 `GET /gen-models?op=inpaint` 已经过滤过「这一类有没有工作流」，
但**它不保证那份工作流有 `ref_mask` 槽位**（校验函数 `validateComfyWorkflow` 有这条判据
`comfyui.ts:757-762`，可生成链路按设计**不调它**，见 `comfyui.ts:1156-1175` 那段的理由）。

#### ③ `op` 写错当没给

`isGenOp` 不在名单里 → `op` 视为 `undefined`（`src/index.ts:1642-1643`），
于是走普通生成：`kind: 'image'` + 有 `refs` → `i2i`，没 `refs` → `t2i`（`generate.ts:208`）。
**不报错**。写错一个字母，用户看到的是「出图了但跟我想要的不一样」，而不是「参数错了」。

界面该怎么防：`op` 只从下拉里取（值域 `GEN_OPS`，`net-gen.ts:49`），不要让它来自自由文本；
提交前用 `GET /gen-models?op=<op>` 把模型下拉先缩掉。

### 网络模型渠道带 `op` / `mask`：**明确报错，不静默忽略**

出处 `net-gen.ts:233-256`：

- `op` 不是 `caption` 且 `kind !== 'text'` → `GenError('unsupported')`，
  文案写明「它的 API 只有『生成 / 编辑』，没有超分、多角度、局部重绘。这类操作用 ComfyUI 渠道」。
- `mask` 给了 → `GenError('unsupported')`，「它的 API 没有『遮罩』这个参数」。

这条**是刻意**的：静默忽略会让人以为「我抹的遮罩生效了」。

## 二、`GET /api/ecom-workbench/gen-models?op=`

出处：`src/index.ts:1718-1737`（路由）、`generate.ts:765-778`（`ModelOption`）、
`generate.ts:789-802`（`listModels`）、`generate.ts:826-843`（`filterModelsByOp`）。

### 回包

```jsonc
{
  "ok": true,
  "op": "inpaint",     // 只在「请求带了可用的 op」时才出现
  "models": [ { "channelId": "ch-comfy", "channelName": "本地", "protocol": "comfyui",
                "modelId": "local", "modelLabel": "本地模型", "caps": ["image"] } ],
  "items": [ … ]       // 与 models 指向同一个数组（AGENTS.md 的「列表类接口键名约定」）
}
```

### 三条要记住的

1. **`op` 不认识 / 没给 → 回包里没有 `op` 这个键**，清单也不过滤。
2. **空数组不是错误**。`?op=upscale` 而没有任何渠道挂扩图工作流时，
   `models` 与 `items` 都是 `[]`、`ok` 仍是 `true`。界面该显示「这一类还没有渠道挂工作流，
   去渠道设置里选一份」，**不要显示「加载失败」**。
3. **`?kind=` 与 `?op=` 可以同时给**，先按 `kind` 过滤再按 `op` 过滤。
   路径是 `/gen-models`，**不是 `/models`** —— 那个路径是 dsh 的模型目录
   （`src/index.ts:1703-1717` 那段注释记了踩坑经过：同名路由不报错，先到的把后到的静静吃掉）。

### `?op=` 到底筛掉了什么

| 渠道协议 | 除 `caption` 外的四个 op | `caption` |
|---|---|---|
| `comfyui` | 这一类**有工作流**（渠道挂的或内置的）才留 | 同上（`text` 类有内置 `text-qwen3-5`，留） |
| `openai` / `gemini` | **一条都不留** | 留（Gemini 那条路能做带图问答） |

出处 `generate.ts:826-843`。`caption` 是唯一放行网络模型的 op。

## 三、`resolveMentions()`

出处：`src/schedule/mentions.ts`。**纯函数**：零依赖、不读存档、不碰 DOM，
界面直接 `import` 就能用（别的宿主半接口都得走 HTTP，这个是例外）。

### 签名

```ts
import { resolveMentions, listMentions } from '../../schedule/mentions.ts'

const r = resolveMentions(prompt, (nodeId) => targetOrUndefined)

// target:
interface MentionTarget {
  kind: 'text' | 'image' | 'video' | 'audio' | 'config' | 'other'
  name?: string          // 显示名
  text?: string          // 仅 text：正文
  artifact?: string      // 仅 image / video / audio：**产物 id**
}
```

### 返回

```ts
interface MentionResult {
  prompt: string       // 替换后的提示词，直接拿去 POST /generate
  refs: string[]       // ⚠️ **产物 id**（art-…），不是画布节点 id
  missing: string[]    // ⚠️ **画布节点 id**（n3 这种）
  textNodes: string[]  // 被拼进去的文本节点 id
}
```

### ⚠️ `refs` 是产物 id、`missing` 是画布节点 id

这是最容易接错的一处，两个数组装的是**两种不同的 id**：

| 数组 | 装什么 | 拿它干什么 |
|---|---|---|
| `refs` | **产物 id**（`art-abc123`） | 逐条 `GET /api/ecom-workbench/artifact/<id>` 取字节 → base64 → 塞进 `POST /generate` 的 `refs` |
| `missing` | **画布节点 id**（`n99`） | 在界面上把那个节点标出来（「这个引用找不到」） |

**`missing` 不是错误，也不用删任何东西** —— 提示词里那条提及**原文还在**
（`mentions.ts:143-204`，找不到就走 `out += src.slice(at, found.end)`）。
界面要做的是提示，不是清理。静默删掉等于吞掉用户输入。

### 从 `refs` 到 `POST /generate`：中间**必须有一步转换**

`refs` 里是**产物 id**，而 `POST /generate` 的 `refs` 要的是 **base64**。
直接塞会把 `art-abc123` 当成图片内容发出去（上游报「不是合法图片」，或者更糟：静默回一张占位图）。

三步走完：

```ts
// 1) 解析提及 —— 拿到产物 id
const r = resolveMentions(prompt, lookup)

// 2) 产物 id → 字节 → base64（逐条）
const refs = []
for (const artifactId of r.refs) {
  const res = await fetch('/api/ecom-workbench/artifact/' + encodeURIComponent(artifactId))
  const buf = new Uint8Array(await res.arrayBuffer())
  refs.push({ mime: res.headers.get('content-type') ?? 'image/png', base64: bytesToBase64(buf) })
}

// 3) 带着 refs 提交（提示词用 r.prompt，不是原文 prompt）
await call('/generate', { method: 'POST', body: JSON.stringify({
  kind: 'image', op: 'inpaint', prompt: r.prompt, model, refs, mask,
}) })
```

细节：

- `GET /api/ecom-workbench/artifact/<id>` 回的是**原始字节**（不是 JSON），
  `content-type` 就是那份产物的真 mime（`src/index.ts:1479-1497`）。所以 `mime` 从响应头取，别自己猜。
- `bytesToBase64` 是界面已有的工具（`src/client/workbench/ContentCanvas.tsx` 在用）。
- **提示词要用 `r.prompt`**（已经替换过的那份），不能用用户输入框里的原文 —— 原文里还是 `@[名字](n3)`。
- `r.missing` 只用来在做界面上提示，**不要因此中断提交**。

### 进 `missing` 的两种情形

1. `lookup(id)` 返回 `undefined` —— 画布上没有这个节点。
2. 节点在，但**引不出内容**：图片 / 视频 / 音频节点的 `artifact` 是空串
   （`mentions.ts:189-195`），或节点 `kind` 是 `config` / `other`（`mentions.ts:169-175`）。

### 替换规则

| 节点类型 | 原文 `@[名字](id)` 变成什么 |
|---|---|
| `text` | **正文直接插进来**（`mentions.ts:177-185`），不加任何标记 |
| `image` / `video` / `audio` | `[图: 名字]`（`mentions.ts:196-199`） |
| 找不到 / 引不出 | **原样保留**原文字符串 |

- `refs` 按**第一次出现**排序、去重（同一个节点被提及两次只进一次）。
  参考图的顺序会影响结果，所以不能靠对象键序。
- `@[](n2)`（名字空）**算合法**：名字只是标签、id 才是定位，显示名退回节点自己的 `name`。
  这条判断的理由写在 `mentions.ts` 文件头。
- 真正判成**畸形**（原样保留、不报错）：缺右括号、id 里有空白、名字里有换行。
- `listMentions(prompt)` 只解析不替换，回 `{ name, id }[]`，做输入框高亮用（`mentions.ts:212`）。

## 四、五个 `op` 各自要给什么

出处：`generate.ts:193-212`（`categoryOf` 的映射）、`generate.ts:283-294`（`workflowMissingWhy`）、
`comfyui-workflows/registry.ts`（内置清单）。

| op | 映射到哪类工作流 | 要给什么 | 不给会怎样 |
|---|---|---|---|
| `inpaint` | `inpaint` | `refs[0]`（底图）+ **`mask`** + `prompt` | 没 `mask` → 用工作流自带的占位遮罩 `1111.png`，**任务照样成功**（见上文「静默行为①」）。没 `refs` → 占位底图被裁掉、下游跟着塌，结果比「用占位图」更乱（「静默行为①」末尾） |
| `upscale` | `upscale` | `refs[0]`（原图）；`prompt` 可空；**没有倍率参数** | 内置**没有**这一类工作流 → 渠道没挂就报「没挂「放大」工作流…」 |
| `superResolve` | `superResolve` | `refs[0]`；**没有倍率参数** | 同上，内置没有 → 「没挂「超分」工作流…」 |
| `caption` | `text` | `refs[0]`（要反推的图）；`kind` 给 `'image'` 或 `'text'` 都行 | 两条路现在**都通了**（2026-10-26 修），但走网络模型时**那个模型必须真有 `text` 能力** —— 见下条 |
| `angle` | `angle` | `refs[0]` + `prompt`（写清转多少度 / 哪个角度） | 内置没有 → 「没挂「多角度」工作流…」 |

### `caption`（反推提示词）：两条路都能用（2026-10-26 修通）

这一条原先写过「两条路都不通」—— 那是当时的**真实状态**，不是推测。现在修好了，结论变了，这里同步。

**路一：ComfyUI（内置 `text-qwen3-5`）** —— 只有文本、没有文件，**任务成功**。

产出走 `textsOfHistory`（`comfyui.ts:981-1008`），与 `outputsOfHistory`（只挑文件）并列：

| 函数 | 挑什么 | 用在哪 |
|---|---|---|
| `outputsOfHistory` | `images` / `gifs` / `videos` / `audio` —— **能 `/view` 取回字节的文件** | 图片 / 视频 / 音频类 |
| `textsOfHistory` | `text` / `string` 里**真正是字符串**的项 | `text` 类（反推提示词） |

`runComfyGeneration` 的判据按类别分（`comfyui.ts:1219-1244`）：

- `category === 'text'` → **有文本就算成功**，文件可有可无；
- 其余类别 → **必须至少一个文件**，光有文本不算数（它们要的确实是文件，
  只看文本会让「工作流配错、只回了一段日志」也被当成成功）。

返回形状 `ComfyGenResult`（`comfyui.ts:1071-1086`）多了 `texts: string[]`（`:1083`），**没有文本时是空数组、不是 `undefined`**。

**文本怎么变成产物**：`runBranch` 把每条文本按 `text/plain; charset=utf-8` 存成产物
（`generate.ts:519`），所以界面的读法**不变** —— `task.artifacts[]` 里那一条的 `url`
取回来就是那段字。不另开 `task.texts` 字段，因为那会让界面写第二套展示分支。

**路二：网络模型（Gemini / 带图问答）** —— 能用了，但**模型必须真有 `text` 能力**。

请求侧会对网络模型的 `caption` **强制按 `kind: 'text'` 发**（`generate.ts:444-445` 的 `captionOnNet` / `effectiveKind`），
因为反推的产物是文字：调用方通常给 `kind: 'image'`（手里是张图），
但「能出图」不等于「能读图答字」—— 按 `image` 判会放行一个只会画图的模型，
然后它真去画图了（实测：回来一张图，不是一段描述）。

所以：

| 模型登记的能力 | 结果 |
|---|---|
| 只有 `image` | 提交后**被能力校验拦**：`模型 x 没有「text」能力（它有的是：image）` |
| 有 `image` + `text`（Gemini 那种） | 正常跑完，请求里**没有** `responseModalities`，回来是 `text/plain` 产物 |

`?op=caption` 的清单也照这个筛（`generate.ts` 的 `filterModelsByOp`：`op === 'caption' && m.caps.includes('text')`），
**只会画图的模型不会出现在 caption 的清单里** —— 列出来就是把用户引向一条必然报错的路。

真端到端（真打一次 Gemini）**还没验**，因为没有真 key；验的是请求形状与结果解析（假 `fetchImpl`）。

### 缺工作流时那句人话

`workflowMissingWhy` 分两支（`generate.ts:283-294`）：

- 这一类**内置也没有**（`superResolve` / `upscale` / `angle`）→
  「这个渠道没挂「超分」工作流，内置清单里也没有这一类（superResolve）：请去渠道设置里给它选一份工作流再试。」

失败时这句原文就在 `task.error` 里，**界面直接显示，不用自己拼**。

⚠️ **这句话的正确性依赖「那三类内置确实没有」这个前提**。`tests/gen-op.mjs` 的 ③b 段钉住了它

**真给这三类补了内置工作流时，那段会红，要回来改文案的判据。**

### `size` 的写法：比例会真算出宽高，认不出来会**失败**

`size` 走 `sizeBindings`（`generate.ts:666-683`），它现在**调 `parseSize`**（`comfyui.ts:614-647`）。
`parseSize` 认三种：

| 写法 | 结果 |
|---|---|
| 不填 / `auto` | 1024×1024 |
| `1024x1024`（x 或 × 都认） | 逐字填，超过 8192 判非法 |
| `16:9` | 短边 1024 → **1820×1024** |
| `9:16-2k` / `9:16_2k` | 带档位，2k → 长边 2048 |

**认不出来就失败，不静默**。原文示例：

```
尺寸写法认不出来：16：9（写成了中文冒号「：」，要英文冒号「:」）。
能写的是「1024x1024」「16:9」「9:16-2k」这几种；原来那句：尺寸不合法：16：9
```

⚠️ **这是一次行为改变**（2026-10-26 之前）：原先 `sizeBindings` 自己写了一份只认
`数字x数字` 的正则，认不出就返回 `{}` —— 于是 `16:9` 静默不填、工作流用它的默认尺寸、
**出图比例不对且没有任何提示**。而 16 份内置工作流里有 11 份确实带 `width`/`height` 槽位（逐份数过）。
现在的判据是：**用户填了东西就该生效，或者明确告诉他为什么没生效。**

失败时**不会提交给 ComfyUI**（`applyBindings` 在提交之前，白跑一次更糟）。

## 原先三条「已知不生效」的现状

2026-10-26 之前这里挂着三条。**现在三条都修好了**：

| 项 | 现状 |
|---|---|
| 比例尺寸（`size: "16:9"`） | **已生效**。`sizeBindings` 调 `parseSize`，比例真算出宽高；认不出来会失败并说清（见前节） |
| 负面提示词（`negativePrompt`） | **已生效**。**两条判据并用**：按标题认（含内置那份的整句 `CLIP Text Encode (Negative Prompt)`）∪ 按字段名认（`negative_prompt`）。16 份里有 2 处可填（见下节） |
| 一次出几张（`count`） | **已生效**。填进建 Latent 节点的 `batch_size`，按结构找不按标题（见下节） |

下面的小节留着，因为它们是**槽位名怎么定的依据**（哪几份工作流有、实际标题长什么样）。
换人接手时不要重新猜一遍。

### `count` 现在真生效（2026-10-26 修）

**16 份工作流里 4 份带 `batch_size`**：

| 工作流 | 节点 | 类 | `_meta.title` |
|---|---|---|---|
| `audio_minimax_music_3_api.json` | `53` | `EmptyMiniMaxMusic3LatentAudio` | 「空 MiniMax Music3 潜空间音频」 |
| `i2i_flux2_dev_api.json` | `164` | `EmptyFlux2LatentImage` | 「空Latent图像（Flux2）」 |
| `qwen_image_21_api.json` | `507` | `EmptyLatentImage` | 「空Latent图像」 |
| `t2i_z_image_turbo_api.json` | `57:13` | `EmptySD3LatentImage` | 「空Latent图像（SD3）」 |

**那 4 个标题都是描述性文字，不是槽位标记** —— 按 `_meta.title` 一条也匹配不上。

**做法：按结构找，不按标题。**

```
for (节点 in 工作流) if (typeof 节点.inputs.batch_size === 'number') { 填它; break }
```

为什么不用「给那 4 份 JSON 补 `_meta.title`」：**那 16 份与上游逐字节相同（SHA256 16/16）**，
改了将来上游更新就合并不了。而 `batch_size` 这个名字在 ComfyUI 里只有一个含义（一次出几张），
按结构找不会误伤 —— 这与 `seed` 的兜底（`comfyui.ts:320-326`）、`negativePrompt` 的字段名兜底是同一个套路。

规矩：

- `count > 1` 才填；`1` 或没给时**不动工作流**（那 4 份本来就是 `batch_size: 1`，改它无意义）。
- 只填**第一个**带 `batch_size` 的节点（一份工作流里可能有两处，只有一个在生效链路上）。
- **不循环提交 N 次** —— 那会把一次生成变成 N 次计费与 N 条记录。
- 工作流没有 `batch_size`（视频 / 音频那几类常见）→ `count` 不生效，但**任务照常成功**，不崩。

**产物数**：ComfyUI 一次跑完在 `/history` 的 `images` 里给 N 条，`outputsOfHistory` 全收，
所以 `count: 3` 会得到 3 条产物（实测断言过了）。

**边界**：`count` 只对**图片类**有意义。音频 / 视频类即使有 `batch_size` 也未必是「出几段」的意思，
界面不要对这几类显示张数输入。

### `negativePrompt` 现在真生效（2026-10-26 修）

**16 份内置工作流里有 2 处可填的负向文本**，各自靠**不同判据**认：

| 工作流 | 节点 | 类 | 认它的依据 | 字段名 |
|---|---|---|---|---|
| `inpaint_qwen_image_api.json` | `277` | `CLIPTextEncode` | **标题** = `CLIP Text Encode (Negative Prompt)` | `text`（与正向同一字段名） |
| `qwen_image_21_api.json` | `512` | `TextEncodeQwenImage21` | **字段名** = `negative_prompt`（标题是「文本编码 Qwen Image 2.1」，**一个 negative 都没有**） | `negative_prompt` |

```json
// inpaint_qwen_image_api.json — 节点 277（靠标题认）
"277": { "class_type": "CLIPTextEncode",
         "inputs": { "text": " ", "clip": ["275", 0] },
         "_meta": { "title": "CLIP Text Encode (Negative Prompt)" } }

// qwen_image_21_api.json — 节点 512（靠字段名认，标题里没有 negative）
"512": { "class_type": "TextEncodeQwenImage21",
         "inputs": { "prompt": ["485", 0], "negative_prompt": "", "resolution": 0, ... },
         "_meta": { "title": "文本编码 Qwen Image 2.1" } }
```

#### ⚠️ 这个数字被数错过三次，每次都错在「数形状而不是数性质」

把三种数法都记下来，免得下一个人再数第四遍：

| 数法 | 数出 | 错在哪 |
|---|---|---|
| `grep -l "negative"` 看**文件名** | 3 份 | 命中的多是**连线**：`KSampler.inputs.negative = ["52", 0]` 指向一个 `ConditioningZeroOut`，那是连线不是可填文本。`audio_minimax_music_3_api.json` 那一份整个是误命中 |
| 按**标题**搜 `negative` / `负面` / `负向` / `反向` | 1 份 | 漏掉了「标题里没有 negative、但字段名叫 `negative_prompt`」的 `qwen_image_21` |
| **结构判据**：`inputs` 里**键名**含 negative 且**当前值是字符串**（不是连线） | 1 处 | 也漏 `inpaint` 那份 —— 它的字段名是 `text`，只能靠标题认 |
| **两条判据合起来**（标题 ∪ 字段名） | **2 处** | ← 正确答案 |

**结论**：判据要盯**性质**（这个字段能不能填字符串），不是盯形状（有没有 negative 这个词、标题长什么样）。
两处必须**同时**用两条判据：
- 按标题认（含整句 `CLIP Text Encode (Negative Prompt)`、`negative`、`negative_prompt`、中文两种）；
- 按字段名认（`inputs.negative_prompt` / `inputs.negative` **且值是字符串**）。

**顺序**：按标题那条在正向 `prompt` 分支之后；按字段名那条在主循环之后（填到过就不再填）。
连线的判据是「值是字符串」—— `["52", 0]` 不是字符串，往那里写会把工作流写坏。

不给 `negativePrompt` 时那个槽位**保持原值**（不被写成空串）。

**其余 14 份工作流没有负向槽位**，给它们填负面提示词仍然「没地方放」——
那不是 bug，是那份工作流本身没有这个输入。界面别把它当成必填。

#### 正向那侧自查过，没有同类问题

`inputs` 里键名恰好是 `prompt` / `positive_prompt` / `positive` 且值是**字符串**的节点：
**16 份里 0 个**（逐份 JSON 解析过）。正向提示词全都走 `_meta.title = "prompt"` 那条判据
（比如 `qwen_image_21_api.json` 的节点 485 是 `PrimitiveStringMultiline`，标题就是 `prompt`）。
所以正向那侧不需要补「按字段名认」的第二条腿 —— 补了也没有对象可填。
