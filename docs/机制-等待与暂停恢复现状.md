## 一、现状：有四种「等」，两种机制

**这一节讲什么**：把「延迟」「等待（等时长 / 等时刻 / 等人点继续）」分清，并说清各自占不占进程、
能不能跨重启、在运行记录里长什么样。末尾讲一个已知的矛盾。

### 1.1 一张表看完

| | 延迟（`flow.delay`） | 等待 · 等一段时长 | 等待 · 等到某个时刻 | 等待 · 等人点继续 |
| --- | --- | --- | --- | --- |
| 定义位置 | `src/nodes/flow/delay/node.ts` | `src/nodes/flow/wait/node.ts:71` | 同左 `:72` | 同左 `:73` |
| 谁执行 | 内置函数 `delayFn`（`src/dispatch/builtins.ts:89-95`） | 调度器 `runWait`（`src/workflow/run.ts:2129`） | 同左 | 同左 |
| 等的时候进程 | **占着**：`setTimeout` 睡在同一进程里 | **放开**：存现场后**结束这次运行** | 同左 | 同左 |
| 能不能跨重启 | 不能 | 能 | 能 | 能 |
| 运行记录 | 一条记录，节点停在 `running`，直到睡完（`src/dispatch/dispatcher.ts:203-206`） | 两条：第一条标「等待中」，恢复后**新建**第二条 | 同左 | 同左 |
| 上限 | **没有上限**（`delayFn` 不判，见 1.4） | 20 天（`WAIT_MAX_MS`，`src/workflow/snapshot.ts:132`） | 20 天（下一天同一时刻，最多约 1 天） | 0 或 20 天（`timeoutHours`，`:99-109`） |
| 可否放进循环体 / 并行体 | 可以 | **明确报错，不许**（`run.ts:2160`、`:1709`） | 同左 | 同左 |

### 1.2 「延迟」怎么工作

- 参数只有两个：`ms`（延迟时长，**没有 max**，`node.ts:26`）、`random`（随机抖动，`:28`）。
- 实现就是一句 `await new Promise(resolve => setTimeout(resolve, ms))`（`builtins.ts:93`）。
- 输出**原样传上游**（`builtins.ts:94`），所以插在任意位置都不改数据流。
- 它**不进 `NODE_IMPLS`**、也不由调度器特判 —— 它就是一个普通 builtin 节点。

### 1.3 「等待」怎么工作

三种模式由 `readWaitPlan` 解析（`snapshot.ts:177`），一律**不猜**：参数不全、时刻写错、
超过 20 天都返回一句可读的错（`snapshot.ts:202-215`），由 `runWait` 当节点失败报出去
（`run.ts:2189` 的 `if (read.plan === undefined)`）。

三种模式的差别全在「什么时候该继续」这一个数上：

| 模式 | `resumeAtMs` 是什么 | 谁来触发继续 |
| --- | --- | --- |
| `duration` | 现在 + ms（`snapshot.ts:216`） | 30 秒扫一次的扫盘器（`src/index.ts:1328`） |
| `until` | 今天（过了就是明天）的那个 `HH:MM`（`snapshot.ts:143-155`、`:209`） | 同上 |
| `manual` 无超时 | `Number.MAX_SAFE_INTEGER`（`snapshot.ts:63`、`:191`） | **只有人点「继续」**（`src/index.ts:2359`） |
| `manual` 有超时 | 超时那一刻（`snapshot.ts:197-198`） | 到点被扫盘器捡起，但恢复入口判**失败**（见 2.6） |

`manual` 无超时用 `MAX_SAFE_INTEGER` 的技巧值得记一笔：它让扫盘器那句
`resumeAtMs > now` 天然跳过（`src/index.ts:1298`），于是**不必改扫盘器**就能实现「永不自动继续」
（理由写在 `snapshot.ts:55-61`）。

### 1.4 ⚠️ 已知矛盾：300 秒上限对「延迟」**实际上不成立**（与预期相反）

派发器确实配了单节点 300 秒（`src/dispatch/dispatcher.ts:166` 的 `timeoutMs: options.timeoutMs ?? 300000`，
宿主半构造时也明写 300000：`src/index.ts:602`）。但**它对延迟节点掐不断**，原因有两层：

1. **超时只是 abort 一个信号，不是 race**。`withTimeout` 的写法是
   `const timer = setTimeout(() => { timedOut = true; ac.abort() }, ...)`，然后
   `const r = await ex.run(merged); return timedOut ? { ...r, timedOut: true } : r`
   （`dispatcher.ts:249-259`）。也就是说：**执行方不理会信号时，就等它自己跑完**，
   超时只在事后打一个标记。
2. **内置执行方根本不给函数传信号**。`createBuiltinExecutor` 调内置函数时只传了
   `{ nodeId, workdir, upstream }`（`src/dispatch/executors.ts:169`）—— 没有 `signal`。
   而 `delayFn` 只用 `setTimeout`（`builtins.ts:93`），**没有任何能被打断的点**。

⇒ 结论（**已核实**）：把「延迟」填成 300000 毫秒以上，它会**真的睡完**，不会被掐断；
派发器那边会把这次标成 `timedOut: true`，但这个标记在 `dispatchNode` 返回时被**丢掉**了 ——
`dispatchNode` 只回 `ok / status / output / logs / error` 五个字段（`src/index.ts:638-645`），
`timedOut` 不在其中。

⇒ 连带后果（**推断**，依据上面两条）：如果用户把延迟填成 10 分钟想等视频生成，
它真的会等 10 分钟，但这一路：
- 占着工作流里一个节点并发槽（节点并发 2，`src/index.ts:602`）；
- 占着工作流级一个队列位（队列默认 2，`src/workflow/run-queue.ts:90`）；
- 期间界面上只显示「运行中」，**没有任何进度**；
- 停不下来 —— 但原因不在延迟本身，见 3.5。

所以「延迟不能用来等长任务」这个结论要改一个字：**不是不能，是不该** ——
它不会失败，它会让一份工作流、两个并发槽一起傻等。

### 1.5 运行记录里长什么样

运行记录的形状在 `src/workflow/workflow-runs.ts`：节点级 `state` 有六种，含 `waiting`
（`:72`，注释明写「等待中不是失败」）；运行级有 `waiting?: boolean` 与 `resumeAt?: number`
（`:126`、`:132`）。

写入点共四处，都遵守同一条规矩（挂起时 `ok` 保持原样、另标 `waiting`）：
`src/index.ts:926`、`:957`、`:1783`、`:2309`（四处的写法完全相同：
`...res.paused === undefined ? {} : { waiting: true, resumeAt: res.paused.wait.resumeAtMs }`）。

界面上「等待中」是运行历史里的一个独立小区块（`src/client/workbench/RunHistoryPanel.tsx:364-409`），
每 30 秒自己刷新一次（`:267-270`），每行两个按钮：「继续」与「放弃」。

## 二、一条运行挂起之后到底发生了什么

**这一节讲什么**：按时间顺序，从「决定挂起」到「恢复完 / 放弃」，每一步给代码出处。

### 2.1 谁决定要挂起

判据不是「等了多久」，而是「**跑到 `flow.wait` 这个节点了**」。
`runSeq` 按节点类型分派：`byId.get(id)?.def.id === WAIT_DEF_ID` 时走 `runWait`
（`src/workflow/run.ts:2270`，`else if (byId.get(id)?.def.id === WAIT_DEF_ID) await runWait(id, ctx)`；
`WAIT_DEF_ID = 'flow.wait'` 定义在 `:65`）。

`runWait` 开头先做两件与其它节点相同的事（`run.ts:2129` 起）：
1. **可达性判断**：上游那条路这次没走 → 判未走分支、跳过（`:2134`，
   `if (!hasLiveInput(id, ctx) && hasAnyInput(id) && …)`）。
2. **跳过判断**：节点被标记 `skipped` → 上游原样穿下去（`:2141`，`if (spec.skipped)`）。

然后有一道**硬拦**：等待节点**不能在循环体里**（`run.ts:2160`）。报错原文：

> 「等待」节点不能放在循环里（循环体的恢复本版本还不支持）：{id}。循环体内如需等待，请使用「延迟」节点。

并行体里同样有这道拦（`run.ts:1709`）。理由写在两处注释里，是同一个：
现场只记「从哪个节点之后继续」，而恢复时按**主序**切片（`mainOrder.indexOf`），
循环体 / 并行体的节点不在主序里，切片会落空 → 恢复＝整份从头跑 → 再挂一次，永远跑不完。

### 2.2 现场存到哪、存了什么

**存哪**：`data/ecom-workbench/paused/<runId>.json`，一运行一个文件
（`pausedDir`，`src/workflow/pause-store.ts:36-38`；文件名经 `safeName` 防穿越，`:48-50`）。

**存什么**：`RunSnapshot` 结构，共 12 个字段（`src/workflow/snapshot.ts:92-123`）：

| 字段 | 含义 | 为什么要有 |
| --- | --- | --- |
| `version` | 形状版本，固定 `1` | 读回时判兼容（`asSnapshot` 只认 1，`:228`） |
| `runId` | 运行 id，也是文件名 | — |
| `workflowId` | 工作流名 | 恢复时按它**重新读存档**（`src/index.ts:884`） |
| `startedAt` / `pausedAt` | 开始 / 挂起时刻 | 回看与排序 |
| `resumeAfter` | 从**哪个节点之后**继续 | 见下条 |
| `ran` | 已跑过的节点（去重） | 恢复后运行记录要延续 |
| `executions` | 实际派发次数 | 循环时与 `ran` 不等 |
| `outputs` | 每个节点的输出（JSON 化） | 否则恢复后下游拿不到前半段数据 |
| `unreachable` | 已判「未走分支」的节点 | 不恢复的话它们会突然开始跑 |
| `inputs` | 本次实际生效的输入 | 与 `outputs` 同理 |
| `wait` | `WaitPlan`：模式 + `resumeAtMs` + …… | 扫盘器与超时判断都靠它 |

**为什么是 `resumeAfter` 而不是「从哪个节点开始」**：等待节点自己的输出（上游原样穿过去）
已经写进 `outputs` 了（`run.ts:2175-2180`，`outputs.set(id, through)`），再跑一次它会**再挂一次**，
无限循环 —— 这条写在 `snapshot.ts:103-109` 的字段注释里。

**落盘必须排队**：同一份运行可能同时被「跑完的清理」与「恢复的删除」碰到，
所以每个文件一条串行队列（`pause-store.ts:53-72`）。这一段是项目红线级的东西：
运行历史曾因为不排队而丢过记录（`pause-store.ts:9-14` 有长注释追责）。

### 2.3 进程怎么收尾

**挂起是一次异常，不是一个返回值**。`runWait` 组装好现场后直接
`throw new RunPausedError(snap)`（`run.ts:2244`）。

为什么必须是异常：挂起可能发生在**任意深度**（循环里、并发里），返回值的路要逐层判
「是不是挂起了」，任何一层漏判就会继续往下跑 —— 那正是「暂停没停住」这种最难查的坏行为
（理由写在 `RunPausedError` 的类注释里，`run.ts:333-345`；类本体在 `:347`）。

两道 catch 都**先认它、再谈失败**：
- `runSeq` 的 catch 第一行：`if (e instanceof RunPausedError) throw e`（`run.ts:2280`），
  原样再抛，不被 `onError` 的失败策略吞掉；
- `runGraph` 主序那一层：抓到后写进 `pausedAtEnd`（`run.ts:2338`），然后**照常返回**
  （`ok: true`、`aborted: false`、多带一个 `paused` 字段，见 `:2415-2424` 的返回值）。

**挂起时不收口**：结束节点声明的产出**整段跳过**（`run.ts:2397-2400` 的注释与判据
`if (endSpec !== undefined && paused === null)`）。理由：产出是「跑完之后交出的值」，
半截的产出比不产出更坏。

**宿主半落盘**：`/workflow/run` 那条路在 `src/index.ts:1865` 起，
判据是 `res.paused !== undefined` 时 `await savePausedRun(paused)`（`:1868`）。
存不上**当成失败**报出去（`:1877`，文案「运行现场存不下（磁盘？），这次没法恢复 —— 当成失败处理」），
不假装挂起 —— 假装的话用户会等一个永远不来的恢复。

### 2.4 谁负责把它捡起来

**一个 30 秒的扫盘器**，注册在 `ctx.effect` 里（`src/index.ts:1269` 起那段注释，
`beat` 函数在 `:1290`，定时器在 `:1328`）。每一拍：

1. `listPausedRuns()` 读整个目录（`:1295`；实现见 `pause-store.ts:158-176`，坏文件跳过、按 `pausedAt` 倒序）；
2. 逐份判 `snap.wait.resumeAtMs > now` → 跳过（`:1298`）；
3. 正在恢复的记在 `resuming` 集合里，跳过（防同一份被扫两次）；
4. 调 `resumePausedRun(snap, 'auto')`；
5. **失败要提醒**：`(await readNotifyPrefs()).failNotify` 为真时弹通知（`:1313`）。
   读偏好失败由 `readNotifyPrefs` 自己吞掉并回默认值。

两个细节：
- 定时器 `unref()`（`:1329`），不会吊住进程；
- **起来时先扫一次**（`:1331` 的 `beat()`），插件重启后那些「早就该继续」的现场不必再等半分钟。

**为什么是扫盘而不是「挂起时算好 setTimeout」**（`src/index.ts:1269-1280` 那段注释）：
挂起本来就跨重启，那时根本没有那个定时器了；而每 30 秒比一次 `resumeAt` 是幂等的 ——
重启、休眠唤醒、改时间，下一秒都比得出来。

### 2.5 恢复时怎么接上

恢复**不是「把那个 Promise 接着跑」**，而是「拿现场 + 存档**从头调一次调度器**」——
挂起时那次运行已经结束了，栈都散了（理由见 `src/index.ts:846-865` 的注释
「为什么是「重新调 `runWorkflowFile`」而不是「把那个 Promise 接着跑」」）。

`resumePausedRun`（`src/index.ts:870`）的六个步骤：

| # | 做什么 | 出处 |
| --- | --- | --- |
| ① | **先删现场**再跑（跑的过程中若又挂一次，会写下新的一份；不删则两份并存说不清谁是当前） | `:875` |
| ② | 生成**新的** runId 与开始时间 | `:878-879` |
| ③ | 走**同一个**工作流队列（各开一个等于上限翻倍） | `:884` |
| ④ | 把现场当 `resume` 传进 `runWorkflowFile` | `:891` 附近 |
| ⑤ | 运行记录**新建一条**（`via: 'resume-auto'` / `'resume-manual'`），不是改原来那条 | `:921`、`:938` |
| ⑥ | 只有**真跑完**才归档产出（挂起时产出是半截的，写进去等于污染板块记录） | `:942` |

调度器侧怎么用现场（`RunGraphInput.resume` 的三条语义，`run.ts:164-182`）：

1. `outputs` / `ran` / `executions` / `inputs` **从现场恢复**（`run.ts:586` 的 `resolvedInputs`、
   `:699` 的 `Object.entries(resume.outputs)`、`:701` 的 `[...resume.ran]`、`:703` 的 `executions`）；
2. `unreachable` 也恢复（`:733`）；
3. **从 `resumeAfter` 的下游开始**：`mainOrder.indexOf(resume.resumeAfter)` 取下标，
   再 `.slice(下标 + 1)`（`run.ts:635-636`）。

**恢复时不能中途改的东西**（写好在那段注释里的）：
- `targets`（「只跑这几个节点」）在恢复时**被忽略** —— 现场里已经定死了「这次要跑整张图」；
- 工作流存档如果在那之后被改过，恢复用的是**当前存档**的行为 + 旧现场的 `ran`/`outputs`，
  两者可能对不上。这一点**代码里没有防护、也没有说明**（见第三节第 3 条）。

### 2.6 失败 / 超时 / 用户放弃分别怎么处理

| 情形 | 发生了什么 | 出处 |
| --- | --- | --- |
| **恢复时又挂一次**（工作流里有第二个等待节点） | 存下**新的**现场，记录里 `waiting: true` 且 `resumeAt` 换成新的；界面上那行**留在原处**，只更新时刻 | `src/index.ts:929-937`；前端 `RunHistoryPanel.tsx:300-308` |
| **恢复时节点失败** | 照常按 `onError` 走；记录 `ok: false`；`failNotify` 为真则弹通知 | `src/index.ts:904`、`:1313` |
| **`manual` 超时到了** | 扫盘器会把它捡起来（`resumeAtMs` 就是超时时刻），恢复入口判**失败**：`manualExpired` 非空 → 主序被清空（`run.ts:651-657`）、`aborted = true`（`:2349`） | `snapshot.ts:285-294`（返回的超时说明原文） |
| **用户点「放弃」** | 删掉现场文件，之后不再自动恢复。**运行记录不动** | `src/index.ts:2351-2357`（路由）；`removePausedRun`（`pause-store.ts:134-147`，不存在也算成功） |
| **用户点「继续」** | 走 `resumePausedRun(snap, 'manual')`，**不等**到点 | `src/index.ts:2359` 起 |
| **现场文件坏了 / 手改坏** | `asSnapshot` 判不过 → 返回 `null` → 当作「没有这份现场」，不抛 | `snapshot.ts:225-264` |
| **现场存不下** | 当失败处理，不假装挂起 | `src/index.ts:1868`（存）、`:1877`（失败文案） |

**「放弃」有一个静默的后果**（**已核实**）：删现场只是删 `paused/<id>.json`，
**运行记录里那条 `waiting: true` 不会被改**（`src/index.ts:2351-2357` 只调了
`removePausedRun`）。于是运行历史里会留一条永远「等待中」的记录，而等待中区块里已经没有它了。
界面上点「放弃」时前端会把它从当前列表摘掉（`RunHistoryPanel.tsx:332`），所以当场看不出来；
**下次打开运行历史才会看到那条悬挂的记录**。

## 三、需要审查的判断点（六条）

**这一节讲什么**：每条都是「现在怎么做（事实）→ 另一种做法 → 两种代价 → 建议」。
这是全文唯一允许有意见的地方。

### 3.1 「延迟」与「等待」该不该合并

**现在**：两个节点、两套机制。延迟 = `setTimeout` 睡在进程里（`builtins.ts:89-95`）；
等待 = 存现场 + 结束运行 + 扫盘恢复（`run.ts:2129` 起）。分工写在两个节点的头部注释里
（`delay/node.ts:16-23`、`wait/node.ts:16-23`），原则是「几秒用延迟，几小时用等待」。

**另一种做法：合并成一个「等」节点，用参数区分钟级 / 小时级**。
好处是界面上少一个概念，用户不必先判断「我这算几秒还是几小时」。

**两种代价**：

| | 现在（两个节点） | 合并成一个 |
| --- | --- | --- |
| 用户要做的判断 | 必须先想「这次会不会超过几十秒」 | 不用想 |
| 记录噪音 | 几秒级不产生额外记录 | **每次小睡都多一条运行记录**（等待必然新建记录，`index.ts:938` 的 `appendRun`） |
| 停得住吗 | **两者都停不住**（全链路取消信号被覆盖，见 3.5）；等待至少在「等」的这段时间里运行已经结束 | 取决于底层走哪条 |
| 画布可读性 | 两个节点名字不同，一眼看出是长等还是小睡 | 靠参数才能看出 |
| 出错面 | 两套代码、两套测试（`pause-*.mjs` 与 `delay` 相关用例） | 一套，但内部分叉照样会有两块逻辑 |

**建议：不合并。** 理由不是「两家都这样」，而是这两件事的**物理性质**不同：
一个占着进程、一个放开进程。合并成参数后会退化成「一个节点、两套隐藏行为」，
而用户填错参数时（本该等 3 秒填成等待）会**凭空多一条运行记录**、还得手工去恢复。
⚠️ 但**停止无效**这件事必须先修（见 3.5），否则「延迟」这个节点本身是不安全的：
填一个长时长之后，用户既没法等它快点结束、也没法叫停。

### 3.2 等的时候进程占着 vs 放开

**现在**：延迟占着（`setTimeout`）；等待放开（结束运行）。两者的代价都写在
`wait/node.ts:16-23` 的那张小表里，一句话是「延迟不能等几小时、也不能重启；
等待能跨重启，但会多一条运行记录」。

**另一种做法：让延迟也「放开」**（睡的时候把并发槽让出去，只留一个闹钟）。
或者反过来：让等待也用「进程内等」，但支持跨重启的兜底。

**两种代价**：

| | 现在（延迟占着） | 延迟也放开 |
| --- | --- | --- |
| 并发被占 | 一个延迟 10 分钟 = 占掉 1/2 节点并发（`index.ts:602`）+ 1/2 工作流队列（`run-queue.ts:90`），两份同时延迟就全堵死 | 不占，但**要新写一套「可挂起的延迟」**，本质就是等待 |
| 用户看到什么 | 节点「运行中」转 10 分钟，**没有任何进度** | 与等待相同：运行结束、列表里多一条「等待中」 |
| 能不能停 | 现在停不住（3.5，全链路） | 能（前提是 3.5 先修；只放开并发而取消信号仍然被覆盖的话，照样停不住） |
| 实现变化 | — | 相当于把延迟做成等待的一种模式，两个节点又回到 3.1 的合并问题 |

**建议：保持现在这样，但把「不许填太大」做成明面上的限制。**
具体是：给延迟的 `ms` 加一个上限（比如 60 秒），超了给一句可读的错并指向「等待」节点
（现在的 `ms` 参数**没有 max**，`delay/node.ts:26`）。
理由：这既保住了「几秒不产生记录」的好处，又把「拿延迟等长任务」这条路当场堵住 ——
现状是它不报错、真的傻等（停止的问题另见 3.5）。

### 3.3 跨重启的代价：现场落盘的东西多了会怎样

**现在**：现场是**一份 JSON，一个运行一个文件**（`pause-store.ts:36-38`），
里面含 `outputs`（每个节点的输出全量）。宿主的列表接口特意**不返回 `outputs`**，
因为「一份采集的原始数据可能很大」（`src/index.ts:2334` 的注释）。

**另一个做法：现场只存「引用」，大输出落到别处按需取**（比如输出单独一个文件、现场只存指针）。

**两种代价**：

| | 现在（全量进 JSON） | 存引用 |
| --- | --- | --- |
| 现场大小 | 与数据量成正比。一份采集几 MB 的 JSON 是可能的 | 固定很小 |
| 恢复时读的代价 | 一次 `readFile` + `JSON.parse`（`pause-store.ts:112-122`） | 要多读 N 个文件，**任何一个丢了现场就不完整** |
| 实现复杂度 | 低（一个文件、一次写） | 高（要管两批文件的一致性与清理） |
| 磁盘会不会涨 | 会：挂起期间一直躺着。**代码里没有任何过期清理**（已核实：`removePausedRun` 只在恢复时 `index.ts:875`、放弃时 `:2355` 被调） | 同样会涨（引用指向的文件还得有人清） |

**建议：先不做「存引用」，但补两件小事。**
① 「等待中」列表上加一个「这份现场多大」的显示（现在完全看不到，用户不知道磁盘被占了多少）；
② 加一条过期清理：`pausedAt` 超过 N 天且 `mode` 是 `duration`/`until` 的（`manual` 无超时的不动），
扫盘时顺手报一条「这份早已该恢复，但一直没成功」。
理由：现在**没有任何东西会提示「有一份现场躺了三个月」**，
而且它每 30 秒被扫一次、每次都跳过（`index.ts:1298`），永远安静。

### 3.4 视频那种「提交 + 查询」的长任务，该用等待还是另做机制

**事实**：现有两条路都别扭 ——
- 延迟：会等、但占并发、没进度、停不住（3.5 全链路那条）；
- 等待：能跨重启，但**「等到某个时刻」只能填 `HH:MM`**（`snapshot.ts:143`），
  精确不到「18 秒后再查一次」；用它做轮询会让每次查询多一条运行记录。

**另一种做法：给「轮询」单开一种机制**，形如「重复执行这段、直到条件成立或超时」。
我们其实已经有零件：循环的跳出条件（`flow.loop` 的 `breakConditions`，`loop/node.ts:115`）
+ 延迟节点。拼得出来，代价见下。

**两种代价**：

| | 用「循环 + 延迟 + 跳出条件」拼 | 新做一种「轮询」机制 |
| --- | --- | --- |
| 现在能不能用 | **能**（零件都在） | 不能，要写 |
| 画布可读性 | 多 3~4 个节点，业务意图被轮询噪音盖住 | 一个节点 |
| 等待期间 | 占着并发槽（延迟占着，见 3.2） | 可做成放开 |
| 跨重启 | **不能**（循环体里不许放等待，`run.ts:2160`；延迟不跨重启）→ **重启就丢** | 可做成能 |
| 实现代价 | 0 | 要动调度器（新增一类「由调度器解释执行」的节点，参照 `runWait` 的分派位置 `run.ts:2270`） |

**建议：先用「循环 + 延迟 + 跳出条件」跑通，别急着做新机制。**
理由：视频生成到底要等多久、多久查一次，**目前只有厂商文档上的一句话**
（见 `内容/调研-图片与视频生成工作流.md` 的视频一节），没有任何本地实测。
在不知道真实耗时分布之前做「轮询机制」，八成会按错的数字设计超时与间隔。
⚠️ 前提是 3.5 先修：轮询里必然有延迟，停止无效的话这个方案在真机上没法用。
等实测出来、且确认要跨重启，再做第二种。

### 3.5 ⚠️ 「停止」对所有节点都无效（不只是延迟）—— 建议最优先修

**事实分三层，每层都已核实**：

1. **入口是通的**：`/run` 路由建了一个 `AbortController`，客户端断开（＝点停止）时 `ac.abort()`，
   并把它当 `signal` 传给 `d.dispatch`（`src/index.ts:1574-1600`，`signal: ac.signal` 在 `:1594`）。
2. **派发器把它丢了**：`withTimeout` 里自己新建了一个 `AbortController`，
   然后 `const merged: DispatchRequest = { ...req, runId: id, signal: ac.signal }`
   （`src/dispatch/dispatcher.ts:254`）—— 这一行**用新信号盖掉了外部传进来的那个**，
   而且**没有监听外部信号去 abort 自己的那个**。外部信号只在 `{ ...req }` 里被展开了一次，
   紧接着就被同名键覆盖。
3. **即使不丢，内置函数也拿不到**：`createBuiltinExecutor` 调内置函数时只传
   `{ nodeId, workdir, upstream }`（`src/dispatch/executors.ts:169`），没有 `signal`。
   而 `delayFn` 只有一个 `setTimeout`（`builtins.ts:93`），没有任何能被打断的点。

**由这三层代码事实推出的结论（推断，不是读到的原文）**：
四种执行方**都收不到用户点的停止** —— shell / http / agent 各自的
`req.signal.addEventListener('abort', …)`（`executors.ts:75`、`:284`）挂的是派发器自建的那个
只受超时触发的信号；`executors.ts:94` 与 `:286` 那两处 `if (req.signal?.aborted === true)`
也就只在**超时**时成立，永远等不到用户点停止。
所以这不是延迟的专属问题，是**全链路**的。
真机验证方法（本轮没做）：跑一个 `code.shell` 填 `ping -t 127.0.0.1`，点停止看进程是否退出。

**另一个做法：派发器把外部信号接进来**（几行）：
`if (req.signal !== undefined) req.signal.addEventListener('abort', () => { ac.abort() }, { once: true })`，
以及给 `BuiltinFn` 的 `ctx` 补一个 `signal` 字段。

**两种代价**：

| | 现在 | 接上外部信号 |
| --- | --- | --- |
| 点「停止」 | 界面上按钮是假的：节点照跑，直到自己结束或撞到 300 秒 | 立刻停 |
| 并发槽 | 停止后仍被占着（节点并发 2，`index.ts:602`） | 立刻释放 |
| 实现量 | — | 派发器 **3 行**；内置函数 ctx **1 个可选字段**；延迟与 `code.js` 各自监听一次 |
| 测试影响 | — | 要给「外部取消能传到执行方」补一条用例（现在**没有**：`tests/host-dispatch.mjs` 全文只出现一次 `signal`，且是进程退出事实那个字段，不是取消）。已有的 `agent-node.mjs` 测的是**超时**与执行方自己的取消语义，覆盖不到这一层 |
| 风险 | — | 低。信号是可选字段，不传就是现在的行为；但**行为会变**：以前点了不动的节点现在会立刻变成 `cancelled`，界面上要从「运行中」跳到「已取消」——这条要真机看一眼 |

**建议：修，且优先于本文件其它所有条目。**
理由：这是界面上的一个**假按钮**。而且它把 3.4 那条「先拼轮询」的方案也拖下水 ——
轮询里必然有延迟，一旦要停就停不住；浏览器与子进程那类长任务同理。

> 记一笔文档史：本节早先的版本把这条写成「延迟节点停不住」，那是从一个现象反推的；
> 顺着信号流查到根因在派发器之后，结论改成上面那个范围更大的版本。以本节为准。

### 3.6 等待节点不能在循环体 / 并行体里 —— 这是功能缺口，不是设计选择

**事实**：两处硬拦，都当场报错（`run.ts:2160` 循环、`:1709` 并行），报错文案指向「改用延迟」。
根因写得很清楚：恢复按**主序**切片，而循环体 / 并行体的节点不在主序里（`run.ts:632-634`）。

**已知的真实后果**（来自 `.scratch/工作台-模型与汇报/issues/01-第四轮汇总.md:112`）：
「千川那份的登录等待」—— 它的登录检查在循环体内，所以**接不上**等待节点。
也就是说：现在没法在批量采集途中等一次人工登录。

**另一个做法：现场改成记「路径」而不是「节点 id」**（第几层循环、第几轮、体内第几个节点），
恢复时按路径重建作用域。

**两种代价**：

| | 现在 | 记路径 |
| --- | --- | --- |
| 千川那类场景 | 做不到 | 能做 |
| 实现 | — | 要改 `RunSnapshot` 形状（`version` 得升到 2，`snapshot.ts:94`）、
`asSnapshot` 兼容两版、`runGraph` 的恢复切片、以及循环每轮的作用域重建。
**测试面很大**：`pause-resume`、`pause-e2e`、`pause-store`、`loop-plan`、`run-graph`、
`wait-manual` 都要跟着看 |
| 老现场 | — | 旧版（`version: 1`）现场必须还能读，否则挂着的那些直接作废 |

**建议：明确写「本版本不支持」，把报错文案再往前走一步。**
现在的文案已经说清了（「配置不支持，不是出了故障」），但**没有告诉用户替代方案**。
建议在报错里补一句人名级的指引：「循环里要等人工，请在循环体外先放一个等待节点，
或在循环里用延迟重试」。真正的「循环体内等待」等 3.4 的结论出来再一起做 ——
两者要改的是同一块（恢复切片）。
