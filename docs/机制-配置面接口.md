# 配置面接口

> 面向**界面那一半**（`src/client/workbench/`）。这一页写的每个形状都能在代码里找到出处，
> 出处一律写成 `文件:行号`。**改动代码后如果这里对不上，以代码为准并回来改这一页。**
>
> 管的是**配置面**这五块：拉模型、默认模型、存储目录、提示词源、渠道模型形状。
> 生成那条链路（`/generate`、`/gen-models`、`resolveMentions`）见
> [生成与图像操作接口](机制-生成与图像操作接口.md)。

## ⚠️ 先说最重要的一条：`POST /generate` 的 `model` 可以不给，**界面不许自己回落**

```ts
// ❌ 这两行必须删掉（曾经是 ContentCanvas.tsx:1493 / :1550 / :1552-1553）
const model = (d.model ?? '').trim() !== '' ? (d.model ?? '').trim() : (ms.data[0]?.modelId ?? '')
const channelId = (d.channel ?? '').trim() !== '' ? d.channel : ms.data[0]?.channelId
```

**取清单里的第一个，不是「设置」，是撞运气**：换一个渠道、换一台机器，出的东西就变了，
而用户什么都没改。这正是用户点名问的那句话：

> 「我都没看到生图、视频、文本、音频这些的模型设置在哪，节点是怎么知道自己该用什么模型的？？？」

**现在后端有三层（`generate.ts:360-388` 的 `resolveGenerationTarget`）：**

| 层 | 情况 | 结果 |
|---|---|---|
| ① | 调用方给了 `model` | 用它 |
| ② | 没给 → 读「默认模型」里这一类 | 用**它的渠道 + 模型** |
| ③ | 默认也没设 | **报错**，见下 |

第 ③ 层的原文（`generate.ts:382-387`）：

> 这次生成没有指定模型，而「生图」这一类还没有设默认模型。去工作台设置的「默认模型」里给
> 「生图」选一个再试；或者在这次提交里直接指定模型。（以前没指定会静默取模型清单里的第一个
> —— 那样出来的是什么全凭渠道顺序，已经改掉了。）

⚠️ **界面若自己回落，就等于把「撞运气」装回来，还盖住了后端那句话** ——
用户看到的会是一张不知用什么模型画的东西，而不是「去设置里选一个」。
`POST /generate` 的 HTTP 层**不再校验 `model` 必填**（`src/index.ts:1656-1661` 那段注释即依据），这是刻意的：
「有没有出处」要看磁盘上的默认模型文件，HTTP 那一层判不了。

**四类的中文名**（`generate.ts:391` 的 `KIND_LABEL`）：`image`→生图、`video`→生视频、
`text`→文本、`audio`→音频。报错里用的就是这几个，界面照抄即可。

## 一、拉模型清单

`GET /api/ecom-workbench/channels/:id/models?kind=<可选>` — `src/index.ts:1772`

拿这个渠道的 `baseUrl` + 密钥去**真拉一次**上游。返回的是「上游有什么」，
**还没有能力标记** —— 用户勾哪些、各标什么能力，是界面那一侧的下一步。

### 三条协议的路径

| 协议 | 端点 | 出处 |
|---|---|---|
| `comfyui` | `{base}/api/experiment/models/<类别>` | `model-fetch.ts:103` `comfyModelsUrl` |
| `openai` | `{base}/v1/models`（地址已带 `/v1` 时不重复加） | `model-fetch.ts:119` `openAiModelsUrl` |
| `gemini` | `{base}/v1beta/models` | `model-fetch.ts:131` `geminiModelsUrl` |

### ComfyUI 必须带 `?kind=`

四个取值（`model-fetch.ts:45` `COMFY_FETCH_KINDS`，接口路径段的映射在 `model-fetch.ts:57`）：

| `?kind=` | 实际请求的路径段 |
|---|---|
| `diffusion` | `diffusion_models` |
| `text_encoder` | `text_encoders` |
| `checkpoint` | `checkpoints` |
| `vae` | `vae` |

⚠️ **`text_encoder` 与 `text_encoders` 是两个名字**：参考项目的界面叫 `clip`、接口叫
`text_encoders`，我们对外叫 `text_encoder`。**不要自己拼**，用上表。
不带 `?kind=` 会给一条 `no-endpoint` 的错，说明要哪一类。

### 回包

```jsonc
// 成功（注意：**没有** items 键，见下文「为什么这一组不给 items」）
{ "ok": true,
  "models": [{ "id": "flux1-dev.safetensors", "label": "flux1-dev.safetensors" }],
  "url": "http://127.0.0.1:8188/api/experiment/models/diffusion_models" }

// 失败（**HTTP 仍是 200**，看 ok）
{ "ok": false, "kind": "auth", "status": 401, "url": "https://…/v1/models",
  "models": [],
  "error": "密钥不对或没权限（HTTP 401）：检查这个渠道的密钥填了没有、有没有过期、这个账号能不能列模型。" }
```

`url` 一定要显示或至少记进日志 —— **地址写错是最高频的原因**，而它是唯一能一眼看出这点的地方。

### 四种失败：一张对照表（这是「失败要说清」的落地）

`kind` 的四个值（`model-fetch.ts:42` `FetchFailKind`），分类逻辑在 `model-fetch.ts:215-298` `requestOnce`：

| `kind` | 什么情况 | 界面显示什么 | 用户该去改什么 |
|---|---|---|---|
| `unreachable` | fetch 抛错（连不上 / DNS / 拒绝连接） | 「连不上这个地址：…」+ 上游原文 | **地址写错**、端口没开、服务没起 |
| `auth` | 401 / 403 | 「密钥不对或没权限」 | 密钥填了没有、过期没有、这个账号能不能列模型 |
| `no-endpoint` | 404 / 405 | 「这个地址没有列模型的接口」 | **协议选错了**（OpenAI 兼容 / ComfyUI / Gemini 是三条不同的路），或 ComfyUI 版本不对 |
| `upstream` | 其它非 2xx / 回的不是 JSON | 「上游返回 HTTP xxx：」+ 上游原文 | 上游自己的问题，把那句话显示给用户 |

**「连不上」与「没这个接口」必须分开**：看到「连不上」会去查网络，而实际上可能是
「这个地址不是 OpenAI 兼容的」—— 两件事的修法完全不同。`tests/model-fetch.mjs` ④ 段
有一条专门钉这个（`四种失败的 kind 是四个不同的值`）。

**空数组不是失败**：`ok: true` + `models: []` 的意思是「这个渠道这一类**确实**一个都没有」，
`error` 里会写「这个地址的「vae」这一类一个模型都没有」。界面该显示「这一类没装模型」，
不要显示「加载失败」。

### 为什么这一组不给 `items`

`AGENTS.md` 的约定是「列表类接口同时给具名键 + `items` 指向同一个数组」。
**这里刻意不照做**，因为回包里的主体是 `{ok, kind, status, url, error, models}` 一组
**并列字段**，不是一个数组。硬包一个 `items: [...]` 会让通用渲染函数读到一个
「只有一个元素的数组」，把一次拉取结果显示成一条记录。

判据：**回包的主体是「一条记录 + 一组状态字段」时不给 `items`；主体是「一组同类条目」时给。**
`/model-defaults` 同理（它是映射，四个键）。

## 二、默认模型

`src/schedule/model-defaults.ts`。存 `data/ecom-workbench/model-defaults.json`，与 `channels.json` 同级。

### `GET /api/ecom-workbench/model-defaults` — `src/index.ts:1797`

```jsonc
{ "ok": true,
  "defaults": { "defaultImageModel": { "channelId": "ch-a", "modelId": "img-1" } },
  "status": { "image": true, "video": false, "text": false, "audio": false },
  "broken": { "image": "这条默认指向的渠道已经不在了：ch-x" } }
```

- `defaults` 只有设过的类（没设的键不出现）。
- `status` 四类各一个布尔值（界面画「已设 / 未设」）。
- **`broken` 是这次加的**：设了默认、但那个渠道或模型**已经不在了**时，这里给一句原因。
  界面该把它标红 —— 否则用户以为设好了，生成时才失败。

### `PUT /api/ecom-workbench/model-defaults` — `src/index.ts:1824`

```jsonc
// 两种写法都收
{ "defaults": { "defaultImageModel": { "channelId": "ch-a", "modelId": "img-1" } } }
{ "defaultImageModel": { "channelId": "ch-a", "modelId": "img-1" } }
```

- **整份覆盖**：没给的类就被清掉（`null` / 缺键 = 回到「没设」）。
- **半条引用不收**（只有 `channelId` 没有 `modelId`，或反过来）—— 它比没有更糟：
  会让人以为设过了。见 `model-defaults.ts:81` `asModelRef`。
- 四个键名（`model-defaults.ts:44` `DEFAULT_KEYS`）：`defaultImageModel` / `defaultVideoModel` /
  `defaultTextModel` / `defaultAudioModel`。

⚠️ **路径是 `/model-defaults`，不是 `/model-prefs`**。后者已经被 dsh 的模型目录用过
（`/models/prefs`），本项目为此踩过路由撞车（生成那条路被迫改成 `/gen-models`）。
加路由前先 grep。

### 为什么单独一个文件、不放进 `channels.json`

默认模型是**插件级偏好**（「没特别指定时用哪个」），不是渠道的属性。塞进渠道表会有两个问题：
一条渠道被删掉时偏好跟着消失（用户其实只是想换渠道）；`readChannels` 的语义会变脏。
它与 `model-prefs.json`（契约 H，管工作流节点的 `ai.agent`）**也不是一件事**，
故意分开存 —— 合并会让「改生成默认」把工作流的模型偏好一起改掉。

## 三、存储目录

`src/schedule/storage-config.ts`。存 `data/ecom-workbench/storage.json`。

### `GET /api/ecom-workbench/storage` — `src/index.ts:1842`

```jsonc
{ "ok": true,
  "config": { "artifacts": "D:\\ecom\\artifacts" },     // 只有改过的键
  "dirs": [ { "key": "artifacts", "label": "产物",
              "path": "D:\\ecom\\artifacts", "isDefault": false,
              "defaultPath": "…\\data\\ecom-workbench\\artifacts" } ] }
```

五个键（`storage-config.ts:33` `STORAGE_KEYS`）：`canvases` / `artifacts` / `materials` /
`genLogs` / `promptCache`。`label` 是中文名（画布 / 产物 / 素材 / 生成记录 / 提示词缓存）。

### `PUT /api/ecom-workbench/storage` — `src/index.ts:1848`

```jsonc
{ "dirs": { "artifacts": "D:\\ecom\\artifacts" } }   // 也接受不带 dirs 直接平铺
```

三条规矩：

1. **空串 = 恢复默认**（`""` 会把那一格删掉，回到数据根下那个目录）。
2. **改前逐格验可写**：目录不存在就建，建完**真写一个临时文件再删**（`storage-config.ts:109-154` `checkDir`）。
   为什么必须真写：`access(dir, W_OK)` 在 Windows 上不可靠（只看只读属性，不看 ACL / 磁盘满 / 网络盘断）。
3. **任一格不过就整份不存**，回 `400` + `{ key }` 指是哪一格：
   ```jsonc
   { "ok": false, "key": "artifacts",
     "error": "「产物」：要写完整路径（形如 D:\\ecom\\artifacts），不要用相对路径：rel/x" }
   ```

**为什么整份不存，不「能存的先存」**：只存一半会让产物**散在两个地方** ——
用户以为全改了，实际有一格还是老路径，一半进新盘一半进旧盘。那比全不存难查得多。

**相对路径一律拒绝**：进程的工作目录会随启动方式变（桌面端与兜底 CLI 不同），
相对路径今天指这里、明天指那里，产物就散了。

### 生效方式：热生效 + **重启时再套一次**

目录是每次调用现算的（`artifacts.ts` 的 `dirOf`），存完立刻套用
（`storage-config.ts` `saveStorageConfig` 结束时 `setDirOverrides(next)`）。

⚠️ **但那份覆盖表在内存里，重启就空了** —— 所以 `apply(ctx)`（`src/index.ts:1304`）
启动时必须调一次 `applyStorageConfig()` 把盘上的 `storage.json` 套回来。
这个函数一度**写好了却零调用方**（只在注释里被提到），后果是
「用户改了产物目录 → 热生效 → 重启 → 全部回默认，而 `storage.json` 明明还在」。
当时的测试是绿的，因为它自己手动调了那个函数 —— 测试替生产补了最后一公里。

那条套用是**后台跑**的（`apply` 是同步签名，不能 `await`）。文件坏了（JSON 写坏、
权限不对）会通过 `ctx.logger.warn` 报一句：「从没配过」安静用默认，「配过但读不出来」必须说出来。

**不改数据根**：`channels.json` / `model-defaults.json` 这些配置留在数据根 ——
跟着内容跑会让「换盘」变成「换配置」。

⚠️ **不搬旧文件**。改路径不改数据位置：新产物进新目录，老产物还在老目录。
假装「自动搬家」比不搬更糟（搬一半失败会留下两份互不相认的数据）。

## 四、提示词源

`src/schedule/prompt-source-config.ts`。存 `data/ecom-workbench/prompt-sources.json`，
**只存用户改过的部分**（内置源的 `name` / `url` 会随上游更新，存快照等于把它们冻住）。

| 方法 | 路径 | 用途 | 出处 |
|---|---|---|---|
| GET | `/prompt-sources/config` | 列全部源（内置 + 自定义） | `src/index.ts:1871` |
| POST | `/prompt-sources/config` | 加一个自定义源 | `src/index.ts:1876` |
| PUT | `/prompt-sources/config/:id` | 改 `enabled` / `name` / `url` | `src/index.ts:1887` |
| DELETE | `/prompt-sources/config/:id` | 删自定义源（**内置的删不掉**） | `src/index.ts:1899` |
| POST | `/prompt-sources/config/:id/probe` | 测连通 | `src/index.ts:1911` |

源的一条（`prompt-source-config.ts:42` `PromptSourceConfig`）：

```jsonc
{ "id": "awesome-gpt-image", "name": "Awesome GPT Image",
  "url": "https://raw.githubusercontent.com/…/awesome-gpt-image.json",
  "homepage": "https://github.com/ZeroLu/awesome-gpt-image",
  "license": "MIT",
  "enabled": true,
  "builtin": true }
```

### ⚠️ 内置五个：删不掉，只能停用 — `409` + `builtin:true`

```jsonc
// DELETE /prompt-sources/config/awesome-gpt-image → HTTP 409
{ "ok": false, "builtin": true,
  "error": "「awesome-gpt-image」是内置源，删不掉（内置副本跟代码一起打包，删了下次升级还会回来）。不想用它就停用：把 enabled 改成 false。" }
```

界面该把 `409` 显示成「只能停用」，并给一个**停用**按钮（`PUT { enabled: false }`），
而不是把删除按钮做成灰的却不说原因。**停用后它仍在配置清单里**（`enabled: false`）——
停用与删除是两件事。

⚠️ **但停用会真的把它从提示词库里摘掉**。配置页与提示词库是两个消费方：

| 消费方 | 停用之后 |
|---|---|
| `GET /prompt-sources/config`（配置页） | **仍在**，`enabled: false`（要能再启用回来） |
| `GET /prompt-sources`（提示词库） | **不在了** |
| `GET /prompt-sources/:id` | `404` + `disabled: true`，话是「已停用」 |
| `POST /prompt-sources/:id/refresh` | 拒绝：「这个源已停用」 |

这条一度是**假的**：`prompt-cache.ts` 的 `listSources` 只 `for` 一遍内置常量，
既不看 `enabled`，也看不到用户自己加的源 —— 配置做完了、消费方没读。
2026-10-26 改成遍历 `listConfiguredSources()` 之后才真生效。

自定义源的 `enabled` 没有单独字段（**存在就是启用**，删掉就是不启用）。要临时停用就删掉
再加 —— 与内置的「停用但不删」不同：自定义的是用户自己加的，删了不会自己回来。

### 全部停用：空态要带一句话

`GET /prompt-sources` 在清单为空时多回一个 `emptyNote`：

```jsonc
{ "ok": true, "sources": [], "items": [],
  "emptyNote": "提示词源全被停用了。到「工作台设置 → 提示词源」里启用至少一个，或加一个自己的源。" }
```

界面不能只画一个空列表 —— 「没配」「停光了」「加载失败」在页面上必须长得不一样。

### 测连通

```jsonc
// HTTP 200，看 ok
{ "ok": true, "count": 53, "status": 200, "url": "https://…/awesome-gpt-image.json" }
{ "ok": false, "error": "连不上：ENOTFOUND。检查地址写对没有、网络通不通。", "url": "…" }
```

四种失败各有各的话（`prompt-source-config.ts:306-359` `probeSource`）：

| 情况 | 话 |
|---|---|
| 连不上 | 「连不上：…检查地址写对没有、网络通不通」 |
| 404 | 「这个地址没有东西（404）—— 检查地址末尾有没有落文件、仓库改名没有」 |
| 回的不是 JSON | 「这个源多半是一个网页，不是提示词 JSON」 |
| 是 JSON 但不是数组 | 「这个源要求顶层是条目数组，实际是一个对象」 |

**测连通只数条目、不落盘**（`probeSource` 函数体里没有任何 `writeFile` / `saveSourcesFile` 调用，只 `listConfiguredSources` 读一次）：它的目标是「地址对不对、结构对不对」，不是刷新数据。
真刷新走 `/prompt-sources/:id/refresh`。

### 探针的 fetch 注入点：函数有，路由没有

`probeSource`（`prompt-source-config.ts:316`）的签名是
`probeSource(id: string, doFetch?: typeof fetch)`，`:322` 是 `const impl = doFetch ?? fetch` ——
函数本身收注入参数。

但路由那条调用没传：`src/index.ts:1948` 写的是 `await probeSource(id)`，
于是它退回全局 `fetch`，测试里那条「测连通」会真的去拉 GitHub
（网络通 1424ms，网络不通 32073ms）。

缺口在路由层没有注入点，不在函数层没有参数。这两句差的不是措辞，是「该改哪一层」：
函数签名早就对，改它等于白改。当前测试侧用 `withStubbedFetch()` 包住全局 `fetch` 绕开
（`tests/config-routes.mjs:113`），要根治得让路由那条能拿到一个可注入的 `fetch`。

⚠️ 这条写得这么细，是因为它已经犯过一次：曾有一句注释断言探针函数不收注入参数，
而定义就在旁边的行里。指出一个能力不存在，和指出一件事不会发生，是同一种错 ——
两者都该能指到具体行号。

### 自定义源：**能列出、能测连通、能拉、能读**

`listSources` 会列出用户加的源（`from: 'custom'`、`builtin: false`），单条读取也回。

**刷新那条路支持自定义源**：地址取配置里的那一份（不再硬取内置常量），
拉到的结果写进 `prompt-cache/<id>.json`，之后 `readSource` / `listSources` 都读得到，
`from` 从 `'custom'` 变成 `'cache'`。这条已用一个临时自定义源实测过三步（造源 → 拉 → 读），
不是读代码推的：

```
① addSource           → true，配置清单里出现 {name:'探针源', url:'https://example.invalid/prompts.json', builtin:false, enabled:true}
② refreshSource(替身)  → {ok:true, count:2, note:'已从上游拉到 2 条并写进缓存'}
                         打的地址就是配置里那个（不是任何内置常量）
③ readSource          → from=cache，2 条，第一条正文读得出来
   listSources        → 有它 {count:2, from:'cache', builtin:false}
   缓存文件           → prompt-cache/tmp-custom.json 存在
```

**还没拉过的自定义源**（没有缓存）走的是另一支：`from: 'custom'`、`count: 0`，`note` 是
「这个源是自定义的，还没有内容（**刷新一次就有**）」。这是**有意的**——
自定义源没有内置副本可以回落，静默回一个空清单会让人以为这个源坏了。
括号里必须给出下一步动作：只写「还没有内容」会让人以为它永远没有内容。

⚠️ 这句话的括号**曾经写错**（写的是「刷新只适用于内置那几份」的意思，而事实相反）。
那半句让两个人误判：lead 据此让界面别放刷新按钮，于是那个按钮真的漏做了。
**代码里一句过期的解释，比文档写错更能把人带偏** —— 改这类状态时，先搜一遍话术。

**界面入口：已有**（`src/client/workbench/PromptSourcesSettings.tsx:288` 调
`POST /prompt-sources/:id/refresh`，内置与自定义同一个按钮；`:18` 的注释也写明两者都支持）。

## 五、渠道的模型：四种形状都收

`src/schedule/channels.ts:192-244`。`POST /channels` 的 `models` 字段接受：

```jsonc
// ① 字符串数组（界面那条「一行一个」的文本格式）
["gpt-image-1|GPT Image|image,video", "plain-model"]

// ② 对象数组（拉了模型后勾选出来的）
[{ "id": "gpt-image-1", "label": "GPT Image", "caps": ["image", "video"] }]

// ③ 两种混在一个数组里（界面切换过程中会出现）
["str-a|甲|image", { "id": "obj-b", "label": "乙", "caps": ["video"] }]

// ④ 整段多行文本（调用方直接发草稿里那段字）
"txt-1|一号|image\ntxt-2|二号|video"
```

字符串那条的格式：`id|显示名|能力,能力`。只有 `id` 时 `label` 退回 `id`、`caps` 为空。
**不认识的能力值会被丢掉**（`CAPS` 是闭集：`image` / `video` / `text` / `audio`）。

**为什么四种都收**：老渠道存在磁盘上了（全是对象），强制某种形状等于要写一次迁移 ——
这次改动不该让任何已存渠道读不出来。
