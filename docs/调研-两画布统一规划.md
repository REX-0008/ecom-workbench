## 0. 这份文档回答什么

执行工作流画布（下称**执行画布**）与内容画布（下称**内容画布**）现在各有一套「怎么看这块画布」的控件。两份控件功能重叠、位置各异、叫法不同。用户要的是：**哪几项该像、哪几项不该像**，以及**理由**。

罗列两边各有什么不算答案。所以下面每一项都给「归哪一类 + 为什么 + 代价」。

**在核之前先说清一件事**：两个画布从根上不是同一种东西 —— 执行画布的节点是**一个执行步骤**（有入出口、连边表示数据流、能跑），内容画布的节点是**一块素材**（图片 / 文本 / 视频 / 音频 / 配置，摆位置有意义、跑不起来）。所以下面凡涉及「节点本体怎么显示」的，一律判「该保持差异」，不拉进来统一。

## 2. 三处判断的理由

### 2.1 「设置项内容」的重合其实只有一组

把两边设置项并排看，名字像的有四对，但**只有一对真是同一件事**：

| 名字像的一对 | 真是同一件事吗 |
|---|---|
| 执行画布「背景透明」（`SettingsDrawer.tsx:198-222`） / 内容画布「线格深浅」（`CanvasSettingsPanel.tsx:120-137`） | **不是**。前者调的是画布底**那一层的不透明度**（让画布透出外壳背景），后者调的是**线本身的颜色浓度**。一个是「底透不透」，一个是「线深不深」 |
| 执行画布「自动排版间距」10-400（`SettingsDrawer.tsx:228-254`） / 内容画布「新节点落位间距」0-120（`CanvasSettingsPanel.tsx:169-184`） | **不是**。前者是 **ELK 自动布局**时节点之间留多少空（`runLayout` 用），后者是**手动加一个节点时**它落在离上一个多远（`ContentCanvas.tsx:588` 的 `nodes.length * prefs.dropGap`）。名字像而已 |
| 执行画布「展开高度」 / 内容画布「面板宽度」 | **不是**。前者是节点内参数区的高度，后者是节点设置浮层的宽度档位 |
| 执行画布「输出高度」 / 内容画布（无） | 执行画布独有 |

**重合的只有「背景 / 线格」那一组**（表第 4 项）。其余全部是各自业务带出来的，硬凑统一只会多出一批「改了不生效」的开关 —— 这一轮已经修过好几次这一类（票 34 的节点尺寸、票 35 的快捷键重复、票 01 的线格深浅存了没人读）。

所以第 3 项判「需用户裁」而不是「该统一」：真正要裁的不是「留哪些项」，而是「要不要把两个设置面板合成一个」。见 §3 选项 A/B。

### 2.2 为什么第 9 项这次该反过来（执行画布 → 内容画布）

历史上这一项的方向一直是反的：票 35 之前，执行画布的抽屉里有快捷键表，内容画布**也有**，两边一致。票 35 时用户说「快捷键既然有了独立的展示按钮，那么就不要再设置中放了，重复了没必要」（`CanvasSettingsPanel.tsx:52-58` 原话记录）。

于是内容画布变成「只有独立入口」，执行画布还留着抽屉里那张表 —— 两边**从一致变成不一致**，这是票 35 的副产物，不是有意设计。

现在要定的是：往哪边收。

- 执行画布的抽屉里那张表（`SettingsDrawer.tsx:35-70`，三组 19 条），和它的键盘处理是**分开维护**的两份（注释自己写着「改一处要同步另一处」）
- 内容画布的清单是函数生成的（`shortcutHelp()`，`CanvasZoomControls.tsx:60-75`），步数从同一份 state 来

**判给内容画布这一侧**，三个理由：
1. 用户票 35 的原话就是「独立入口够了，设置里别重复」—— 那条判断对两边同样成立
2. 独立入口是**随时可查**的，藏在设置里要先开抽屉再翻到最底下
3. 执行画布那张表是手写的，删掉它顺手消掉一处「两份要同步」的隐患

### 2.3 为什么第 10 项的位置不该统一

两个画布的骨架不同：

- 执行画布是「**顶部全局工具条 + 画布**」，工具条里同时有运行 / 停止 / 保存 / 恢复 / 撤销 / 锁定 / 设置 / 图例 —— 撤销在这一排里符合「全局动作」的分组
- 内容画布是「**画布内工具条 + 画布**」（`CanvasToolbar.tsx` 是 `contentCanvasBar`，浮在画布上），它没有顶部全局条

把执行画布的撤销搬进画布，与「顶部条属于全局动作」这条既定分组相冲突；把内容画布的撤销搬到顶上，则要让它在没有全局条的前提下新造一条。**两边都合理，所以位置不动。**

但**步数的可见性**该统一：执行画布的步数**只写在 `title` 里**（`WorkflowCanvas.tsx:4283`，鼠标悬停才看得见），内容画布是右下角常显一条（`ContentCanvas.tsx:2420-2423`）。措辞两边本来就一样（都是 0 步说「没有可撤销的操作」，`ContentCanvas.tsx:251` 与 `WorkflowCanvas.tsx:4283` 逐字相同），差的是**看不看得见**。执行画布补一条常显提示就行 —— 这是「同一条信息怎么呈现」，不是骨架问题。

## 3. 三处需要用户裁的选项

### 选项 A／B：两个设置面板要不要合成一个（对应表第 3 项）

**A. 只统一形态，各自保留自己的项（推荐）**

- 两边都用同一种面板形状（都改成浮窗，或都改成抽屉），项各留各的
- 代价：3 个文件，不触设置项本身
- 好处：不冒「合并之后某项放哪」的争论；各自业务的项不用硬塞
- 风险：低

**B. 合成一个面板，分「通用」与「本画布」两段**

- 通用段：背景 / 小地图 / 缩放相关（两边都有意义）
- 本画布段：执行画布放节点尺寸、自动排版、输出高度；内容画布放对齐吸附、落位间距、面板宽度
- 代价：3 个文件 + 一次完整视觉走查；`CanvasSettingsPanel` 与 `SettingsDrawer` 要抽成一份公共组件
- 好处：用户不用记「这个设置在哪个画布的面板里」
- 风险：中。两份面板的 DOM 钩子（`data-ewb-settings-*`、`data-ewb-canvas-settings`）被 3 个测试钉着，抽象时容易漏

**推荐 A。** 理由：用户这次要的是「相对统一」，A 已经满足；B 会引出「某一项到底算不算通用」的长期争论，而这类争论每来一次就要动一次面板。

### 选项 C：操作模式切换要不要双向统一（对应表第 11 项）

**C1. 两边都加常驻按钮（往内容画布走）**

- 执行画布补一个「框选 / 平移」常驻按钮
- 代价：1 个文件（`WorkflowCanvas.tsx`）+ 要给 `panOnDrag` 接一个 state（现在它是常驻 `true`）
- 好处：新用户不用记 Ctrl；与内容画布一致
- 风险：中。执行画布的 `panOnDrag` 常驻是**既定设计**（`CanvasToolbar.tsx:24-26` 写着「本组件不接管它」），改成可控 state 要重验 Ctrl 临时框选那条路

**C2. 内容画布改成「靠 Ctrl」，不加常驻按钮（往执行画布走）**

- 代价：1 个文件
- 好处：少一颗按钮
- 风险：内容画布的主要动作是**摆素材**，拖动频率远高于执行画布，去掉常驻按钮会让「想框选时一直按着 Ctrl」变成常态

**倾向 C1。** 但这一项涉及手感，属于「两边都有理」，交用户裁。

## 4. 明确不统一的：节点显示

用户原话：「不要把节点显示之类两个板块一开始就完全独立的内容放进来」。

具体是哪几项、为什么：

| 项 | 执行画布 | 内容画布 | 为什么不能统一 |
|---|---|---|---|
| 节点本体 | 执行步骤：标题 + 状态灯 + 入出口 + 展开后的参数区（`WorkflowNode.tsx`） | 素材块：按类型的尺寸表（`content-nodes.tsx`）、图片预览、文本正文 | 一个是「这一步做什么」，一个是「这块东西长什么样」。共同点只有「都在画布上是个方块」 |
| 连线 | 表示数据流，有端口与合法性别（`branch.ts` 的 `__handle` / `__error`） | **没有连线**（内容画布不连东西） | 内容画布不存在这个对象 |
| 分组框 / 循环框 | 编组（纯视觉名单）+ 循环容器（`parentId` 归属，影响调度） | 只有编组，且不参与任何执行 | 循环框在执行画布上是**执行语义**，在内容画布上无从谈起 |
| 节点上的运行信息 | 状态、日志、汇报、模型痕迹（`WorkflowNode.tsx` 的汇报块） | 无 | 内容画布没有「运行」这件事 |

一句话：**这两样东西共用的只有「画布」这个容器，容器怎么用该像，容器里装的东西不该像。**

### 建议一直不做

- 表第 12 项 · 图例 —— 内容画布没有连线，造一个图例等于给一个不存在的概念配说明
- 节点显示那四项（§4）—— 用户已明确排除

## 6. 一句话总结

**该像的只有「怎么看这块画布」这一层**（缩放、小地图、复位、设置面板壳、快捷键入口、锁定、背景），大约 8 项；**不该像的是「画布上装什么」**（节点、连线、分组、运行信息），4 项。

最划算的一步是第 8 项（执行画布补缩放百分比）：一个文件、纯增量、当天能验。
