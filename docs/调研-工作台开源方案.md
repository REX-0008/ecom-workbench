# 电商FDE简历与面试规划 · 工作台开源方案调研（2026-10-05）

> 状态：**调研完成**——候选清单已出，待用户逐个评估后选路线。
> 筛选第一标准：**结构简单、能跑起来、容易改**（不是功能强大）。数据抓取日 2026-10-05。

## 一、结论先行

| 首选 | 一句话理由 |
| --- | --- |
| **① 本机 workbench 插件继续做底子** | 它已经是你想要的那个形态（BI＋监控＋自动化按钮），缺的只是"流程可视化"这一块，补一块比重起一套便宜得多。 |
| **② dock（dsh 插件基座，9★）** | 唯一一个把"工作台外壳 + 面板注册表"做成了公开接口的 dsh 插件，插件式挂面板比改源码简单，适合当外壳升级件。 |
| **③ n8n 只当"流程可视化的样板"参考，不要当底子** | 它的条件分支画法直观、可直接抄设计；但它是执行引擎（fair-code、要自托管整套），你要的是**展示**流程，不是让流程跑起来。 |

**关键判断（推断）**：你的核心诉求「什么条件进入什么样的下一步的可视化」，本质是**一张带状态的流程图**，不是一套工作流引擎。实现成本最低的路线是在现有 `panel.html` 里加一张流程图（React Flow 或 Mermaid 渲染），节点颜色由按钮/巡查结果驱动——**不需要引入 n8n / Dify 这类运行时**。

## 二、候选清单

### 1. dock（DSH 工作台基座）
- **是什么**：给 dsh Web 加 VSCode 式外壳（活动栏/侧边栏/编辑器区/面板/状态栏），并开放 `ctx.workbench` 注册表，让功能插件挂面板、视图、命令。
- **地址/星数**：https://github.com/AKS1st/dock ｜ ⭐9 ｜ npm `dock-base`
- **技术栈**：TypeScript + React 18，客户端平台 Web。
- **改造难度（0 代码＋AI）**：**中**。用它是"装 + 注册"，不用改它源码；但每加一个面板仍要写一段 TS/React 注册代码，AI 能写、你要会验收。
- **能提供**：工作台外壳、多标签编辑器区、停靠/浮窗、布局持久化、命令系统、设置窗口。
- **缺点**：**只有外壳，没有 BI、没有流程、没有业务面板**；星数低（9），生态小，长期维护不确定。

### 2. DSH-Creator（jacky-creator，内容生产与运营工作台）
- **是什么**：面向内容创作者的 dsh 本地工作台——灵感→选题→脚本→视频/字幕/封面→发布→复盘，每条内容是一个普通文件夹。
- **地址/星数**：https://github.com/Jackywxsz/DSH-Creator ｜ ⭐108 ｜ npm `jacky-creator`
- **技术栈**：dsh 插件（npm 成品包，一键装），内容落本地目录。
- **改造难度**：**低**（装完即用）。改它要读 TS 源码，属中等。
- **能提供**：内容管理、运营看板（今日推进/档期/内容管线/阶段目标）、灵感库、发布后复盘——**正是你"内容生产"核心模块的现成骨架**。
- **缺点**：绑定 DSH Desktop 2.0.2；流程可视化是"管线阶段"，**没有条件分支图**。

### 3. dsh-shop-assistant（电商店主工具集）
- **是什么**：面向店主/客服主管的 dsh 插件——批量差评回复（按你自己的退货政策）、竞品页转标题卖点、上架前利润与六维评分（固定公式，不是瞎猜）。
- **地址/星数**：https://github.com/pengzhou267-ai/dsh-shop-assistant ｜ ⭐0 ｜ npm `dsh-shop-assistant`
- **技术栈**：dsh 插件 + 中文 Markdown skills + CSV。
- **改造难度**：**低**。它的"可替换售后政策知识库"和 skills 都是 Markdown，**非程序员能直接改文字**。
- **能提供**：售后回复流水线、上架决策打分——对应你清单里的"客服：售后处理"。
- **缺点**：**没有界面**（纯对话+表格），没有流程可视化；星数 0，等于无社区验证。

### 4. Metabase（BI 看板）
- **是什么**：开箱即用的开源 BI，非技术人员点选就能出看板。
- **地址/星数**：https://github.com/metabase/metabase ｜ ⭐49,545 ｜ 技术栈 Clojure + React
- **改造难度**：**用起来低，改起来高**。装 + 点选做看板很容易；改源码（Clojure）对 0 代码＋AI 基本不现实。
- **能提供**：BI 面板（你已用 Superset 达成同类能力）。
- **缺点**：**改不动源码**。结论：把它当"外部看板"，用 iframe/webview 嵌进你的工作台（你现有 workbench 已经是这个模式），不要试图改它。

### 5. DataEase（国产开源 BI）
- **是什么**：人人可用的开源 BI，中文界面，Tableau 替代品。
- **地址/星数**：https://github.com/dataease/dataease ｜ ⭐24,587 ｜ 技术栈 Java + Vue
- **改造难度**：**用起来低，改起来高**（Java/Vue 双端）。
- **能提供**：中文 BI 面板、多数据源。
- **缺点**：体积重（Java 栈），改源码成本高。**仅在"想要中文 BI 且 Superset 不好用时"作为备选**。

### 6. n8n（工作流可视化，参考样板）
- **是什么**：可视化工作流自动化平台，节点连线 + 条件分支，自带 AI 能力与 400+ 集成。
- **地址/星数**：https://github.com/n8n-io/n8n ｜ ⭐206,721 ｜ 技术栈 TypeScript
- **改造难度**：**中**。自托管容易；多数需求靠拖节点配置完成，**不必改源码**。但它自身是个重系统。
- **能提供**：条件分支的**画法参考**（条件→下一步的连线语义），以及真要做"自动化执行"时的引擎。
- **缺点**：官方自述为 **fair-code**（非 OSI 开源，商用限制，未逐条核实）；引入后你多了一套要维护的系统。**当样板，不当底子。**

### 7. React Flow（xyflow）＋ bpmn-js（流程可视化前端库）
- **是什么**：React Flow 是画节点连线图的前端库；bpmn-js 是 BPMN 2.0 流程建模/渲染工具包。
- **地址/星数**：https://github.com/xyflow/xyflow ⭐38,584 ｜ https://github.com/bpmn-io/bpmn-js ⭐9,680
- **技术栈**：TypeScript / JavaScript，纯前端库。
- **改造难度**：**中**。它们是"零件"不是"应用"，要自己写一层页面；但 AI 生成 React Flow 页面的成熟度很高，是**本清单里最适合"用 AI 写一段就能看到效果"的**。
- **能提供**：**「什么条件进入什么样的下一步」的直接实现材料**——节点=环节、边=条件、节点颜色=当前状态。
- **缺点**：不提供数据、不提供执行、不提供持久化，全要自己接。

### 8. ComfyUI（＋ dsh-comfyui 插件）
- **是什么**：节点式 AI 出图/出视频引擎，工作流本身就是可视化流程图；dsh-comfyui（⭐97）让 agent 直接驱动它。
- **地址/星数**：https://github.com/comfyanonymous/ComfyUI ⭐136,184 ｜ 插件 https://github.com/fandc520/dsh-comfyui ⭐97
- **技术栈**：Python（引擎）＋ dsh 插件（桥接）。
- **改造难度**：**低到中**。装完即用；改节点/工作流是拖拽 + 配置，改引擎才要 Python。
- **能提供**：**内容生产的实际产能**（批量出图/出视频），且天然带"节点图"这种流程可视化形态。
- **缺点**：它是"生产工具"，不是"业务工作台"；业务条件（售后、选品）它管不了。

## 三、本机 workbench 插件的评估

**结论：能当底子，而且是最省力的底子——它已经覆盖了你要的四件中的三件。**

已读源码：`my-dsh-plugins/workbench/`（README、`src/workbench-node.ts` 580 行、`src/client/workbench/WorkbenchColumn.tsx` 382 行、`panel.html` 479 行）。

| 你要的形态 | 它现在有没有 | 证据 |
| --- | --- | --- |
| BI 界面 | **有** | 右列左半 = Superset 看板，经 dshDesktop webview 承载（`workbench-config.ts` 的 `SUPERSET_URL`） |
| 监控界面 | **有** | 右列右半 = 自家 `panel.html`，由 `/api/workbench/panel-url` 提供 |
| 自动化按钮 | **有** | `buttons.json` 7 个按钮（启动BI/清洗入库/下载抖音/下载天猫/一键更新/全部下载/手动巡查），`POST /api/workbench/run` 起 bat 并回传日志 |
| 流程可视化（条件→下一步） | **没有** | `panel.html` 只有卡片/行/状态点样式，全文无 flow/graph/canvas 相关代码 |

**它的优势**（相对任何外部候选）：
- `panel.html` 是**纯 HTML+CSS+JS、479 行、零框架**——加一张流程图是往里塞一段脚本，不是重构。
- 数据落盘、调度器、按钮执行、错误分类（ok/fail/captcha/curfew/login）、块级补偿缓存**都已实现**（`workbench-node.ts`），你只需在展示层加流程。
- 已经接好"面板注册"这条路（`shell.overlay`），不用学 dock 的新注册表。

**它的短板**：只服务你一个人、无测试、无文档给外人看；星数 0（私有）；流程可视化要自己从零加。

**建议动作（推断）**：先在这套插件里做**一张售后处理流程图**（节点=环节、边=条件、颜色=状态）作为验证；跑通了再决定要不要换 dock 当外壳。

## 五、智能客服可行性（简略）

**结论：过于复杂，不建议自建；最多用"知识库 + 现成插件"做半自动。**

- **Chatwoot**（⭐37,555，Ruby）：客服工单台，功能全但 Ruby 栈、重，0 代码改不动 ｜ https://github.com/chatwoot/chatwoot
- **Rasa**（⭐21,344，Python）：自训 NLU + 对话管理，**要标注语料、要训练**，与"AI 辅助改代码"能力不匹配。
- **FastGPT**（⭐29,781）／ **Dify**（⭐157,891）：RAG 知识库问答，部署一套即可用，但都是独立重系统，**属于"再维护一套平台"**。
- **dsh-wechat-channel**（⭐1）：微信公众号消息触发 dsh 会话并回推，是**最贴近你现有栈的轻量接法** ｜ https://github.com/Shr-CS/dsh-wechat-channel
- **建议**：客服先做"**售后处理流程图 + 可替换政策知识库**"（dsh-shop-assistant 已有），人工在环；不引入独立客服平台。
