## 0. 结论优先：最值得采用的 6 条

1. **失败处理要做三态，不是两态。** n8n 的 `onError` 是 `stopWorkflow | continueRegularOutput | continueErrorOutput`（【已验证】n8n `packages/workflow/src/interfaces.ts:1738`），Dify 是 `none | fail-branch | default-value`（【已验证】Dify `web/.../nodes/_base/components/error-handle/types.ts:3-7`）。两者都多出「**失败专用出边**」这一态：失败结果走独立分支，不污染正常下游。我们现在的 stop/continue 缺的就是这条。
2. **幂等 = 原子认领 + 版本号，判据是「影响行数」。** TradeMind 收尾时执行 `UPDATE ... WHERE id AND locked_by AND execution_id AND lock_version`，`RowsAffected == 0` 即判定租约丢失并报错（【已验证】`lease.go:58-77`）。工作流层的对应物是 Temporal 的 `WorkflowIdReusePolicy` / `WorkflowIdConflictPolicy`——用运行标识决定重复启动是**拒绝**、**复用**还是**终止旧的**（【已验证】`temporal/api/enums/v1/workflow.proto:16-44`）。
3. **运行记录要「每次尝试一条」，不是「每节点一条」。** Dify 的 `NodeTracing` 带 `retry_index`/`retryDetail`、`iteration_id`/`loop_id`/`parallel_id` 与 `predecessor_node_id`（【已验证】Dify `web/types/workflow.ts:43-113`）。长流程出问题时，唯一能还原现场的就是「第几轮、哪个循环体、哪个并行分支、前驱是谁」。
4. **超时要分层，并且要能区分「超时」与「被取消」。** Temporal 分 `startToCloseTimeout`（单次尝试）、`scheduleToCloseTimeout`（含重试的总时长）、`scheduleToStartTimeout`（排队，永远不可重试）（【已验证】`activity-options.ts:103-142`）；dsh-node-flow 用 `makeTimeoutSignal().isTimeout()` 把超时中止与调用方中止分开，好让报错文案能说「运行超时」而不是「被取消」（【已验证】`dsh-node-flow/lib/index.js:218-237, 743`）。
5. **数据传递用「引用路径」，不要用「拷贝值」。** Dify 的下游引用是字符串数组选择器（`from_variable_selector?: string[]`，【已验证】`web/types/workflow.ts:317`）；n8n 更进一步用 `pairedItem` 记录「这条输出来自上游第几项的第几个输入」（【已验证】`interfaces.ts:1853-1876` 与 `IPairedItemData`）。这是支持一对多、可追溯的唯一办法。
6. **参数与配置的校验必须在「任何东西开始跑之前」响亮失败。** dsh 的 workflow seam：`meta` 先按 schema 校验，不过就直接拒绝，脚本正文一行都不执行（【已验证】`refs/deepseek-harness@62962ee4/docs/subsystems/workflow.md`）。

## 1. 工作流数据模型

### 1.1 节点与边的标准字段

| 引擎 | 节点字段（核心） | 边 / 连接 |
|---|---|---|
| n8n | `id` `name` `type` `typeVersion` `position` `parameters` `credentials` `disabled` `notes` `executeOnce` `alwaysOutputData` + 失败三态与重试四项（【已验证】`interfaces.ts:1739-1762`） | 连接表按**节点名**（不是 id）→ 输入口名 → 输出数组索引三层嵌套（【已验证】`IConnections` `interfaces.ts:513-521`） |
| Dify | 通用字段 `error_strategy` `retry_config` `default_value`（【已验证】`workflow/types.ts:118-120`）；节点 `type` 取 41 个枚举之一（【已验证】取自其 web 目录树，含 `if-else` `iteration` `loop` `list-operator` `variable-assigner` `question-classifier` `human-input`） | 沿 React Flow 的 `source`/`target` + handle；前端 `Node`/`Edge` 直接就是 React Flow 类型（【已验证】`workflow/types.ts:2,150`） |
| dsh-node-flow | `id` `type:"workflow"` `position` `data{kind,label,...}` `style`；9 种 kind 各自字段（【已验证】本仓 `skills/dsh-node-flow-skill/references/node-types.md`） | 显式 `sourceHandle`/`targetHandle`，句柄 id 是契约（`if` → `true`/`false`；`loop`/`while` → `iterate`/`done` + 目标 `in`/`back`）（【已验证】`references/workflow-schema.md`） |
| GHA | job 级：`needs` `if` `outputs` `env` `concurrency` `continue-on-error` `timeout-minutes`；matrix：`strategy.fail-fast` `strategy.max-parallel`（【已验证】workflow-syntax.md 对应小节标题） | 依赖是 job 名列表（`needs`），非图结构 |

**建议（【推断】）**：沿用 dsh-node-flow 的「`data.kind` + 显式 handle id」骨架——它已在本机跑通，且 handle 是唯一需要严格校验的部分。把 n8n 的失败三态与重试四项搬进 `data`，把 Dify 的 `default_value`（失败时用默认值继续）作为第三态的实现方式。

### 1.2 变量与数据传递

- **引用语法**：Dify 用「路径数组」而非模板串（`from_variable_selector: string[]`，【已验证】）；dsh-node-flow 用单一 `result` 字符串变量 + 节点内表达式（`JSON.parse(result)` / `Number(result)`），跨节点**没有**命名变量（【已验证】node-types.md）。
- **n8n 的表达能力**：接口层暴露 `evaluateExpression(expression, itemIndex)`——表达式**按数据项逐个求值**，所以参数可以引用「当前这一项」（【已验证】`interfaces.ts:1312`）。
- **【推断】取舍**：单 `result` 字符串最省事但很快撑不住（我们已看到要手写 `JSON.parse`）；建议改成「节点输出是**命名端口的 JSON 对象**，下游用 `节点id.端口名` 路径引用」，同时保留「无引用时默认取上游唯一输出」的糖。

### 1.3 条件分支与循环

- **分支**：dsh-node-flow 的 `if` → `true`/`false`、`switch` → 每个 case 值 + `default`（【已验证】workflow-schema.md）。这是最清晰的做法：**分支不是节点属性，而是出边上的 handle id**。
- **循环**：Dify 把循环拆成显式节点对——`loop-start`/`loop-end`、`iteration-start`/`iteration`，循环变量单独用 `variable-assigner`（【已验证】其 web 节点目录）。dsh-node-flow 用单节点 + `back` 回边，并在 `NodeTracing` 意义上等价的 `maxIters` 上设硬上限（默认 100）（【已验证】`index.js:560`）。
- **【推断】**：单节点 + 回边更好画、更难调试；拆成 start/end 两个节点更啰嗦但循环体边界明确、嵌套时不会串。**嵌套循环是我们必须现在就决定的**——dsh-node-flow 每次迭代会复制一份 `visited` 集合来隔离循环体（【已验证】`index.js:387-392`），这是单节点方案能支持嵌套的关键实现细节。

## 2. 执行语义

### 2.1 串行 / 并行

- **串行**：dsh-node-flow 是「沿边深度优先」，一个节点返回后**依次**对每条出边 `await`（【已验证】`fanOut` `index.js:414-419`）——即天然串行，多条出边也串着跑。
- **并行**：Dify 有独立的 `parallel_run_id` / `parallel_start_node_id` / `parent_parallel_id` 追踪并行分支（【已验证】`web/types/workflow.ts:62-77`）；GHA 用 matrix + `max-parallel`（【已验证】）；Airflow 用 `max_active_tis_per_dag` / `max_active_tis_per_dagrun` 限流（【已验证】`2.10.5 airflow/models/baseoperator.py:262-263`）。
- **【推断】**：我们当前「派发器 + 适配器」模型下，最省的并行表达是**节点声明 `fanOut: true` 时其出边并发、否则串行**，并给每个适配器设并发上限（对应 Airflow 的 pool 与 TradeMind 的按来源闸门）。

### 2.2 失败处理

| 维度 | 已验证做法 |
|---|---|
| 停止 vs 继续 | n8n `onError` 三态（`interfaces.ts:1738`）；Dify `none / fail-branch / default-value`（`error-handle/types.ts:3-7`）；dsh-node-flow `stop`（返回输入、不走下游）或 `continue`（把空串发给下游并记 error）（`index.js:456-511`） |
| 重试参数 | Temporal：`initialInterval` `backoffCoefficient` `maximumInterval`（默认 100×初始）`maximumAttempts` `nonRetryableErrorTypes`，并有一组显式校验（系数必须 >0、最大间隔不能小于初始间隔、次数必须是正整数）（【已验证】`retry-policy.ts:9-81`） |
| Airflow 等价物 | `retries` `retry_delay` `retry_exponential_backoff` `max_retry_delay` `execution_timeout` `trigger_rule` `depends_on_past` `wait_for_downstream` `on_failure_callback`（【已验证】`baseoperator.py:245-265`） |
| 致命错误要穿透 | dsh 的 `WorkflowError.fatal`：脚本里用错 API（参数错、未知选项、超出上限）一律 `fatal:true`，`parallel()/pipeline()` **重新抛出**而不是把该项映射成 `null`——「选项写错必须把脚本打死，不能伪装成一次普通的子任务失败」（【已验证】docs/subsystems/workflow.md）。**这条对派发器同样成立**：适配器配置错 ≠ 节点执行失败。 |

### 2.3 幂等与重试（避免重复副作用）

- **原子认领**（【已验证】TradeMind）：`tryClaimCollectTask` 把 pending/retrying 原子地改为 running 并附租约；收尾用带版本号的 `UPDATE`，影响行数为 0 就认输（`lease.go:29-77`）；续期由独立协程保活，过期由 reaper 回收（`lease.go:44-49, 80-84`）。
- **队列不丢**（【已验证】TradeMind）：`LPUSH` 入队 → `BRPOPLPUSH` 挪进 `...:processing` → 成功 `LREM` / 失败用 `TxPipelined` 同时 `LPUSH` 回主队列并 `LREM` 出处理队列（`queue.go:49-100`）。进程崩溃时消息留在 processing，可回收。
- **重复启动策略**（【已验证】Temporal）：`WorkflowIdReusePolicy`（重复 id 对**已结束**的流程：允许 / 仅允许失败的重跑 / 拒绝）+ `WorkflowIdConflictPolicy`（对**运行中**的：失败 / 复用现有 / 终止现有）（`workflow.proto:16-44`）。
- **【推断】**：我们的 run key 建议 = `工作流id + 触发源 + 业务主键`，配 conflict policy；节点的副作用型适配器（写平台、发消息）必须携带 run key 到下游做去重，而不是只靠重试次数。

### 2.4 取消

- dsh 的契约：`WorkflowRun.cancel(reason)` 取消自身与全部子任务；`result` **永不 reject**，取消时以 `stopReason:'cancelled'` 正常 resolve；`dispose()` 幂等，等待脚本与子进程静止（【已验证】docs/subsystems/workflow.md）。
- `stopReason` 是**封闭三值** `completed | cancelled | error`，非 completed 时带 `error`，消费方映射成「错误结果」而不是把半成品当成功（【已验证】同上）。
- 取消的强度是可选策略：Temporal 的 `ActivityCancellationType` = `ABANDON` / `TRY_CANCEL` / `WAIT_CANCELLATION_COMPLETED`（默认等待完成）（【已验证】`activity-options.ts:29-62`）。
- 实现手段：`AbortSignal`（dsh-node-flow 的每个 code/agent 节点都建自己的 `AbortController`，并保证 `finally` 里 `clear()` 掉定时器）（【已验证】`index.js:223-236, 430-455`）。
- **【推断】**：适配器接口应显式收 `signal`，并规定「**不响应 signal 的适配器**必须声明 `cancellable: false`」，否则界面会骗用户说已取消。

### 2.5 运行状态持久化与恢复

- dsh-node-flow 的做法最省：运行结束后把整条 run 记录（`{id,name,startedAt,nodeCount,status,failed,value,nodes[]}`，每节点 `{id,kind,status,ms,output,logs,error}`）落 JSON 文件，**只留最近 50 条**（【已验证】`index.js:610-621, 241-280`）。这是「有历史可查」但不是「可恢复」。
- 真正的可恢复：Airflow 把每次尝试落成 TaskInstance 行，`clear_task_instances` 重跑时把 `max_tries = try_number + retries`、`state = None`，并用 `RESTARTING` 区分「正在重启」（【已验证】`taskinstance.py:459-480`）；Dify 的 `human-input` 节点让流程可暂停后恢复（【已验证】其节点目录）。
- **【推断】**：内部小团队用，建议「**每节点一次尝试落一行**」+ 崩溃后**不自动续跑**，只允许「从失败节点重跑」——自动续跑要求每个适配器都幂等，代价远超收益。

## 3. 参数与依赖

- **参数校验**：dsh 的 workflow 引擎在运行前按 schema 校验 `meta`，不过则**在任何东西跑之前**拒绝（【已验证】docs/subsystems/workflow.md）。GHA 的 `on.workflow_call.inputs.<id>` 要求显式 `type`，并有 `required` / `default`（【已验证】workflow-syntax.md 对应小节）。n8n 有 `typeValidation: 'strict' | 'loose'` 的开关（【已验证】`interfaces.ts:2117`）。
- **【推断】**：用 JSON Schema 校验节点参数，且在**两个时刻**各校验一次——保存工作流时（给人看错误）与派发前（防手改 JSON）。
- **依赖检查（NPM / 外部程序 / 环境变量）**：**未获取**到「声明式依赖预检」的成熟一手范式。GHA 靠 `setup-*` action 隐式装（【已验证】workflow-syntax.md 有 `jobs.<job_id>.uses`），Temporal 靠 worker 注册，都不是运行前声明式校验。
- **可借的原则**（本机一手来源）：dsh 要求「**配置错误要响亮失败**：自包含的在加载期失败，否则在最晚可解析的点失败，绝不静默跳过缺失的引用」（【已验证】`refs/deepseek-harness@62962ee4/AGENTS.md` 约定段）。
- **【推断】**：节点声明 `requires: { npm: [], bins: [], env: [] }`，派发前解析；缺失时**不降级、不跳过**，直接把该节点标成不可运行并在画布上标红。

## 4. 可观测性

- **每个节点记什么**（【已验证】Dify `NodeTracing`，`web/types/workflow.ts:43-113`）：`inputs` / `outputs` / `process_data` 各带 `*_truncated` 标记，超大内容另存并由 `outputs_full_content.download_url` 取全文；`status` `error` `elapsed_time` `created_at` `finished_at`；`execution_metadata` 里带 token 数与花费；`predecessor_node_id` 记录前驱。**「截断标记 + 全文外链」是长输出日志表存不下的正解。**
- **循环/并行的进度**：`metadata.iterator_length` / `iterator_index` / `loop_length` / `loop_index`（【已验证】同上）——进度不是百分比，而是「第 i / n 项」。
- **重试历史**：`retryDetail: NodeTracing[]` + `retry_index`（【已验证】同上）；dsh-node-flow 则把每次运行的 `nodes[]` 快照整体留下（【已验证】`index.js:610-621`）。
- **dsh 的事件纪律**（【已验证】docs/subsystems/workflow.md）：`workflow/*` 事件是**只观察**的数据快照，载荷里**永远不带活的 run 对象**（订阅者拿不到 `cancel`/`dispose`）；`workflow/end` 刻意**不含结果值**（避免订阅者拿到调用方结果的别名）；每个监听者收到独立克隆，抛错的监听者只记日志、不影响后续监听者。
- **进度上报**：dsh 用 `phase(title)` 发进度分组事件，**只做展示分组，不含执行语义**（【已验证】同上）。
- **运行历史存储**：Airflow 的 XCom 表主键是 `(dag_run_id, task_id, map_index, key)`，另有 `run_id`（【已验证】`models/xcom.py:80-105`）——即「按运行实例 + 任务 + 映射下标 + 键」定位一个值。dsh-node-flow 用 JSON 文件留最近 50 条（【已验证】）。

- **存疑（与委托人设计相关）**：委托人的「执行层＝派发器 + 适配器」在本次调研的五个引擎里**都没有直接先例**——它们都是「引擎自己执行」。最接近的是 Temporal 的 worker（引擎只派发 task queue，worker 领取并执行）与 dsh 的 `ctx.workflowEngine`（引擎只编排、子任务交给 subagent seam）。**建议把 Temporal worker 的「引擎/工作者分离 + 任务队列 + 并发上限 + 优雅停机」当作我们派发器的直接参照。**
