## 1. 一句话结论

**没有一份「拿来即用」的节点库——但也不需要从零设计：n8n 与 Node-RED 的节点定义都是声明式的，可解析出结构照着抄；工作量为「写一层字段映射 + 填 26 个节点的参数」，约 2–4 天。** 唯一要守的红线：**n8n 是非开源许可，只能读结构、不能抄代码进分发物**（见 §2）。

### 通用参数设计（所有节点共用）

沿用 `src/workflow/model.ts` 的 `NodeDef`，给 `params` 补一层**参数元数据**（现在只有默认值，缺「怎么渲染表单」）：

| 字段 | 作用 | 对应 n8n 的 |
| --- | --- | --- |
| `paramDefs: ParamDef[]` | 声明每个参数是文本框/下拉/开关 | `INodeProperties.type` |
| `label` / `description` | 表单标签与说明 | `displayName` / `description` |
| `type` | `string\|number\|boolean\|options\|json\|file\|secret` | 同 `type` |
| `default` / `required` | 默认值与必填 | `default` / `required` |
| `options[]` | 下拉选项 | `options` |
| `showWhen` | **联动显隐条件**（如「method=POST 才显示 body」） | `displayOptions.show` |
| `advanced` | 是否收进「高级」折叠 | `displayOptions` + UX guidelines 的 advanced |
| `secret` | 是否密码框（防泄露） | n8n UX 指南强制 |

**\* 说明**：`showWhen`＋`advanced` 是 n8n 全部 438 个节点共用的两条规律，**已验证**（`httpRequest/v3.ts` 里逐字段带 `@displayOptions.show` 注释），也是「节点不臃肿」的关键。

## 4. 推荐方案

| 用什么 | 对象 | 理由 |
| --- | --- | --- |
| **直接用（不改）** | `@xyflow/react`（已装）、`cheerio`、`playwright`/`patchright`、`crawlee`、`croner`、`zod`；本地 `dsh-node-flow-skill` 已有的 `if/loop/switch/code/agent` 语义 | 许可干净、已装或纯依赖 |
| **改造（抄结构）** | **Node-RED 的 `defaults` 声明 → 我们的 `ParamDef`**（**首选**，Apache-2.0，字段最直白）；**Activepieces 的 `createAction({props})` → `ParamDef`**（MIT，次选）；**n8n 的 `displayOptions.show` 联动规律**（**只借规律、不抄代码**） | 三者都是「声明式参数表」，映射成本最低 |
| **自己写** | 26 个节点的 `NodeDef` 常量 + 一层的执行适配（派发到 `shell/agent/http/builtin`）；「节点库折叠分组」UI | 这是我们的业务，别人的抄不来 |
| **不要做** | 试图解析 n8n 的 6222 个 `.ts`/`.schema.js` 自动生成节点库 | n8n 有 438 节点、跨 7 个大版本，**解析器成本远高于手写 26 个**；且许可不允许抄代码 |

**落地顺序建议（推断）**：先抄 Node-RED 的 `defaults` 形状定 `ParamDef` → 填「数据/流程」5 个（最通用、无外部依赖）→ 再填「代码/终端」5 个（本地就能跑）→ 最后填「爬虫/浏览器/电商」16 个（依赖浏览器与平台登录态）。
