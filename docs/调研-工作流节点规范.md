## 1. 一句话结论

业界对「参数说明」这件事有两条成熟路线：**n8n 用 lint 强制每个参数必须有 description 并规定其写法**（100+ 条规则，绝大多数是文案规则），**Node-RED 用「帮助页五段式」把节点整体说明做成独立区块**；而「本该是枚举却写成自由文本」**没有任何平台提供自动检测工具**，这一层必须靠人写规范 + 评审兜住。

## 3. Q1–Q5 逐条回答

### Q1 参数该有哪些字段

- **「参数说明」在各家的名字**：n8n = `description`；Langflow = `info`；Activepieces = `description`；ComfyUI = widget `tooltip`；Dify = Schema 的 `description` + UI `tooltip`；**Node-RED 根本没有这个字段**——它靠节点作者手写编辑对话框 HTML，说明只能放在通用的 `form-tips` 提示行里。
- **放在哪**：n8n 的 `description` 渲染为参数的工具提示/副文本；需要富文本或链接时另开 `hint`（可含 `<a>`，Slack 节点 Slack's Block Kit Builder 即用此字段，[MessageDescription.ts:510](https://raw.githubusercontent.com/n8n-io/n8n/master/packages/nodes-base/nodes/Slack/V2/MessageDescription.ts)）。
- **必填吗**：接口层面各家都是可选；**只有 n8n 在工具链上强制**——linter 里有 `node-param-description-empty-string`、`node-param-description-missing-final-period`、`node-param-description-weak` 等一整组规则，见 [eslint-config/src/configs/nodes.ts:108-137](https://raw.githubusercontent.com/n8n-io/n8n/master/packages/%40n8n/eslint-config/src/configs/nodes.ts)。这是本次调研最有说服力的一条：**「参数必须有说明」是靠 lint 保住的，不是靠自觉。**
- 相对委托人的 `ParamDef`：已有 `hint` 但没有「选项级说明」；n8n 与 Activepieces 都在选项上给了 `description`，建议补 `options[].description`。

### Q2 「能是选项的应该是选项」

- **类型必须从枚举清单选**：n8n 用 `type: 'options' | 'multiOptions'` 表达枚举（`NodePropertyTypes`，26 种，[interfaces.ts:1939-1963](https://raw.githubusercontent.com/n8n-io/n8n/master/packages/workflow/src/interfaces.ts)）；ComfyUI 有专门的 `COMBO` 类型；Activepieces 区分 `StaticDropdownProperty`（写死）与 `DropdownProperty`（异步拉取）。
- **动态拉取机制**：n8n `typeOptions.loadOptionsMethod` + `loadOptionsDependsOn`（[interfaces.ts:2023-2025](https://raw.githubusercontent.com/n8n-io/n8n/master/packages/workflow/src/interfaces.ts)），依赖哪些字段变更就重新拉取选项；Langflow 用 `real_time_refresh` + `refresh_button` + `external_options`（[input_mixin.py:112-120, 308-320](https://raw.githubusercontent.com/langflow-ai/langflow/main/src/lfx/src/lfx/inputs/input_mixin.py)）；Activepieces 用 `DynamicProperties{refreshers}`（[dynamic-prop.ts](https://raw.githubusercontent.com/activepieces/activepieces/main/packages/pieces/framework/src/lib/property/input/dynamic-prop.ts)）。
- **「该枚举却写成自由文本」有没有工具能发现**：**没有**。n8n 的 options 相关 lint 只检查枚举**内部一致性**——`node-param-options-type-unsorted-items`、`node-param-option-name-duplicate`、`node-param-option-value-duplicate`、`node-param-option-name-containing-star`、`node-param-option-description-identical-to-name`（[configs/nodes.ts:148-160](https://raw.githubusercontent.com/n8n-io/n8n/master/packages/%40n8n/eslint-config/src/configs/nodes.ts)），**没有**任何规则判断「某个 string 参数本应是 options」。→ 这一条只能靠评审规范 + 对现有参数做取值分布排查。
- **可复用的自查法（推断，未在任一家见到）**：把现有 89 个参数的默认值与实际取值列出来，同一参数出现 ≥2 个稳定取值且取值集合封闭的，就该改成 `select`；出现自由填写的「模式/类型/单位/策略」类参数是最高危的。

### Q3 节点级说明怎么写

- **n8n 的层次**：`displayName`（节点名）+ `description`（一句话）+ `subtitle` + `documentationUrl`（[INodeTypeBaseDescription:2825-2840](https://raw.githubusercontent.com/n8n-io/n8n/master/packages/workflow/src/interfaces.ts)）+ **参数数组内可嵌 `type: 'notice'` / `'callout'` 说明块**，`typeOptions.sectionHeader: true` 还能把 notice 渲染成分区标题（[interfaces.ts:2016-2017](https://raw.githubusercontent.com/n8n-io/n8n/master/packages/workflow/src/interfaces.ts)）+ 运行期提示 `hints`（`NodeHint{message,type,location,whenToDisplay}`，[3179-3186](https://raw.githubusercontent.com/n8n-io/n8n/master/packages/workflow/src/interfaces.ts)）。
- **展开设置时用户看到什么**：以 n8n 为例——参数列表里穿插 notice 说明块与分区标题、每个参数带 description 副文本或 hint 链接、顶部有官方文档链接。**不是只有参数。**
- **Node-RED 的五段式（本次最值得抄的节点说明结构）**：帮助页固定为「引入（2-3 行，首段同时作为调色板 tooltip）→ Inputs → Outputs → Details → References」（[help-style-guide.md](https://raw.githubusercontent.com/node-red/node-red.github.io/master/docs/creating-nodes/help-style-guide.md)）。它把「这个节点做什么、吃什么、吐什么、细节、去哪看文档」一次讲全。
- **Langflow**：组件级 `display_name` / `description` / `documentation`（链接）/ `icon` / `priority`（[官方文档](https://docs.langflow.org/components-custom-components)）。
- **Dify**：节点级 `title` + `desc`，并且每类节点有独立的「帮助」按钮指向官方文档（[help-link.tsx](https://raw.githubusercontent.com/langgenius/dify/main/web/app/components/workflow/nodes/_base/components/help-link.tsx)）。
- **n8n 的资源/操作两级（Resource → Operation）**：先一个 `resource` 枚举选「操作哪个东西」，再一个 `operation` 枚举（`displayOptions.show.resource` 联动）选「怎么操作」，然后各操作自己的参数按 `displayOptions.show.operation` 出现。例：Slack 的 `resource: ['message'] → operation: [post/update/delete/…]`（[MessageDescription.ts:4-60](https://raw.githubusercontent.com/n8n-io/n8n/master/packages/nodes-base/nodes/Slack/V2/MessageDescription.ts)）。**为什么分层**：一个节点封一个服务，服务下「资源 × 操作」组合爆炸，分层把 N×M 的参数摊平成一条线性路径；n8n 甚至用 lint 固化这条经验——**operation 超过 5 个而没拆 resource 就报错**（[resource-operation-pattern.ts](https://raw.githubusercontent.com/n8n-io/n8n/master/packages/%40n8n/eslint-plugin-community-nodes/src/rules/resource-operation-pattern.ts)，阈值 5）。

### Q4 联动与折叠的成熟做法

**n8n `displayOptions` 语法（已读实现，非猜）**（[node-helpers.ts:341-474](https://raw.githubusercontent.com/n8n-io/n8n/master/packages/workflow/src/node-helpers.ts)）：

- `show: { A: [...], B: [...] }` —— **不同键之间是 AND**（源码注释 "All the defined rules have to match"，435-453 行）。
- **同一键的数组内部是 OR**（`checkConditions` 用 `.some()`，345 行）。
- `hide` 与 show 相反：**任一键命中即隐藏**（"Any of the defined hide rules"，456-470 行）。
- 比较器在 `_cnd` 下：`eq / not / gte / lte / gt / lt / between / startsWith / endsWith / includes / regex / exists`（[interfaces.ts:2126-2138](https://raw.githubusercontent.com/n8n-io/n8n/master/packages/workflow/src/interfaces.ts)，实现 360-400 行）。
- 特殊键：`@version`（取 `node.typeVersion`，用于版本迁移场景，如 `{ _cnd: { lte: 2.5 } }`）、`@feature`、`@tool`；**键以 `/` 开头表示从节点根取值**（`/authentication`，Slack 节点 779 行即此用法）。
- 值以 `=` 开头（表达式）时直接判定为显示（446-448 行）。

**折叠 vs 联动 的使用边界（n8n 的分工）**：

- **「取决于别的参数」→ `displayOptions`**（选 A 才出现 B/C）。
- **「始终可选、大多数人不用管」→ `type: 'collection'`**：一个折叠容器，用户点「Add option」才展开，标题与占位文案由 `displayName`/`description`/`placeholder` 给出（Slack 的 "Options / Other options to set / Add option"，[MessageDescription.ts:740-752](https://raw.githubusercontent.com/n8n-io/n8n/master/packages/nodes-base/nodes/Slack/V2/MessageDescription.ts)）。
- **注意**：**n8n 的参数定义里没有 `advanced` 字段**（全文检索 `interfaces.ts` 无此字段）。`advanced: bool` 是 **Langflow**（[input_mixin.py:94](https://raw.githubusercontent.com/langflow-ai/langflow/main/src/lfx/src/lfx/inputs/input_mixin.py)）和 **Activepieces**（[common.ts](https://raw.githubusercontent.com/activepieces/activepieces/main/packages/pieces/framework/src/lib/property/input/common.ts)）的做法；Dify 是 UI 组件层的 `supportFold`（[field.tsx](https://raw.githubusercontent.com/langgenius/dify/main/web/app/components/workflow/nodes/_base/components/field.tsx)）。**推断**：委托人的 `advanced` 属 Langflow/AP 路线，那就要接受它的代价——advanced 只表达「次要」，表达不了「依赖谁」；两者需要并存而不是互相替代。
- **分组/分区**：n8n 没有通用的「基本/高级/认证」三段式字段，靠 `fixedCollection`/collection 名字（官方措辞：group fields that are semantically related）+ notice 的 `sectionHeader` 造分区标题；Langflow 有 `TabInput`（[inputs.py:899-913](https://raw.githubusercontent.com/langflow-ai/langflow/main/src/lfx/src/lfx/inputs/inputs.py)）。

### Q5 现成的「节点说明规范」文档

**有，n8n 的 UX guidelines 是本次找到的最完整一份**（[官方页](https://docs.n8n.io/integrations/creating-nodes/build/reference/ux-guidelines/)），要点：

- **大小写**：节点名、参数显示名、下拉标题用 Title Case；**节点动作名、节点 description、参数 description（tooltip）、hint、下拉 description 用 Sentence case**。
- **术语**：用第三方服务 UI 里的说法而非 API 文档叫法（例：Trello 用户「archive」，API 叫「closed」）；不用技术行话（用 field 不用 key）；同一概念只用一个词。
- **占位符**：填示例、以 "e.g." 开头（`e.g. https://example.com/image.png`）。
- **布尔参数说明**：一律以 **"Whether..."** 开头（例：「Whether to append a link to this workflow…」，Slack 节点 759 行）。
- **引用参数名**：文案里提到参数/字段名用单引号包起来。
- **操作命名**：`name` 标题式、可省资源名；`action` 句式、要带资源名、省略冠词；`description` 句式、要补充比名字更多的信息。
- **错误信息**：必须含「发生了什么」+「怎么解决」，避免用 error/problem/failure/mistake 这类词。
- **参数顺序/分组**：排序选项放进独立 collection；>10 字段的接口要加 Simplify 开关。

配套还有 **n8n Code standards**（明确指向 linter）与 lint 规则名清单；**n8n Verification guidelines**（提交验证的门槛，含"英文only"、"必须有文档"等）。
**Node-RED 有《节点帮助编写风格指南》**（五段式，见 Q3）。
**Langflow 有自定义组件规范**（display_name/description/documentation/icon/priority + inputs 定义），**Dify 未找到参数级文案规范**（未获取）。

## 4. 推荐给委托人的规范

### 4.1 字段清单（可直接落地）

`NodeDef` 增：

| 新字段 | 含义 | 依据 |
|---|---|---|
| `docsUrl?: string` | 官方/内部文档链接 | n8n `documentationUrl`、Dify help-link、Langflow `documentation` |
| `help?: string` | 节点详细说明（Markdown，五段式：做什么/输入/输出/细节/参考） | Node-RED help-style-guide（可抄） |
| `whenToUse?/caveats?: string` | 「什么时候用/别用」与注意事项 | n8n `hints`、UX 指南的错误引导精神 |

`ParamDef` 增/改：

| 新字段 | 含义 | 依据 |
|---|---|---|
| `description: string`（**必填**） | 参数意义（一句话，句式、句末带句号） | n8n `description` + lint 强制（可借规律） |
| `options[].description?: string` | 选项级说明 | n8n `INodePropertyOptions.description`、AP `DropdownOption.description`（AP 可抄） |
| `placeholder?: string` | 示例值 | n8n/lf/AP 均有一致做法 |
| `group?: 'basic'\|'advanced'\|'auth'\|string` | 分区；`advanced` 保留为兼容快捷方式 | n8n collection 分组 + 通用三段式 |
| `min?/max?: number` | 数值边界 | n8n `typeOptions.minValue/maxValue` |
| `kind` 扩 `'multiselect'\|'notice'` | 多选 / 纯说明块 | n8n `multiOptions` / `notice`（借规律） |
| `showWhen` 扩比较器 | 支持 `eq/neq/includes/gte/lte` + 多条件 AND | n8n `_cnd` 比较器表 |

保留现状：`hint` 继续做「可含链接的补充说明」，与 `description` 分工——**description 说「是什么」，hint 给「去哪看/怎么做」**。

### 4.2 写法规则（8 条，可直接进评审清单）

1. **每个参数必须有 description**，空字符串视为未完成（对应 n8n `node-param-description-empty-string`）。
2. 说明用**陈述句、句末带句号**，不与显示名重复（对应 `-missing-final-period` / `-excess-final-period` / `-identical-to-display-name`）。
3. 布尔参数的说明以「**是否**」开头（对应 `boolean-without-whether`）。
4. 该枚举就枚举：**稳定取值 ≥2 且取值集合封闭 → `select`**；取值来自远端；先用静态清单 + 备注，别急着上动态拉取。
5. 选项的 label 写名词、description 写「选了会怎样」（不要 label/description 重复）。
6. 占位符写**真实示例**，不写「请输入…」。
7. 依赖别的参数才出现的 → `showWhen`；**始终可选但多数人不用管** → `advanced`。两者不能互相替代。
8. 涉及服务/平台的术语，用对方界面里的说法，不自造词。

### 4.3 显示层（回应「展开后至少知道这个节点在做什么」）

节点设置面板从上到下：**节点名 + 一句话 summary → 帮助区（可折叠，Markdown：做什么/输入/输出/细节/参考链接）→ 分区参数（基本 / 高级 / 认证）→ 每个参数带 description → 必要时插 notice 说明块**。这块结构直接照 Node-RED 五段式，成本最低、依据最硬。
