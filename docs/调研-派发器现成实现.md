## 1. 一句话结论

**有现成的，而且就在本机运行时里**：dsh 自带 MIT 的 `ctx.subprocess`（子进程 + AbortSignal 取消 + 杀树 + 优雅终止）和 `ctx.jobs`（任务登记 / 输出环 / 取消），desktop profile 已加载——**外壳直接用它们，不引入 Redis / Postgres，也不需要 execa / tree-kill**；唯一空缺是「排队」，用 `p-queue`（MIT，11.4KB）补。

`ctx.subprocess` 能力（**【已验证】** `packages/subprocess/subprocess/src/types.ts:77-107,169-196`）：
- `spawn(spec)` 收 `{argv,cwd,stdio,graceMs,signal?,env?}`；**不做 shell 解释**，`cmd.exe /c x.bat` 要自己拼 argv（与现 workbench 一致）。`signal` 触发**整棵进程范围**终止升级，`graceMs` 是宽限期。
- `terminate()` 幂等；`waitForExit(signal?)` 等**范围真正清空**（非仅顶层退出）；`done` 给 `{exitCode,signal}`，**刻意不带**超时/取消分类——由调用方判因。
- `collected.stdout/stderr` 是**按字节偏移的非消费式读取器**，带 `lossy`/`spillPath`（大输出落盘），退出后仍可读。**服务 dispose 会终止所有托管进程并等其退出。**

【已验证】Windows 杀树：`subprocess-local/src/spawn.ts:64-65,109-120` —— `taskkill /PID <pid> /T /F`（`spawnSync`，幂等不抛）；更强一层是 Job Object 的 `TerminateJobObject`（`win32-process/src/process.ts:630`）。**正好替代现 workbench 手写的 `execSync("taskkill /PID … /T /F")`**（`my-dsh-plugins/workbench/lib/index.js:506,535`）。

## 3. 推荐方案

**外壳直接用 dsh 自带 seam + 补一个 p-queue。不引入 Redis / Postgres。**

理由（**推断**，依据在上）：
1. **单机 / 小团队 / 插件内**：BullMQ、pg-boss、graphile-worker、agenda、Temporal 都是为「跨进程跨机 + 崩溃恢复」设计的，代价是**外部服务**；我们一条都用不上，反多一个运维对象。
2. **两个硬需求 dsh 已实现且 MIT**：① 可取消（`AbortSignal` → 整棵进程范围终止，Windows 走 `taskkill /T /F` 或 Job Object）；② 子进程管理（`terminate()` 幂等 + `waitForExit()` 等真实静默 + 输出偏移读、溢出落盘）。**这两块正是手搓最易错的部分。**
3. **缺口只有「排队」**：`dsh-jobs-local` 的并发上限是**拒绝**不是排队——`packages/jobs/jobs-local/src/index.ts:219-224` 实测超限直接 **throw**（`background job limit reached…`），**与我们要的 `queued` 态不符**，所以要在它**前面**放真正的队列 → `p-queue`。
4. **p-queue 的取消语义正好对**：等待中的任务被 `signal` 中止会**从队列移除**并 reject；**已在运行的**由操作自身处理（【已验证】readme「##### signal」段）。等于「queued 态队列管、running 态适配器管」，与六态模型天然对齐。

| 委托人的需求 | 用什么 | 出处 |
|---|---|---|
| 起子进程 / 包 bat、node 脚本 | `ctx.subprocess.spawn({argv:['cmd.exe','/c',bat],…})` | types.ts:77-107 |
| 杀子进程树 | `terminate()` + `waitForExit()` | types.ts:187,195 |
| 可取消 | spec 的 `signal?: AbortSignal` | types.ts:98 |
| 超时与取消分开 | 自建 `AbortController` + `dsh-timeout` 的 `TimeoutReason`/`timeoutOf()` | util/timeout/src/index.ts:12,184 |
| `queued` 态 + 并发上限 | `p-queue`（`concurrency`） | readme |
| 重试 / 退避 | `p-retry`（**desktop 已装**）或自写循环 | — |
| 运行记录 / 取消登记 | `ctx.jobs`（`start/kill/wait/read`，带 owner 与输出环） | jobs/src/index.ts:110-183 |
| 六态 | `xstate`（可选）或自写 switch | — |

**不建议**引入：BullMQ / pg-boss / graphile-worker / agenda / Temporal / Inngest / Restate（都要外部服务）；execa、tree-kill（与 dsh-subprocess 重叠）；piscina（worker_threads 非子进程）。

## 4. 最小自研方案

### 4.1 模块划分（4 个文件，都在插件内）

```
dispatcher/
  dispatcher.ts   # 派发器：认领→排队→派发→收口。唯一持有 p-queue 与状态表
  registry.ts     # 适配器注册表 name->adapter（照抄 ctx.subagents.registerProvider 形状）
  adapters/{shell,http,builtin,agent}.ts
  types.ts        # DispatchRequest / ExecutorAdapter / 六态
```

### 4.2 关键接口（伪代码）

```ts
// registry.ts —— 参照 packages/subagent/subagent/src/index.ts:512 registerProvider
interface ExecutorAdapter {
  kind: 'shell' | 'agent' | 'http' | 'builtin'
  cancellable: boolean              // 不响应 signal 的必须声明 false，否则界面会骗用户
  prepare(node, ctx): PrepareResult // 缺参数/缺依赖 → 这里响亮失败，不进队列
  run(prepared, signal): Promise<Outcome>
  dispose?(): Promise<void>
}
register(adapter): Disposer         // 返回 disposer（dsh 约定：注册即 effect）

// dispatcher.ts —— 一次派发
async function dispatch(node, upstream, runCtx) {
  const a = registry.get(node.executor)      // ① 找不到 → missing 态，不排队
  const p = a.prepare(node, runCtx)          // ② 配置错 → 立刻抛，不产生 attempt
  const attempt = { id, nodeId, retryIndex, loopId, predecessorNodeId, state: 'queued' }
  store.insert(attempt)                      // ③ 每次尝试一行，带上下文坐标
  const ac = new AbortController()
  linkCancel(runCtx.signal, ac)              // ④ 父信号 → 本 attempt
  const reason = new TimeoutReason()         //    超时单独打标，好分类
  const timer = setTimeout(() => { reason.arm(); ac.abort(reason) }, node.timeoutMs)

  attempt.state = 'running'
  try {
    const out = await queue.add(() => a.run(p, ac.signal), { signal: ac.signal })
    attempt.state = 'success'; return { ok: true, out }
  } catch (e) {
    attempt.state = 'failed'
    // ⑤ 超时/取消不是「业务失败」，不参与重试
    if (reason.isTimeout() || ac.signal.aborted) return { ok: false, kind: 'aborted' }
    return { ok: false, kind: 'failed', error: e }   // 上层再按 stop/continue/continueErrorOutput 分流
  } finally { clearTimeout(timer); attempt.finishedAt = Date.now(); store.update(attempt) }
}
```

### 4.3 三个必须钉住的点

1. **失败三态在派发器外面判**：`dispatch` 只回 `ok/failed/aborted`；`stop | continue | continueErrorOutput` 是**图的走边策略**，属引擎，照 n8n 放 `data.onError`（前序文档 §2.2）。
2. **幂等 = 认领即写 + 影响行数**：`UPDATE attempts SET state='running',owner=? WHERE id=? AND state='queued' AND version=?`，**影响 0 行就是没抢到**（前序文档 §2.3 的 `lease.go:58-77`）。**与外部队列无关，自研 10 行。**
3. **`terminate()` 之后必须 `await waitForExit()`**：`dsh-subprocess` 明说它等的是**整棵进程范围清空**（types.ts:189-195）——只 `terminate()` 就宣告 `stopped` 会漏掉孙进程。**这正是现 workbench `execSync(taskkill /T /F)` 无法保证的。**

### 4.4 代码量估计（**推断**）

types+registry ~80 行；dispatcher（认领/六态/三态）~200 行；shell 适配器 ~120 行（**用了 ctx.subprocess；手搓则 ~300 行**）；http/builtin ~60 行；agent 适配器（包 `ctx.subagents`）~60 行。**合计约 500 行**；若手搓进程管理，**仅 shell 适配器就多 ~250 行，且是并发/生命周期最易出 bug 的部分**。
