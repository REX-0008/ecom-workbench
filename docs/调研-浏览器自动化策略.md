> 状态：调研完成（2026-10-08）。用途：为「工作流全局浏览器策略」提供选型依据。
> 通道：web_search（exa/tavily 生效）+ web_fetch + raw.githubusercontent.com；**未动用** GitHub API 配额。
> 标记：**已验证** = 有一手来源；**推断** = 由证据推导、未直接证实；**未获取** = 没找到可靠来源。

## 一、结论先行

| 位次 | 策略 | 定位 |
|---|---|---|
| **主** | **CDP 接管「专用采集 Profile」的常驻有头 Chrome** | 默认执行策略，承载抖音/天猫等需登录采集 |
| 备 | `launchPersistentContext`（同一 user-data-dir，程序自拉起） | CDP 端口不通时回退；也用于首次扫码登录 |
| 辅 | 无头（`headless=new`） | **仅**公开页/自检/冒烟，**不承载登录态采集** |
| 弃 | Selenium / undetected-chromedriver 作主路线 | 优势在 Python 侧；我们技术栈是 TS，无收益 |

**理由**：登录态是资产，不是每次重建的成本。让「已登录的真实浏览器进程」常驻、采集器只做**接管**而非**新开**，同时满足「少触发风控」与「工程上可统一」。

## 二、主流方案对比（电商采集视角）

## 三、怎么连「用户已登录的浏览器」

**路 1 · CDP 远程调试端口（最主流）**
- 传统方式：`chrome --remote-debugging-port=9222 --user-data-dir=<某目录>` → `connectOverCDP('http://localhost:9222')`。
- **⚠️ 重大变化（已验证，Chrome 官方）**：**自 Chrome 136 起**，若指向**默认 Chrome 数据目录**，`--remote-debugging-port` / `--remote-debugging-pipe` **不再被遵循**；必须同时用 `--user-data-dir` 指向**非标准目录**。官方对自动化场景的建议是改用 **Chrome for Testing**。原因：攻击者大量用调试端口窃取 cookie，Chrome 用「非标准目录 = 不同加密密钥」断掉这条路。（https://developer.chrome.google.cn/blog/remote-debugging-port ，2025-03-17）
- **安全风险**：调试端口 = **完全接管浏览器**（读 cookie、读所有标签页、执行任意 JS）。**绝不能监听 0.0.0.0**。MediaCrawler 用了 `--remote-debugging-address=0.0.0.0`［8］——**反面教材，不抄**。
- 新版路径（已验证）：Chrome 144+ 可在浏览器内 `chrome://inspect/#remote-debugging` 勾选开启，并由用户**弹窗确认**授权；MediaCrawler 已切到这条默认路线［9］。

**路 2 · 连已有实例 vs 新实例复用数据目录**

| 维度 | 连接已有实例（CDP） | 新实例 + `--user-data-dir` |
|---|---|---|
| 登录态 | 天然复用，含扩展/历史/指纹 | 复用（同一目录），但**目录同时只能被一个 Chrome 独占** |
| 反检测 | **最好**——就是用户的真实浏览器［9］ | 次之——内核版本、UA、启动参数可能露馅 |
| 稳定性 | 差——用户关窗口/升级/手动操作会打断采集 | 好——进程归我们管，可 kill、可重启 |
| 冲突 | 与用户抢同一个浏览器 | 与用户日常浏览互不干扰 |

**建议**：走「**专用采集 Profile 的常驻实例**」——路 2 的目录 + 路 1 的连接方式。用户首次在该专用窗口扫码登录，之后长期复用；采集时只接管、不新开。

**路 3 · 「固定 PID」方案（委托人现在用的）**
- **推断**（无一手来源，需确认）：脚本按进程名/PID 找到**一个常驻的、已登录的浏览器进程**并把 PID 落盘；下次采集**连上去复用**而非新开；采集完**不关**，留着下次用。
- **为什么能防判定（推断）**：平台看的是「这个会话是不是新生的干净实例」。固定 PID 让所有采集**始终发生在同一个有登录态、有浏览历史、有扩展的会话里**，指纹连续、行为连续，不像每次都换一个新机器人。
- **同类佐证（已验证）**：MediaCrawler 的 CDP 模式做了同样选择——「连接已有浏览器」是**默认推荐**项，理由为「指纹更真实、自动继承登录态/Cookie/浏览历史、行为更接近真实用户」［9］。
- **统一化建议**：把「怎么找到/怎么起/怎么复用」从各采集脚本抽出，变成**一个进程管理器 + 一个连接适配器**（见第五节）。抖音/天猫各自实现的部分，正好就是这个被抽出来的东西。

**无头模式能不能用**
- **不能作登录态采集的主路线。** 依据：无头特征（`navigator.webdriver`、Canvas 指纹、字体列表）是默认暴露项；默认配置的 Playwright 访问严格风控平台「3 秒就被标为自动化工具」［10］。
- 即便 `headless=new` 已改善，**登录态场景仍不划算**：无头实例与用户真实浏览器不是同一会话，复用收益全部归零。可用场景：不登录的公开页、自站冒烟、CI。

## 四、反爬与账号安全

**什么会触发平台预警**

| 触发因素 | 来源 |
|---|---|
| 高频请求 + UA 单一 + 缺真实浏览器行为（JS 渲染/鼠标轨迹/Canvas 指纹） | 淘宝风控问答［11］ |
| 登录态缺失/过期 → **直接触发滑块或跳登录页** | 1688 采集分析：session 常 <30 分钟，`_ucKey`/`_m_h5_tk` 缺失或过期即触发［12］ |
| 签名不对（`_m_h5_tk`/`_m_h5_tk_enc`/`sign`/`t`/`appkey`） | 天猫 H5 接口逆向分析［13］ |
| 动态 Token + Referer/UA 校验 + 时间戳签名 | 同［12］ |

**委托人判断是对的**（「没登录就执行采集流程，容易触发预警」）——**已验证**：登录态失效会把请求推向验证码/登录页，而这类异常跳转本身就是强风控信号。

**登录态校验该怎么做（委托人明确要做的节点）**
- **铁律：不能用「cookie 存在」判定登录。** 现成反例（已验证）：MediaCrawler 的 B 站 `check_login_state` 曾只判断 `SESSDATA` 是否存在，导致浏览器里残留的**过期** SESSDATA 被判成「已登录」而静默降级（视频被限 480P）；修复方式是**比对扫码前后 cookie 值是否变化**［14］。
- **三态设计**：① **未登录**（探针失败）→ **阻断采集**，提示「请在专用窗口扫码登录」；② **已登录且新鲜**（探针成功 + 凭证未过期）→ 放行；③ **疑似过期**（探针失败但 cookie 仍在）→ 提示重新登录，**不静默降级**。
- **探针按平台配置，优先用页面内真实请求**，而非只看 cookie：**抖音**（已验证）`localStorage.HasUserLogin == "1"` 或 cookie `LOGIN_STATUS == "1"`［15］；**B 站**（已验证）比对 `SESSDATA` 值是否被刷新，仅存在不算［14］；**天猫/淘宝**（推断）检查 `_m_h5_tk`/`_m_h5_tk_enc`/`_tb_token_`/`_ucKey` 齐全**且未过期**，再在页面内实调一个「必须登录才返回」的接口，以是否返回正常数据为准——**需落地时逐平台验证**。

**多账号 / 多实例隔离**
- **Playwright 官方**：每个测试用独立 browser context 是标准隔离模型［3］；但 **context 不隔离指纹**，只隔离 cookie/storage。
- **多账号正确做法（已验证的开源实践）**：**每账号一套独立 user-data-dir + `launchPersistentContext`**，各自独立代理/UA/视口/时区/指纹，并按 LRU 控制同时存活数省内存［16］。
- **易漏的坑（已验证）**：必须加 `--force-webrtc-ip-handling-policy=disable_non_proxied_udp`，否则 WebRTC 走 STUN 直连暴露宿主真实 IP、**绕过 HTTP 代理**，让「一号一代理」的防关联失效。另一细节：账号 UA 里写死的 Chrome 版本必须**对齐真实内核版本**，否则 `Sec-CH-UA` 与 UA 对不上，本身就是自动化特征［16］。

## 五、工程实现：怎么做成「全局设置」

**配置项（建议的全局浏览器策略对象）**：`mode`（`cdp-existing` / `persistent` / `headless`，策略主开关）、`profileDir`（专用采集 Profile 目录，**非** Chrome 默认目录——Chrome 136 硬要求）、`cdpPort`（默认 9222，被占则顺序探测，MediaCrawler 会试 100 个［8］）、`headless`（默认 false）、`stealth`（`off` / `patchright` / `rebrowser`）、`timeout` / `retry`、`perAccountProfile`（多账号是否各自独立目录）。

**抽象成适配器**：工作台已有「**派发器 + 执行方适配器**」架构（见 ../plans/2026-10-05-线路图.md）。浏览器策略正好落成一个**浏览器执行方适配器**，契约建议 4 个方法：

```
resolveProfile(accountId) -> profileDir      // 账号 → 独立 Profile
ensureRunning(profile)    -> endpoint       // 没有就起，有就返回端点（PID 落盘）
connect(endpoint)         -> browser        // connectOverCDP，失败回退 persistent
healthCheck(browser)      -> loginState     // 三态探针，喂给「登录校验节点」
```

**关键纪律**：`ensureRunning` 是**唯一**拥有「起浏览器」权力的地方。抖音/天猫各自的实现收敛到这里之后，「固定 PID」不再是各脚本的私有逻辑，而是这个适配器的内部细节。

## 六、主对话补充：委托人现有实现的一手核实（2026-10-08）

### 6.1 「固定 PID」实际是「固定 Profile + 固定 CDP 端口」

```ts
// launch-chrome.ts —— 实际实现
dy: { dir: .../取数浏览器/dy-demoshop,          port: 9223, headed: true, minimized: true },
tm: { dir: .../取数浏览器/tm-demoshop, port: 9222, headed: true },
// 启动参数：--user-data-dir=<专用目录> --remote-debugging-port=<端口> --remote-debugging-address=127.0.0.1
// 连接方式：chromium.connectOverCDP("http://127.0.0.1:9222")
```

**修正调研的推断**：
| 调研推断 | 实际 |
| --- | --- |
| 「按进程名/PID 找到浏览器进程」 | ❌ **不是按 PID**，是**按固定 CDP 端口连接** |
| 「连上去复用」 | ✅ 对 |
| 「采集完不关，留着下次用」 | ✅ 对 |

→ **「固定 PID」是误称；准确说法是「固定 Profile + 固定 CDP 端口 + 常驻有头窗口」**。

### 6.2 委托人已实测的三条硬经验（比调研的推断更硬）

**① 无头模式会烧掉会话**（`launch-chrome.ts` 注释，2026-09-04 bilibili 四组对照实验）：
> 「无头 HeadlessChrome UA 触发服务端环境校验**烧掉会话**——**cookie 落盘正常但服务端判定未登录，换回有头也不恢复**；有头重启则安全。」

**② 淘宝 cookie 是会话级**（`tb-sycm.ts` 注释，Cookies DB 实证）：
> 「淘宝登录 cookie（unb/cookie2/_tb_token_/skt 等）**是会话级（is_persistent=0，实证，关窗即焚）**——**tm 窗口关闭 = 登录态失效**；窗口常驻 = 会话常驻。」

**③ 掉登录时「不硬闯」**（`tb-sycm.ts` 注释）：
> 「**掉登录时不硬闯**：弹出登录页等人登录（5 分钟超时），成功后自动继续」
> 「响应含 **滑块/验证码/操作过于频繁/请重新登录** → **立即终止，退出码 2，绝不重试**」

### 6.3 抖音与天猫已共用同一浏览器通道（统一化已部分发生）

  ② 起来后**别关那个浏览器**（登录态是资产，我们要的是常驻）。
- 验证：新标签打开 `http://127.0.0.1:9222/json/version`，能看到浏览器版本即成功。

### 6.4 对「统一方案」的直接影响

| 项 | 结论 |
| --- | --- |
| **统一什么** | 把「启动/复用/连接/健康检查」从各脚本抽出 → 一个**浏览器进程管理器 + 连接适配器** |
| **适配器契约**（调研给的 4 方法） | `resolveProfile` / `ensureRunning` / `connect` / `healthCheck` —— **与委托人现有实现吻合** |
| **必须保留的差异** | Chrome（专用 profile、9223）vs QQBrowser（默认 profile、9222）—— **两者 profile 策略不同**，适配器要能表达 |
| **登录校验**（委托人要做） | 现成做法：**掉登录时弹登录页等人**（`tb-sycm.ts` 的 `_wait_for_windows_login` 模式）——**已有实现可复用** |

## 七、中国电商平台的现状与坑

1. **主流方案就是「接管已登录的真实浏览器」**，不是硬破解登录——淘宝的滑块/短信/人脸让模拟登录成功率极低且易封号［17］。
2. **天猫/淘宝不能靠直连接口**：`_m_h5_tk`、`_m_h5_tk_enc`、`sign`、`t`、`appkey` 都要 JS 逆向且规则频繁变；**用浏览器执行正是规避这块成本的正解**［13］。
3. **登录态寿命短**：同类平台 session 常 <30 分钟就需重校验［12］——所以登录校验节点**不能只在流程开头跑一次，长任务中要能中途复检**。
4. **抖音**：MediaCrawler 作者自己标注「抖音登录滑块验证准确率不好，无特殊需求建议不要用抖音登录，或用 cookie 登录」［15］。［17］https://wenku.csdn.net/answer/70fvcx63d5i
