> 状态：调研完成（2026-10-07）

> 纪律：标「已验证」的为实际抓取；标「推断」的为我据证据推导

## 1. 一句话结论

**没有能直接 npm install 的「节点内运行时显示」组件**（npm 检索「reactflow node status / node progress」只返回 xyflow 官方包，无第三方）——但这个模式有三套生产级实现可抄，**MIT 的 Langflow 最值得抄**；自己写「通用预览版」的净成本约 100 行，是最优解；**xterm.js 不推荐**（gzip 118KB 只为显示几行日志，性价比极低）。

### Langflow 的具体做法（已验证源码）
- `src/frontend/src/CustomNodes/GenericNode/index.tsx`：节点卡片 JSX 里**直接内联** `<MemoizedNodeStatus>` 与 `<MemoizedNodeOutputs>`——即状态与输出就画在节点体内，不是浮层。
- 同文件 import 了 `useUpdateNodeInternals` 并调用 `updateNodeInternals(data.id)`——**与我们已知的坑完全一致，官方也这么做**。
- `components/NodeStatus/index.tsx`：`POLLING_INTERVAL = 3000` / `POLLING_TIMEOUT = 21000` 轮询构建状态。

### ComfyUI 的具体做法（已验证源码片段）
- `src/components/graph/nodeProgressCanvasSync.ts`：`progressValue()` 取 `state.value / state.max`，用 `setNodeProgress(node, nextProgress)` 写到节点对象上，变更即 `canvas.setDirty()` 重绘；用 `nodesByLocator` 把执行状态映射到画布节点。
- **推断**：这是 canvas 渲染路径（litegraph），DOM 版直接映射成 style 宽度即可。

## 3. 推荐方案

### 结论：自己写「通用预览版」，抄 Langflow 的结构 + 用 use-stick-to-bottom 兜滚动

**不直接用任何现成组件**——理由：三套实现都是整仓应用（不是可复用包），唯一可复用的两个包（streamdown / xterm）都因体积或依赖被否。

要自己写的量很小，且与现有节点卡片天然契合（`WorkflowNode.tsx` 已有 `stateBar` + `progress` 字段）。

**四类显示，分两级做：**

| 级别 | 内容 | 成本 |
|---|---|---|
| 第一版（通用预览版） | 状态反馈：运行中转圈 + 进度条（`progress` 文字已有）+ 一行最后日志 | ~60 行 |
| 第二版 | 流式文本：增量追加 + 自动滚到底 + 截断 | 再 ~40 行 |
| 暂不做 | 富文本 Markdown、终端模拟 | — |
| 暂不做 | 图片预览（委托人说后面再说） | — |

### 必须先定的三个设计点（做完会返工的地方）

1. **数据别塞进 React Flow 的 `data`**。流式输出每秒几十次更新，写进 `data` 会让**整个节点**重渲染。建议：日志/流式文本走 zustand store（项目**已装** zustand 5），节点内只有那个小面板组件订阅它。
   — **推断**，依据：React Flow 的 node data 变更会触发节点组件重渲染；`WorkflowNode.tsx` 第 74 行用了 `memo`，但 data 换引用照样穿透。

2. **高度必须封顶**。面板给 `max-height` + `overflow:auto`，日志数组只留最近 N 行（建议 50）。否则节点随输出无限长高，布局（elkjs）和画布都会崩。

3. **详情面板出现/消失时调 `useUpdateNodeInternals()`**——这是已知坑，Langflow 也踩了同样的解法（见上）。

### 直接可用的两个依赖（要加就加这两个，其它别加）
- `use-stick-to-bottom`（MIT，32KB，**零依赖**）——自动滚到底，且用户手动上滑时不抢滚动条。这是流式输出体验的关键细节，自己写容易出 bug。
- `@radix-ui/react-progress`（若进度条要无障碍支持）——可选；纯 CSS 也可，项目用 CSS Modules，**推断**纯 CSS 更贴合现有风格。

### 关于 xterm.js（回答委托人「值不值得用」）
**不值得。** 验证数据：gzip 118KB + CSS 2.5KB，纯为了在节点里显示几行日志。附三个额外代价：
1. 它是 canvas 渲染，节点**可缩放**，需要常驻 ResizeObserver + `@xterm/addon-fit` 才能不出现列被裁切；
2. 节点挂载/卸载频繁（React Flow 虚拟化时），xterm 实例的初始化与销毁成本明显高于一个 `<div>`；
3. 节点场景不需要交互式终端（不需要输入、光标控制、真彩色 ANSI 全量支持）。
**结论**：除非后续要支持「在节点里跑交互式 shell」，否则一个 `<div>` + 可选 `ansi-to-react`（12KB，仅当日志含 ANSI 转义时）足够。
