# 假防线：看着写了、其实不生效的规矩（2026-10-15）

> 「没有防线」会让人留神；**「看着有防线」会让人不留神** —— 后者更危险。
> 这份记的是已经踩到的几处，**文件名就是主题**：写规矩之前先确认它真的生效。

## ⚠️ 两条比上表更重要的（2026-10-15 新增，都是方法论的）

### 一、**「修法」本身也是一个待验证的假设**（不要只信审查给的改法）

**真事**：审查（T4）诊断出 #7 那条死规则**完全正确**（实测复现：`.flex-1` 确实赢了）。
但返修者（t11）**把审查给的两个修法都量了**，结果两个**都会造成更大的可见回退**：

| 配置 | 面板根 computed flex | 滚到底后「刷新行」偏移 |
| --- | --- | --- |
| 现状（`.flex-1` 赢） | `1 1 0%` | **0**（仍在视野）✅ |
| 审查给的修法①：加权重 | `0 0 auto` | **−952**（被滚走）❌ |
| 审查给的修法②：去掉根的 `flex-1` | `0 0 auto` | **−952**（被滚走）❌ |

**真因**：那个面板根**必须撑满**（内部那层才是滚动层、「刷新」行要固定）；
压成内容高度后滚动交给外层，**面板头一行就跟着滚走了**。
→ **现态恰好是想要的，正确动作是「删掉那条无效规则」**，而不是按修法去「让它生效」。

**规矩**：
- **审查说「这里有错」通常是可信的；它给的「改法」只是一个假设。**
- 修之前**先把改法量一遍** —— 有可能「现状虽然难看，但是对的」。

### 二、**验证工具本身也会坏，而且坏了会让你误判****真事**：t11 跑突变测试发现「断言突变后照样绿」，**先误判成「我的断言太弱」**。
实际原因是 **`execFileSync('npm.cmd', ['run','bundle'])` 在本沙箱静默失败**：
返回 `status = null`（**既不是非零、也不抛异常**）→ **产物没更新** →
所有读产物的断言都在验**旧产物** → 突变当然抓不到。

**规矩**：
- **任何「读产物」的测试，前提都是「产物是新的」** —— 而「构建有没有真的跑成功」**必须单独验**
  （不能只看它没抛错）。
- 本项目读产物的测试有 4 个：`dom-render` / `host-dispatch` / `bundle-identifiers` / `css-refs`。
  **它们全绿不能证明代码对，只能证明「产物与断言一致」**。
- 修法（t11 的做法）：**直接跑构建命令**，并在**构建失败时打印警告**。

### 三、**jsdom 没有布局 —— 依赖尺寸的 bug 在测试里是隐形的**（2026-10-16 新增）

**真事**：`LoopNodeCard` 里有一行**渲染期**的 `updateNodeInternals(id)`
（React Flow 的 hook）。它在真浏览器里是**每帧往 store 写新对象 → 无限重渲染**
（用户看到的症状是「循环的设置点不开，点什么都没反应」）；
而在 jsdom 里**完全无害** —— `updateNodeInternals` 内部有一道
`doUpdate = dimensions.width && dimensions.height && (…)`，
jsdom 的 `offsetWidth` 恒为 0 → 一次都不写。

所以**全套 46 个测试对此全绿**，`check:types` / `check:tdz` 也全绿。

**规矩**：
- **凡是「依赖真实尺寸/布局才发生」的行为，jsdom 测试证明不了它**。
  这一族包括：`offsetWidth/Height`、`getBoundingClientRect`、
  `ResizeObserver` 的回调、以及**由它们驱动的状态写入**。
- 这类 bug 只有两条路能抓：① **真浏览器**；② **读源码断言**（把「这行在渲染期」
  这个形态直接钉死）。本次走的是 ② —— `refit-base` / `loop-box` 里那几条。
- ⚠️ 与它配套的**反向陷阱**：正因为 jsdom 看不见，**我更容易相信「测试全绿就是好的」**。
  用户报「点了没反应」时，先去想「这个效果在 jsdom 里能观察到吗」——
  观察不到的话，绿不等于对。

### 四、**断言在空数据上抛异常 —— 整份文件断掉，看起来像「只红了两条」**（2026-10-27 新增）

**真事**（票 01，对齐参考线）。自证要求「把阈值改成 0，对应断言必须红」。
改完跑出来**只有 2 条红**，看着像「自证不够狠、判据太松」。

实际是：第 3 条断言写的是

```js
check('★ 竖线画在两条边的纵向范围里',
  r.vertical[0].from <= 100 && r.vertical[0].to >= 220,   // ← 数组空了，这里抛 TypeError
  String(r.vertical[0].from) + '→' + String(r.vertical[0].to))
```

阈值一改 0，`r.vertical` 变成空数组，`r.vertical[0]` 是 `undefined`，
`.from` 直接抛 `TypeError: Cannot read properties of undefined (reading 'from')`
—— **进程当场退出**，后面的 12 条断言**一条都没跑到**。

所以看见的是「2 条红」，真相是「14 条该红的，跑到的只有 2 条」。
**修好之后才是 14 条全红。**

**为什么这个形状特别危险**：

- 它长得**像判据太松**（才红两条），于是下一步很容易走错方向 ——
  去加更多断言，而不是去修那条会崩的；
- 如果那次跑的不是自证而是**正常验收**，那 12 条断言就**从来没跑过**，
  而结论仍然是「通过」（因为崩之前没有红）。**这是假绿，不是假红。**
- 断言里的 `detail` 参数同样会求值 —— 我把 `String(r.vertical[0].from)` 写在
  第三个参数里，它**先抛错**，`check()` 一次都没进去。

**规矩**：

1. **凡是取 `arr[0]` 的断言，前面必须带长度判断**：
   `arr.length === 1 && arr[0].xxx`，不要靠「它应该有值」。
2. **`detail` 参数也是代码**，同样会抛错。空数组时要走一条不取属性的分支
   （`r.vertical.length === 0 ? '（没有线）' : …`）。
3. **看见「红的条数比预期少」，先怀疑「是不是断掉了」，不要先怀疑判据太松。**
   判据太松的表现是「该红的全绿」，不是「只红一部分」。
4. **自证要核对红的条数**，不只是「有没有红」。写清「改成 X 应该红 N 条」，
   跑完对一下数 —— 数对不上就说明中间断了或漏了。

## 怎么避免（三条）

### ① 写完规则**立刻验它生效**，不要靠读代码

**反例（我犯过）**：我读 `.toolbar` 那几档规则，觉得「写得很齐」——
而它们**一条都没生效过**，因为容器查询不作用于容器自己。

**对的做法的代价也不高**（T2/T3 都这么干）：
- **真浏览器 + 产物真 CSS** 量一次实际值（`0px` → `93px` 就是这么量出来的）
- 或用**突变测试**：把规则改坏，看断言**会不会红**。**不红就是假绿**

⚠️ **突变测试是这里唯一可靠的验证**：本项目多次出现「断言绿了，但改坏代码它照样绿」。
判据很简单：**把要验的东西改坏 → 跑测试 → 必须红**。

### ② 判据要锚到「真实结构」，不要锚到「源码文本」

**反例（T3 自己抓到的）**：它的断言原本只查**源码里前后位置**，
抓不住「挪出了块但源码顺序没变」这种改法 → 改成**真实 DOM 结构断言**才有效。

同类的还有：用正则匹配 CSS 时写太宽（`[^{]*`），
结果 `.select option.disabled-fake` 也被匹配进去了。

### ③ **「源码里有」不等于「产物/界面上有」**（2026-10-17 新增，本轮连踩三个）

上表 11 / 12 / 13 是同一族：**判据写在源码层，而效果发生在产物层或界面层**。

| 层次 | 写在哪 | 生效在哪 | 谁看不见 |
| --- | --- | --- | --- |
| 样式 | 组件里的类名 | **编译后的 CSS** | 断点变量缺失 → 整条规则被丢 |
| 界面 | `paramDefs` 的参数定义 | **渲染出来的控件** | 组件提前返回 → 那个参数没人画 |
| 观感 | 内联 CSS 变量 | **人眼看到的对比** | 上下两层同色 → 改了看不出 |

**规矩**：断言要落在**效果真正发生的那一层**。
- 验样式 → 查**产物 CSS 里有没有那条规则**（不是查源码里有没有那个类名）
- 验界面 → 查**DOM 里有没有那个控件**（不是查参数表里有没有那一条）
- 验观感 → 至少查「上下两层的颜色**是不是同一个**」；这一步人眼替不了的部分要**明说交给用户看**

本轮的做法（可照抄）：
`tests/css-refs.mjs` 新增一段 —— 源码里凡出现 `sm:`/`lg:`/`2xl:` 这类变体，
就去**产物里核对**对应前缀的类名真的发射了、且 `@theme` 里声明了那个 `--breakpoint-*`；
用**突变测试**验过（删掉 `--breakpoint-sm` → 当场红）。

### ④ **反面断言也要能「找到东西」，否则它在空串上判断照样通过**（2026-10-17 当场抓到）

写「不许再是 grid」这条反面断言时，我的选择器是「向上找带 **columns** 的祖先」——
于是有人真把它改回 grid 时，那个循环一路走到 null、拿到空串，
反面断言在空串上判断 → **✓ 通过**。**突变测试当场抓出来**（改回 grid 后它报 ✓）。

修法：**找容器的选择器要同时认两种形态**（`columns-ewb-card|\bgrid\b`）——
先找到「那个容器」，**再**判断它是哪一种。顺序反了就是假防线。

同族的还有（本次一起踩的）：
- **读产物的断言，突变测试必须先重新构建**。我第一次突变时只改了源码、没 `npm run bundle`，
  于是测的还是旧产物 → 断言报 ✓，我差点以为「断言是真的在测」。
  这与上表 #8「构建静默失败」是同一个陷阱的另一面。

### ⑤ **「删掉被测物」也是一种突变 —— 断言必须能抓住「根本没有」**（2026-10-17 补）

上表 #14 的第二条假绿：断言写的是「**定义里声明的每个参数都渲染出来了**」。
它**完全合理，也确实抓得住「定义了没渲染」**；但把定义那一项**删掉**时，
定义里没有了、界面上自然也没有 —— 两边一起消失，断言照样 ✓。

**规矩**：凡断言形如「A 里的每一项都在 B 里」/「B 覆盖了 A」，就要问一句：
**「把 A 删空会怎样？」** 删空之后 B 也空了，两边一致 → 绿。
所以这类断言必须**额外钉住 A 里至少有几个、是哪几个**（本例：`name` 与 `inputs`）。

这与 #4 的「反面断言要在空串上判断」是同一族：**两边都能一起变没的断言，等于没有断言**。
### ⑥ 这类「假防线」是**同一个病根**

上表 1 与 2 是同一族：**CSS 的作用域/生效条件没搞清**；
3–5 是同一族：**判据写了、执行没接上**（T8 的原话「判据搬齐了，执行没搬」）。

**所以复查时按这两族去扫**，比一条条看更有效：
- CSS：**这条规则在什么条件下才生效？那个条件现在成立吗？**
- 流程：**这个判据触发之后，谁真的会停下来？**

### ⑦ **「存在才验」= 存在才绿，不存在更绿**（2026-10-26，`dom-render` 五处）

**形状**：
```js
const node = doc.querySelector('[data-group-id]')
if (node !== null) {            // ← 取不到就整块跳过
  if (!node.querySelector('.x')) errors.push('缺 x')
}
```

**取不到时一条断言都不执行、也不报错** —— 而这恰恰是「功能根本没做出来」的那种情况。

`dom-render` 里扫出 5 处（`L1654 / L2116 / L2888 / L3272 / L4675`）。注入验证：把这 5 处的前置一起改成取不到 → **全文件 0 条红**。

**修法：先断言「找得到」，再断言内容。**
```js
if (node === null) errors.push('找不到分组框实例，下面那条没验到')
else { …原来的断言… }
```

⚠️ **`null !== undefined` 是 `true` 这件事要单独注意**：`?.querySelector()` 可能返回 `null`，
写成 `if (x !== undefined)` 时 `null` 会进块，然后在 `null.dispatchEvent` 上抛 TypeError。
崩掉是响的，但报错指向 TypeError，看不出「这一组断言没验到」。

**这与 ④「反面断言要在空串上判断」、⑤「A 里都在 B 里」是同一族**：
**只要「被测物不存在」和「被测物存在且正确」能落到同一个结论上，这条断言就等于没有。**

### ⑧ **位置本身就错了：断言写在元素还不存在的地方**（2026-10-26，`dom-render` ⑤b）

⑦ 的 5 处里，有一处补上兜底后**在正常运行时就红了** —— 那说明不是断言写错，是**位置错了**。

真事：「分组框实例上有描述输入与按钮」那两条，写在 ⑤b「节点外观」段，
而**此刻画布上还没有任何组节点** —— 组是用户右键「打包成分组」之后才创建的，那一整段在 600 行之后。
所以那两条**从写下的那天起一次都没跑过**，而测试一直是绿的。

**处置**：把那两条挪到「选中多个节点后右键 → 打包成分组」那一段（组真的存在的地方），
并在原位置留注释写明「**不移回这里**：这里没有组节点，放回来就是又一次假绿」。

**判据**：给 `if (x) { 断言 }` 补上兜底之后，**如果它在正常路径就红了**，
先别怀疑断言，去查**这个元素在这个位置到底存不存在**。存在性问题是结构问题，不是判据问题。

### ⑨ **用脚本数「形状」，再拿形状当「问题」，一定会多算**（2026-10-26，同一个数错了三次）

查「哪些断言会静默跳过」时，同一件事三个人/三次给出了三个数：

| 次数 | 口径 | 数 | 实际 |
|---|---|---|---|
| 1 | 我按**行数**数「否定断言」（`仍然` 21 行 + `不该/不许/不应` 99 行） | 120 | **7 条真断言**，其余 110 行是注释 |
| 2 | 执行角色按**行级脚本**数「有 else 兜底的」 | 26 | 按括号配平只有 **2 处**，且都不是问题 |
| 3 | 我按**括号配平**数「if 内有断言、else 内无断言」 | 2 | 2 处**都是正确写法**（`if (x === null) { 报错 } else { 正常路径 }`） |

**为什么第 3 次数对了形状、还是数错性质**：

「else 里没有断言」不等于「假绿」。真判据是 ——
**if 条件不成立时，有没有别的地方会报错？**

`L1415` 那种 `if (firstHandle === null) { errors.push('没有端口元素') } else { …验两条… }`
**形状是反的，判据是全的**：找不到时前面的分支已经报错，else 根本不需要兜底。

`L920` 同理：`errors.push('没有那一行')` 在外层 `if` 上，内层 `else` 走的是正常路径。

**规矩**：
- **脚本只能数「形状」，数不出「性质」**。形状当线索可以，当结论不行。
- 判「这条断言会不会静默跳过」只有两条可靠路径：
  ① **注入后看会不会红**（本文件通篇的方法）；
  ② **给每条断言加执行计数**，测试末尾断言「实际执行条数 === 源码条数」，
     差额逐个登记理由（互斥分支那种「只执行一条」是对的，要预先登记）。
- ⚠️ 用脚本数出来的数，**交付时必须说明口径**。只说「有 26 处」而不说「按行级匹配」，
  下一个人会把它当成事实去改 26 个地方。

### ⑩ **判据写在「位置」上而不是「条件」上：挪位置优先于删断言**（2026-10-26）

⑦ 的第一处补完兜底后在**正常运行**就红了。三条路：

| 方案 | 代价 |
|---|---|
| A 挪到元素真正存在的那一段 | 要改测试顺序，但**能真验到** |
| B 删掉这两条 | **减少断言条数** |
| C 留着一直红，当待办标记 | **从此不绿，以后所有人看到红就麻木** |

**选 A。** 理由：**C 比假绿更糟** —— 假绿至少还让人以为在验；
一个天天红的测试会让所有人学会忽略红。B 则是直接放弃。

**判据**：补兜底后「正常路径就红」→ 先别怀疑断言，去查**这个元素在这个位置到底存不存在**。
存在性问题是结构问题，不是判据问题。

### ⑪ **自证注入必须打在代码行上，不能打在注释上**（2026-10-28，同一类问题的第四次）

自证的做法是「把修复改坏 → 断言必须变红 → 还原」。**问题出在「改坏」这一步**：
如果注入脚本按字符串替换，而**注释里也有同一段文字**，替换就命中了注释 ——
代码一行没动，测试当然不红。这时人会得出**完全错误的结论**：
「我的断言抓不到这个 bug，判据太松」→ 然后跑去加固判据，
而真正的问题是自己根本没改坏。

#### 真事（票 33，2026-10-28）

自证「外层栅格是三栏」时，脚本把 `lg:grid-cols-[300px_minmax(0,1fr)]` 换回两栏写法，
跑出来**一条都没红**。差点得出「判据太松」的结论。实际原因：

```tsx
/* 改之前是 … lg:grid-cols-[300px_minmax(0,1fr)] …  ← 注释里也有这一串
 * main  lg:grid-cols-[300px_minmax(0,1fr)]  xl:grid-cols-[320px_minmax(0,1fr)]
 */
<main className="grid … lg:grid-cols-[300px_minmax(0,1fr)] …">  ← 真正的那一行
```

`str.replace()` 换掉的是**注释里那一句**，`className` 一个字没变。

同一天同一个票里又踩一次：给记录抽屉做自证，注入 `open={false}`，
但那段参考原文就抄在组件上方的注释里（`open={logsOpen} onClose={…}`），
**命中次数 2**。那次脚本打印了「命中 2 次」才被我看见。

#### 修法（三条，按可靠度排序）

| # | 做法 | 为什么可靠 |
|---|---|---|
| 1 | **让脚本自己报命中次数，不等于 1 就停** | 命中 2 次会立刻暴露「注释里也有」。这一条就能挡掉绝大多数 |
| 2 | **注入片段带上足够长的上下文**（整行 `className="…"`、整个属性组），而不是只有那一个标识符 | 注释里通常是**孤立的片段**，不会连上下文一起抄 |
| 3 | **注入前后打印 `git diff`**，确认改的是代码那一行 | 最终判据：diff 里出现的东西必须是你想改的那一行 |

⚠️ **只做第 1 条是不够的**：命中 1 次也可能正好命中注释（注释是唯一一处时）。
所以第 2 条是主手段，第 1 条是兜底报警。

#### 反过来说：注释里**不该**抄那段代码

这一轮踩坑的根不是脚本，是**注释本身在抄代码**。注释要写「为什么」，
不要贴「是什么」—— 贴了就成了注入的假目标，也成了别的文本匹配断言的假靶子
（同族问题见 #14 的「断言在整块 `textContent` 里找标签，`hint` 里的同一个词照样命中」）。

docs/ 里也有一次同族的：写「否定断言条数」的统计脚本按行数数，
把注释里的 110 行算成了断言（见本文件后面「用脚本数数」那一节）。

### ⑫ **判据找的字符串形态与产物真实形态不一致 → 永久假红（比假绿更耗人）**（2026-10-28）

假绿是「该红不红」，假红是「该绿不绿」。**假红同样致命，而且更耗人**：
它会让人反复去修一个没坏的东西，最后把一条真判据当成噪音关掉。

#### 真事（票 42，`tests/css-refs.mjs:157`）

那段检查「源码用了某个断点类 → 产物里必须发射了」。找法是：

```js
const needle = '.' + p + BS + BS + ':'   // p 取 sm / md / lg / xl / 2xl
```

对 `sm` / `lg` / `xl` 有效（产物里是 `.sm\\:`）。但 **CSS 规范要求以数字开头的类名必须转义首字符**，
所以 `2xl:` 在产物里的真实形态是：

```
.\32 xl\\:grid-cols-3{grid-template-columns:repeat(3,minmax(0,1fr))}
```

`\32` 是字符 `2` 的八进制转义，后面那个空格是转义终结符，**不是空格分隔**。
于是 `'.2xl\\:'` 这条 needle 永远找不到 —— 红的是判据自己。

它**长期潜伏**没被看见，因为源码里此前没人用 `2xl:`，`used` 表里没这个键，检查空过。

#### 为什么这条特别容易误判成别的原因

我先按「产物过期」处理，跑了 `npm run bundle`（退出码 0，同步 4 个文件），**重跑还是红**。
如果没有「打包后仍红」这一步，结论就会错记成「打包会自愈」，下次照样踩。

**教训**：假红时要先问「是不是判据找的东西形态就不对」，而不是先问「是不是没构建」。

#### 怎么确认是判据的错，不是产物的错

**逐字符看产物**，不要看 grep 的空结果：

```js
const t = readFileSync('lib/client.js', 'utf8')
const BS = String.fromCharCode(92)
const i = t.indexOf(BS + '32 xl' + BS + BS + ':grid-cols-3')
console.log([...t.slice(i, i + 16)].map(c => c.charCodeAt(0)).join(','))
// 92,51,50,32,120,108,92,92,58  ← \32 时空格 2xl \\:
```

对照正确的那条：`.sm\\:` 的字符码是 `46,115,109,92,92,58`。
**两边字符码摆在一起，一眼就能看出形态不同。**

#### 修法

```js
// ⚠️ 只对 2xl 成立，别当通用公式往后推
// CSS 对数字开头的类名转义首字符：2xl → \32 xl（三位数的 3xl 会是 \33 xl）
const needle = /^\d/.test(p)
  ? '.' + BS + BS + '3' + p.slice(1) + ' ' + p.slice(2) + BS + BS + ':'
  : '.' + p + BS + BS + ':'
```

**必须写的注释**：这条分支是「针对已知的 `2xl` 一个特例」，不是「按前缀长度自动推导」。
下一个人照公式往下加 `3xl` 会静默错。

#### 这条与前面几条的关系

| 病 | 方向 | 症状 |
| --- | --- | --- |
| ③⑤⑦ 假绿 | 该红不红 | 有 bug 测试还是绿 → 以为修好了 |
| **⑫ 假红** | 该绿不绿 | 没 bug 测试一直红 → **把真判据当噪音关掉，连带丢掉它本来能抓的东西** |

**判据的「找法」本身也要验**：一条针对产物文本的断言，至少要有一次「乱换一个绝不存在的串，
它必须红」与一次「换成真的那个串，它必须绿」的双向确认。只做单向，假红假绿都发现不了。

### ⑬ **「采样是空的」让判据永远成立**（2026-10-28，票 48）

这是 ⑦「存在才验 = 不存在更绿」的近亲，但更难发现：**采样容器在，只是里面没东西**。

#### 真事

票 48 要把「收起顶部」按钮从侧栏底部搬到面包屑。写完发现 `dom-render` 里一条该红的断言没红：
「侧栏底部那一列**不含**『收起顶部』四个字」。

收窄搜索范围之后它还是绿。真因：**那条断言跑在收起态** —— 收起态的侧栏按钮只有图标、
文字是空串，于是「不含这四个字」对空串恒成立。

```
收窄前：全树搜按钮文字 → 把面包屑那颗新按钮也捞进来 → 假红
收窄后：只搜侧栏底部 → 但那列在收起态文字全是空串 → 假绿
```

**两次连撞，方向相反，根子是同一个**：判据假设「采样里一定有关注的东西」，
而那个假设没有写出来、也没有被检查。

#### 修法（两条前提，缺一不可）

1. **先把界面切回「采样里真有文字」的那个态**（这里是展开态）
2. **加一条「采样必须非空」的前提断言** —— 采样是空的时候直接红，不许往下判

```js
// ① 切回展开态
// ② 采样非空：一条「样本必须正好 N 颗按钮」的前置断言
check('★ 前置：侧栏底部这一列采到了 N 颗按钮（空采样会让下面的判据恒真）', sample.length === 2, ...)
```

#### 与 ⑦ 的区别

| 病 | 采样容器 | 判据结果 |
| --- | --- | --- |
| ⑦ 不存在才绿 | **不存在** | 绿 |
| **⑬ 采样为空** | **存在但空的** | 绿 |

⑦ 至少能靠「容器在不在」发现；⑬ 连容器都在，只是没内容 —— **要专门加一条采样的前置断言才能发现**。

#### 一句话判据

**写「不含 X」之前，先问一句：采样里现在会不会本来就是空的？**
会的话，先把它填起来或切到有内容的态，再加一条「采样非空」。

### ⑭ **零引用判定要扫四种导入形态，漏一种就会误删在用的模块**（2026-10-28，票 47）

删「没人用的文件」之前要先确认零引用。**只扫 `import` 会漏掉动态导入**：

| 形态 | 举例 |
| --- | --- |
| `import x from '…'` | 静态导入 |
| `export … from '…'` | 转出 |
| `require('…')` | CommonJS |
| **`await import('…')`** | **动态导入 —— 最容易被漏掉的那个** |

#### 真事

票 47 第一版扫描只覆盖前三种，`await import()` 没扫。工作台·界面自己发现后补上重扫，
结论没变（`PendingBoard.tsx` 确实零引用），但**如果那个文件被动态 `import` 过，就会被误删**，
而且删完构建与测试都可能是绿的 —— 直到运行时走到那条分支才炸。

#### 修法

扫描脚本必须覆盖四种，并且**在交付里把扫描命令与输出一起贴上** ——
这样别人能看出你扫了哪几种形态，而不是只看到「零引用」这个结论。

```bash
grep -rnE "(import|export)[^;]*from|require\(|await import\(" src/ tests/ | grep <模块名>
```

⚠️ **这条管的是「删文件」这一类操作**，与断言的假绿是两回事，但后果同样静默：
删错了不会立刻红，会在某条很少走到的分支上炸。

### ⑮ **产物没更新，位置判据就一直假绿 —— 全量测试抓不到「刚改的源码」**（2026-10-28，票 48 漏网一条）

票 48 把「收起顶部」按钮从侧栏底部搬到面包屑、把「隐藏对话区」搬到 logo 上。
交付里改了 6 条既有断言，**但漏了第 7 条**：`dom-render.mjs` ⑨-5 那条
「隐藏工作台在隐藏对话区**上面**」——它靠 `textContent` 含「隐藏对话区」找按钮，
而那个按钮已经变成只有图标 + `title` 的 logo 点击区，文字匹配不上了。

**漏网的原因不是没改，是那条当时还是绿的**：`dom-render` 主体跑的是 `lib/client.js`，
而产物是几小时前的旧版，里面按钮还是文字按钮，匹配得上。

直到 `npm run bundle` 之后，新代码才进产物，那条**当场变红**。

#### 这条为什么难发现

| 症状 | 人的判断 |
| --- | --- |
| 改完源码，跑测试全绿 | 「判据都过了」 |
| 打包后，某条突然红 | 「打包把什么东西弄坏了？」 ← **错，是它一直没测到新代码** |

**方向正好相反**：不是打包坏了，是**打包之前那些绿都是对旧产物说的**。

#### 判据

**改了客户端源码、又只跑读产物的测试（`dom-render` 等）→ 那些绿不算数。**

要真验，二选一：

1. 先 `npm run bundle` 再跑（慢，但所见即所得）
2. 把该断言挪到**直接 `import` 源码**的那一段（本仓库 `dom-render` 的 ⑮ 段就是干这个的）

⚠️ **两条都要做到的场合**：位置类判据（元素在哪个父容器里、谁在前）建议进源码段；
整体渲染不崩之类可以留在产物段。**但交付里必须说清这一条跑的是源码还是产物。**

#### 这次的处理

票 48 的交付如实写了「`dom-render` 主体跑旧产物，位置判据挪到 ⑮ 段」——它**知道**这件事。
漏的是「还有一条位置类判据留在主体里没挪」。所以真正要记的不是「产物会过期」，
而是：**挪的时候要扫一遍同类判据，不能只挪自己正在改的那几条。**

```bash
# 改完位置类的东西之后，扫一遍还有没有靠 textContent / 类名找元素的存量断言
grep -n "textContent).*includes\|closest('\.ant-" tests/*.mjs
```

### ⑯ **「有没有这一行」不等于「这一行有用」：import 行扫得出来，打包器却能摇掉**（2026-10-29，票 68 连带）

票 68 让配置板块不再渲染 `ChannelSettings`，而 `ChannelSettings.tsx:58` 是客户端**唯一**
`import` `comfyui-workflows/registry` 的文件。于是那批上游工作流 JSON 在客户端产物里
被摇掉了（`lib/client.js` 小 118 KB）。

`tests/copy-no-markdown.mjs:464` 那条「产物里被豁免的处数必须等于源数据现数」于是从绿变红：
源数据 10 处，产物 0 处。

#### 第一版修法（lead 给的）为什么错

**「扫 `src/client/**` 的 import 行，有就要求 10 处」—— 实测仍然红。**

真因：`WorkspaceSettings.tsx:74-75` 有**两行没人用的 import** 指向 `ChannelSettings` /
`DefaultsSettings`。它们从来没被使用过（打包器早摇掉了），但**字面还在源码里**。
扫 import 行会看到「有」，期望回到 10 处，而产物里是 0 处。

#### 第二版（普通 BFS）为什么也不够

从入口出发跟相对路径做 BFS —— 实测 130 个文件全走通，`reaches = true`。

因为 BFS 只看「文件 A 有没有 import 文件 B」，不看**那个导入的名字后面有没有被用过**。

#### 第三版（对的那个）

从 `src/client/index.ts` 出发，跟链时**只跟「导入的名字在文件别处还出现过」的那些 import** ——
那正是打包器的判据。这样才与 `grep -c "comfyuiT2iWorkflow" lib/client.js → 0` 对得上。

#### 判据

**判断「某东西在不在产物里」时，不要用「源码里有没有那一行」推。**
要么直接 grep 产物，要么照打包器的判据（可达性 + 绑定被用到）推。

⚠️ 换成「源码没 import 就要求 0 处」之后，**必须另加一条反向断言**：
产物里那个特征字符串确实零命中。

否则将来谁把 registry 引回客户端、产物里那批 JSON 回来了，
这条会因为「只要求 0 处」而永远绿 —— 那是把一条防线换成一句空话。

### ⑰ **测试里该容错的函数抛错了：整份测试崩在一条上，后面几十条一条不跑**（2026-10-29，票 69）

票 69 要验「读到坏值（比如 `"abc"`）要落回 1440，不抛错」。
自证时把坏值处理改成 `throw`，按说应该「那条断言红」。

**实际后果更大**：抛错直接把整份测试崩在 `Error`，**它后面那几十条断言一条都没跑**。
输出里只看到一条红，看不出「剩下的没跑」——这正是票 55 被 `.layoutGroup`、
票 66 被 `data-ewb-ws-open` 挡住时那个形状（条件不成立 → 整段跳过 → 只报一条）。

#### 修法

凡是「这个函数**理应**容错」的地方，测试调用处包一层：

```js
const safe = (fn) => { try { return fn() } catch (e) { return { threw: String(e) } } }
```

包一层之后：抛错变成**一条断言红 + 打出原话**，后面的断言照跑。
判据没变（仍是「必须返回 1440」），只是把「整份崩」换成「一条红」。

#### 判据

**自证时看「红了几条」，不看「有没有红」。**
只红一条、而你想它覆盖的是一整组时，先怀疑「它是不是在中间抛错断掉了」。

这条与复查清单第 6 条是同一件事，只是这次真的撞上了。

### ⑱ **自证不变红，先怀疑「判据被别的东西兜住了」**（2026-10-29，一天里撞了四次）

做自证（故意改坏，看测试会不会红）时，最常见的一种失败**不是**「改坏得不够」，
而是**判据外面还有一层东西替它兜着**，于是「里面偷偷坏了」外面看不出来。

这一天里同一个形状撞了四次，每次都是执行角色自己查出来的：

| # | 票 | 改坏了什么 | 为什么没红 | 补的判据 |
|---|---|---|---|---|
| 1 | 56 | 把 `.layoutGroup` 改成新类名 | 找不到控件 → 进 `else` 分支 → **那段 7 条断言一条没跑** | 改成按 `data-*` 找，并扫「没执行且没登记」 |
| 2 | 74→76 | `typesOfCap('text')` 改回 `['text']` | 外层 `typesOfModel` 末尾有 `MODEL_TYPES.filter(...)`，**非三类的值被过滤掉** | 直接钉 `typesOfCap('text')` 本身，不靠外层过滤 |
| 3 | 58 | 去掉 `Math.max/Math.min` | 断言只 grep 常量在不在，**常量还在、照样绿** | 把 `clampLibW` 导出成纯函数，断言**实际调用** |
| 4 | 75 | 注释掉挂 `ChannelSettings` 那句 | 判「导入的名字有没有被用到」时，**注释里提到过这个词也算用过** | 判定前先剥注释（打包器不看注释） |

#### 判据

**自证不变红时，先问三个问题，再想「是不是代码没改坏」：**

1. **那段断言真的执行了吗？** 它是不是在某个 `if` 的 `else` 里、被前一条的失败挡住了？
   （本仓库 `dom-render` 有「会打 ✓/✗ 的断言行：N 处 / 没执行且没登记：M 处」这项扫描，M 必须为 0）
2. **断言验的是「东西存在」还是「行为正确」？** 只 grep 常量、只查类名在不在、
   只 `includes` 一个词 —— 这些在「函数被掏空但常量还在」时全都绿。
3. **判据外面还有没有一层兜底？** 比如 `filter` 会把非法的值筛掉、`try/catch` 会把抛错吞掉、
   上游已经先报错让下游永远走不到。

#### 最好使的一招

**把要验的那个东西导出成纯函数，让断言直接调它、拿返回值比。**

- `clampLibW(100) === 180` 能抓住「`Math.max` 被删了」
- `grep "LIB_W_MIN"` 抓不住

**只有能直接调用、能传坏值进去的判据，才是能红的判据。**
靠读源码文本做的断言，大多只能证明「这段字还在」，不能证明「这段字起作用」。

### ⑲ **「汇总脚本红、单独跑绿」先量输出体积，别先怀疑断言**（2026-10-29，票 60）

现象：

```
$ node scripts/run-tests.mjs            → ✗ content-canvas-ops 红
$ node tests/content-canvas-ops.mjs     → 全绿
```

同一个文件，汇总里红、直跑绿。第一反应是「汇总脚本的判据有问题」，**猜错了**。

#### 真因

票 60 在 `ContentCanvas.tsx` 写了：

```tsx
<ReactFlow defaultEdgeOptions={{ type: 'content' }} … />
```

JSX 里的对象字面量**每次渲染都是新引用** → React Flow 拿到新引用就更新内部 store → 触发再渲染 → 渲染循环。
表现是 React 的 `act(...)` 警告从 1130 条涨到 1689 条，测试输出从 **923 KB 涨到 1.6 MB**。

汇总脚本用 `spawnSync` 收子进程输出，**缓冲区被撑爆**（`ENOBUFS`），于是子进程的结果被判成失败。

#### 怎么发现的

不猜，**量体积**：

```
$ git show HEAD:src/client/workbench/ContentCanvas.tsx > 备份   # ← 别这么备份，见下
$ 跑 HEAD 版 → 923 KB
$ 跑本版    → 1.6 MB
```

体积翻倍就是线索。修法：把那个对象挪到模块级常量 `CONTENT_EDGE_DEFAULTS`，引用不再变，输出回到 1.0 MB。

#### 判据

**「汇总红、直跑绿」时的排查顺序：**

1. **量输出体积**（`… | wc -c`）—— 与改动前对比。差一倍以上先查渲染循环 / 无限日志
2. 查有没有把**对象字面量写进 JSX 属性**（`defaultEdgeOptions={{…}}`、`style={{…}}` 传给会把它放进依赖数组的库）
3. 才是「汇总脚本的判据有没有问题」

⚠️ **把对象 / 数组字面量传给第三方组件要当心**：React Flow、图表库这类内部会拿 props 做浅比较并写 store 的，
每次都当新值 → 每次都更新。**模块级常量是默认做法，除非它真的依赖 props。**

#### 顺带一条：别用「覆盖同名文件」的方式备份

上面那条排查里，备份命令 `git show HEAD:文件 > /tmp/x` 被 Safety Net 整条拦下（连带前面的 `cp` 也没执行），
结果那个重定向**写到了原路径**，把正在改的文件覆盖成 HEAD 版，改动丢失（凭脚本重做）。

**备份先 `cp` 到不同目录、`ls` 确认看得见，再动原文件。**

## 复查清单

1. 这条规则/断言**在什么时候生效**？现在那个前提成立吗？
2. 把它**改坏**，测试会红吗？（不红 = 假防线）
3. 断言锚的是**真实结构**还是**源码文本**？（后者容易被绕过）
4. 判据触发了之后，**谁真的停下来**？（还是只是「记了个字段」）
5. 这条断言是「A 里的都在 B 里」吗？**把 A 删空它会红吗？**（不红就先钉住 A 该有的那几项）
6. 自证时**红的条数对不对**？（只红一部分 = 可能中间抛异常断掉了，见第四节）
