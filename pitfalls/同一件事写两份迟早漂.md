# 同一件事写两份，迟早漂

## 症状

**换一个入口做同一件事，只有一边坏。** 表现为「同一个工作流，在列表里点▶跑是好的、在画布里按▶就报错」。

本次实例（2026-10-15，用户报「抖音表单下载一进循环A第一个节点就报错停止」）：

```
【浏览器-playwright】派发给「builtin」执行方
⚠ 未找到变量 item.url（原样保留，没替换）
✕ page.goto: Protocol error (Page.navigate): Cannot navigate to invalid URL
```

## 成因

「画布内存里的节点 → 调度器规格」这个翻译被**写了两遍**：

| 谁 | 在哪 | 从哪读 |
| --- | --- | --- |
| 宿主半（列表点▶、组合层子工作流） | `src/workflow/run-file.ts` 的 `toRunSpecs` | 存档 JSON |
| 画布（画布里按▶） | `WorkflowCanvas.tsx` 的 `runSeq` 里就地一段 `map` | React Flow 内存节点 |

两份漂了，画布那份漏了两个字段：

- **`parentId`** → 调度器不知道谁是循环体（`loopPlan` 收到空容器）→ 循环体节点被当普通节点**在循环外各跑一次**，那时 `scope.fields` 里没有 `item`，`{{item.url}}` 原样发给浏览器 —— 就是上面那条错。
- **`sourceHandle`** → `edgeIsLive(undefined, ['false'])` 返回 true → **没走的分支照跑**。这个更隐蔽，一直没人发现。

## ★ 最值得记的一点：**测试也在测自己那份**

`tests/douyin-workflow.mjs` 当时**自己手写了一份 specs 映射**（注释里还写着
「我第一版构建 specs 时把 `parentId` 丢了」）—— 它一直在测**自己那份**，
画布那份真实代码**从来没被跑过**。

于是症状是：**测试全绿，坏的那份没人碰。**

「两份实现」所以危险，不是因为会漂，而是因为**漂了之后测试很可能正好盖住坏的那份**。

## 规避

1. **同一件事只留一份实现。** 这次把两个函数收进 `src/workflow/specs.ts`
   （`toRunSpecs` + `toRunSpecsFromCanvas`），画布改调共用函数。
2. **测试要调真实代码，不许自己拼一份输入。** 四条端到端测试
   （`douyin-workflow` / `tmall-workflow` / `ingest-workflow` / `patrol-workflows`）
   全部改成走 `toRunSpecsFromCanvas`。
3. **加一条「两份必须同构」的断言**（`tests/run-specs.mjs`）：同一张图分别经
   两条路翻译，**逐字段**比 —— 只看条数不够，漏字段时条数是一样的。

## 为什么这次能抽出去（而不是又抄一遍）

抽的时候撞到一个真约束：画布**引不了** `run-file.ts` —— 它 `import './store.ts'`，
而 `store.ts` 用 `node:fs`，浏览器里没有。

**解法是把纯逻辑挪出来，而不是回退到抄一份**：`specs.ts` 只依赖 `model.ts` 的类型，
两侧都能引；`run-file.ts` 保留 `export { … } from './specs.ts'`，既有 import 点不用改。

> 遇到「抽不出去」时先分清是**逻辑耦合**还是**依赖耦合**。
> 后者换个文件放就能解决，不构成「只好再写一份」的理由。

## 怎么发现

跑一遍**两条入口**，对同一个工作流比较结果。本次就是「列表里是好的、画布里是坏的」
这一个对比把范围一把缩到「两份翻译的差异」上。

## 同类风险（还没踩但形状一样）

- `toWorkflowDoc`（画布 → 存档）与 `fromWorkflowDoc`（存档 → 画布）是**一对反向**的，
  不是两份同向的，所以不在此列 —— 但它们的字段清单必须成对维护。
- 节点定义的 `params` 默认值与生成脚本里写死的参数值：生成器写进存档的是**实例值**，
  改节点定义默认值时，**已有存档不会跟着变**（它存的是当时的实例值）。

## 第二次踩：**测试替身与被替的东西形状不同**（2026-10-16）

## 症状

用户报「抖音那条链路还是有问题」。查运行日志（`GET /api/ecom-workbench/runs`，
记录只在内存 `Map` 里、没落盘）看到：

```
run-n6-… / defId=code.shell / state=success
  $ cmd.exe /c node …/dy-list-one.mjs …
  {"ok":true,"folder":"D-店铺-整体-抖音","files":[…32 个文件…],"count":32}
run-n7-… / defId=code.js / state=failed
  error: 拿不到目录清单（列目录那步失败？）
```

**上一步明明成功、32 个文件都在，下一步却说它失败。**

## 成因

`code.shell` 交给下游的是**纯文本**（`src/dispatch/executors.ts` 里
`return { status: 'success', output: out.trim() }`）——
脚本往 stdout 打的那行 JSON，到了下一步**还是字符串**。

而 `DY_LAST_DATE` 那段代码只写了「拿到的是对象」那条路：

```js
if (v === null || typeof v !== 'object') return null   // ← 字符串在这里被丢掉
```

于是真机上 n6 的输出（字符串）被整条丢掉 → `files` 仍是 null → 报上面那条错。

## ★ 为什么测试没抓到 —— 这才是要记的

`tests/douyin-workflow.mjs` 的壳桩**自己把最后一行 JSON 解析成了对象**再交给下游：

```js
let parsed = null
for (…) { try { parsed = JSON.parse(lines[i]); break } catch {} }
resolve(parsed ?? { raw: out.slice(0, 200) })     // ← 对象，不是文本
```

**那是 shell 执行方的第二份实现**，而真的那份返回纯文本。
测试里的下游拿到对象 → 能跑；真机上的下游拿到字符串 → 报错。
**测试全绿而功能是坏的**，与上面那次一模一样的味道。

## 修法

1. **`DY_LAST_DATE` 认两种形状**：字符串 → 自己取最后一行能解析成 JSON 的；
   对象 → 已经是那个形状 / 剥驱动壳。
2. **三个测试的壳桩全部改成返回纯文本**（`douyin-workflow` / `tmall-workflow` /
   `ingest-workflow`）—— 只做真执行方做的事，需要解析 JSON 的节点自己解析。
   失败时仍可解读 JSON，但**只为让报错可读，返回值不带它**。
3. 自证：把「认字符串」那条路去掉 → `douyin-workflow` 当场红 4 条（已实测）。

## 顺带发现的第二处

`天猫取数.json` 是**同一个形状**（n10 `code.shell` → n11 `code.js`，n11 只认对象）。
已一并修掉 —— 它还没报错只是**运气好**：那条链上列目录失败时
`dirs` 为空，而 n11 的失败判据是 `reports.length === 0`，而 reports 来自另一条边
（browser.act），所以掩盖过去了。

## 规避（比上面那条更一般）

> **测试替身一旦与被替的东西形状不同，测试全绿而功能是坏的。**

所以：**替身只许做真东西做的事，一行都不许多做。**
「顺便帮它解析一下 JSON 好让测试好写」正是越界 —— 那一行 `JSON.parse`
就足以让一个线上 BUG 藏起来。

判断方法：**把真实现读一遍**，逐条问「替身有没有多做或少做什么」。
本次就是「多做了 JSON.parse」。

## 第三次踩：**照自己的理解重写「探进别人页面」的代码**（2026-10-16）

## 症状

抖音工作流循环 A 第一轮必断：`②c 读已结算日 R` 返回
`{"ok":false,"err":"找不到 dayjs 模板（页面改版？）"}`，紧接着 `②e 算 L` 抛错中断。

看着像「抖音改版了」，其实**不是** —— 我们自己那份代码被简化过。

## 成因

`DY_READ_R` 是**页面内脚本**，要探进抖音自己的 React 组件树里翻一个 dayjs 实例。
它当初是「照源码理解后简化」写的，两处简化错：

| | 我们简化版（错） | 源码 `douyin-ui.ts:81-92`（对） |
| --- | --- | --- |
| 找 dayjs | 只沿父链走，每层 `Object.values` 看一层 | 先看 `ocf.memoizedProps.value.date[0]`，不行再 `walkObj`/`walkFiber` 深挖 |
| 判定 | `typeof val.year === 'function'` | `format` + `toISOString` |

致命的是**第一行**：dayjs 就藏在 `memoizedProps.value.date[0]` 里，
而简化版那句话**根本没碰 `value`**，沿父链走了 60 层也找不到。

## ★ 为什么测试没抓到

`douyin-logic`（纯逻辑）与 `douyin-workflow`（端到端）当时**全是绿的** ——
因为端到端把 `browser.act` 换成了返回构造数据的桩，
**页面里那几百行代码一个字都没被执行**。

这与上面两次同一个味道（测试盖住了坏的那份），但这次更极端：
**没有测试能跑到它**，除非真开页面 —— 而那是用户红线。

## 规避

> **探进第三方页面内部结构的代码，不许自己重写。**
> 它是在跟一个我们控制不了的实现搏斗，**能跑通的那版源码就是唯一靠得准的规格**。

- 现在 `douyin-code.mjs` 的 `DY_READ_R` 注释里写明了「照源码逐句搬」，
  并列出简化错的两处，改它之前先看那段注释。
- 规格只能靠**断言源码那几句还在**来护（`tests/douyin-logic.mjs` 第 ⑥ 段），
  且**先摘掉注释再查**（否则会被说明注释里的同一串救活 = 假绿）。
  ⚠️ 它是 `includes` 子串匹配，**拦得住「删掉那几行」，拦不住「改名」** ——
  真验证只有用户手动跑一次。
- 同类风险：天猫的 `TM_SET` 那几段也是页面内脚本，**同一条规矩**。

## 第四次踩：**手抄源码的配置表，抄漏一个字段**（2026-10-16）

同一天、同一条链路的第二个坑，与上面那个是一对：

抖音工作流循环 A 跑到**第 6 个模块**才断：

```
②c 读已结算日 R  →  {"ok":false,"err":"找不到日期控件（.ecom-dorami-date-picker-wrapper）"}
②e 算 L          →  failed：读已结算日失败…
```

前 5 个模块（交易/直播/短视频自营/短视频合作/图文）**全绿** ——
所以看着像「搜索页改版了」。其实是我们自己的 `DY_MODULES` 里搜索那条的 URL 抄漏一段：

| | URL |
| --- | --- |
| 我们（错） | `…/shop/drainage-terms` |
| 源码 `douyin-ui.ts:45` | `…/shop/search/drainage-terms` |

少了 `/search`。**页面照样打得开**（返回同域的一个页面），
所以前一步「打开页面」不报错，一路走到「找不到日期控件」才暴露。

## 与上面那个（重写规格）的关系

一个是**重写**代码，一个是**手抄**配置 —— 病根相同：

> **凡是与第三方页面 / 外部实现对齐的东西（URL、选择器、判定特征、
> React fiber 里的字段名），都要「原样搬 + 钉一条对规格的断言」。**

手抄之所以危险，是因为**抄漏了看起来也完全合理**（`shop/drainage-terms` 通顺得很）。
靠肉眼看配置发现不了 —— 只有逐条对源码、或真机跑才看得见。

## 规避

1. 配置表**逐条对源码**核（不是抽几条看），核完在注释里写明「照 `douyin-ui.ts:37-52`」。
2. **钉一条断言**，断言表**从源码抄**（`tests/douyin-logic.mjs` ① 段）——
   ⚠️ 从我们自己的配置抄一遍等于什么也没验，那只是把错误复制第二遍。
3. 断言要**做突变测试**：把 URL 改回错的 → 当场红（已实测）。

## 为什么测试当时没抓到

原断言只查「每条都有 url / picker / folder」（**存在性**），不查**等于什么**。
存在性断言拦不住「值抄错了」这一类 —— 与上面「测试替身形状不对」同源：
**断言盯错了东西，绿得毫无意义。**

## 第五次踩：**把源码的「等条件」换成「等固定时长」**（2026-10-16）

同一条链路的第三处，形状还是「我们自造了一份规格」：

| | 源码 `douyin-ui.ts:536` | 我们 |
| --- | --- | --- |
| 等日期控件 | `page.waitForSelector(picker, {timeout: 20000})` | `flow.delay` **固定 4 秒** |

当时备注还写着「比固定 9 秒更稳更快」—— **那是我们自己的判断，不是源码的做法**。

表现：前 5 个模块都过得去（4 秒够），只有**搜索页**的控件出得慢 → 查一次没有 →
报「找不到日期控件」→ 循环 A 中途断掉。

## 教训

> **「等一个条件」和「等一段时间」不是同一个东西。**
> 条件等待会在满足时立刻继续、不满足时一直等到上限；固定时长两头都不对：
> 快了会漏、慢了白等。源码写 20 秒不是随手填的，那是「最慢的页面也能出来」。

改成条件等待时，注意**站在哪一层**：源码那行在 playwright 层（有 `page`），
而我们的代码在**页面内**（没有 `page`）—— 所以做的是「在页面里轮询重查」，
**照源码的意思换做法，而不是照抄那一行**。这一步的判据是
「等价」：满足条件就继续、超时才放弃。

## 测试怎么写

这里是**行为**断言，不是查字符串：让 `document.querySelector` **第一次返回 null、
之后才返回元素**，看它会不会再查一次。把重查那行去掉 → 当场红 2 条（已实测）。

⚠️ 与前面几次对照：**「有没有等」是行为，查字符串查不出来** ——
那种断言只能钉住「源码那几句还在不在」。
