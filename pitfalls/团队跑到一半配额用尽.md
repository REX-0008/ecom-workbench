# 团队跑到一半配额用尽（2026-10-15）

> 一次**真实发生**的情况。记下来是为了下次不慌、不白跑。

## 出什么事了

跑了 5 位专家的团队，其中 **5 个任务里 3 个（T1 / T8 / T9）同时 429 失败**，
另外 2 个（T5 / T6）在配额耗尽**之前**已完成。

报错原文：

```
429 workbuddy upstream soft_rate (http 429):
{"code":6004,"msg":"您的使用量已超出频率限制，将在 2026-10-15 13:10:13 UTC+8 重置，
您也可以切换其他模型继续使用。"}
```

## 三条**已核实**的事实（不是推测）

### ① 配额是「模型级」的，不是「会话级」

用户原话：「**配额是模型限额**，切换个模型就好了」。
所有成员与队长当时都在 `workbuddy/deepseek-v4.1-flash` 上 → 一起撞。

**但运行时改不了成员模型** —— 见下。

### ② 运行中的团队**不能改成员模型**

我试过的三条路：

| 途径 | 结果 |
| --- | --- |
| `agent_teams_edit_plan` 的 `update_member` | ❌ 报错：「运行中的团队**只允许改 pending、未开始的任务**；成员与移除编辑需要 staged 计划」 |
| 直接改 `.agent-teams/<团队>/team.json` | ❌ **AGENTS.md 明令禁止**（不许直接改状态文件） |
| 重建团队（staged 状态下能指定模型） | ⚠️ 可行，但会**动到已完成的记录**（要手工搬进度） |

**根因**（`@nanmicoder/dsh-agent-teams` 的 `README_ZH.md:130` 原文）：

> 「成员创建默认零交互：成员沿用队长当前 LLM 路由时会**快照**该 provider、model
> 与思考强度……成员后续续跑**仍使用最终解析出的快照**。」

**所以模型是创建时定死的，运行中改不了。**

### ③ Web UI 里**没有**「给成员换模型」的按钮

用户去看了：「我还以为我能切换 subagent 的模型，我刚切过去看了，**没有换模型的按钮**」。

---

## 那下次怎么办（**开工前**就该做的）

### ✅ 能改模型的地方只有三处

| 改哪 | 怎么改 | 生效范围 |
| --- | --- | --- |
| **profile 默认** | `profiles/desktop/cordis.patch.yml` 的 `agent-teams` 节加 `memberModel: <模型名>`（还有 `memberProvider`），**然后重启桌面端** | 之后新建的成员 |
| **加成员时逐个指定** | `agent_teams_add_member` 的 `model` / `provider` 参数（**staged 阶段**，也就是用户批准之前） | 该成员 |
| **重建团队** | 删掉重来，在 staged 阶段全指定 | 新团队 |

⚠️ **`create` 的 `plan.members` 不支持 `executionPrompt`**（那是人格），但**支持 `model` / `provider`**
—— 所以「一次原子建队 + 每个成员指定模型」这条路存在，只是要给每个成员单独 `add_member` 才能填人格。
（见工作区 `AGENTS.md` 的「自建团队流程」与「批量调用」两节。）

### ✅ 号池是共享的 → **别指望「多开几个成员就快」**

用户原话：「其实**配额方面所有账号都是相通的**（有号池），只是当前只有一个账号有配额，
**一起跑的话估计分分钟全都跑到限额了**」。

**推论（重要）**：并行度越高，**撞限额越快**。
所以「人多力量大」在**配额受限时反而更糟** —— 5 个成员同时开工，配额几下就见底，
而每个都只跑了一半（**半成品比没跑更麻烦**）。

### ✅ 配额耗尽时的正确处置顺序

1. **先落袋已完成的**（`git commit`）—— 别让已完成产出的记录悬着
2. **检查失败任务有没有留下半成品改动**（`git status`）——
   这次 T1 就留了 `workflow-doc.ts` 的四个新增函数。
   **判断标准**：是不是**纯新增、未接线**（那就可以保留，重跑时能直接用；若动了已有逻辑则要看清）
3. **别急着重试**（重试还是在同一个模型上，立刻又撞）
4. **等配额恢复**（`automation_list` 会给出重置时间）
5. 恢复后 `reassign_task` 重试失败的那几个

---

## ⚠️ 一条容易搞错的：**组员「空闲就绪」不等于「模型可用」**

配额恢复前，成员状态看起来是 `idle/ready`（正常），任务状态是 `failed`。
**这时候派活会立刻再撞 429** —— 所以「状态正常」不能作为「可以开跑」的判据，
要看**配额时间**。

## 复查清单

1. 团队成员用的什么模型？**配额是模型级的** —— 5 个人挤一个模型就会一起撞。
2. 开工前要不要给成员**换一个配额充足的模型**？（只能在 staged 阶段改）
3. 如果只能等：**已完成的先提交**，失败任务留下的半成品**先判断能不能保留**。
