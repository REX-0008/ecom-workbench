# 布局溢出：测试全绿但内容糊在相邻节点上

> 一句话：**jsdom 没有布局**（`offsetWidth` / `scrollWidth` 恒为 0），
> 所以 `.footBar` 这类东西溢出到卡片外面时，`npm test` 永远抓不到。
> 只有真浏览器能量出来。

---

## 症状

- `npm test` 全绿、`check:types` 0 错、`check:tdz` 通过、构建成功
- 真机上：某一栏的内容从卡片**右侧**跑出去，压到**相邻节点**上
- 打开 DevTools 量：容器 `clientWidth` 284px，子项加起来 552px

**为什么不是「被裁掉」**：节点卡（`.node`）**没有** `overflow: hidden`。
所以溢出的部分是**真的画在外面**，不是看不见 —— 比被裁掉更难发现，
因为截图里看着像「隔壁节点的内容」。

---

## 这次的真凶（2026-10-19，t19 → t25）

`src/client/workbench/node-form.module.css` 的 `.footBar`（节点展开区贴底的
「失败处理」那一栏）：

```css
/* 改之前 */
.footBar {
  flex: 0 0 auto;
  display: flex;      /* ← 没有 flex-wrap */
  align-items: center;
  gap: 6px;
  ...
}
```

里面 `.seg`（三选一按钮组）是 `flex: 1 1 auto`，把剩余宽度吃光后，
后面那些**定宽**子项（重试的两个输入框 + 「次，间隔」「毫秒」两段文字）
就直接排到卡片外面。

叠加的第二个成因：`.input` 本身是 `width: 100%`（给竖排表单用的），
放进 flex 行会各占满 —— 所以重试输入框必须**写死宽度 + `flex: 0 0 auto`**。

### 修法（当前实现）

```css
.footBar {
  flex-wrap: wrap;    /* ① 兜底：装不下就折行，绝不溢出 */
}

.footBar .retryNum {  /* ② 输入框写死宽度，别继承 .input 的 100% */
  width: 3.2rem;      /* ≈51px，装得下 0~10 与 0~60000 */
  flex: 0 0 auto;
}
```

## 实测数字（真 Chrome）

| 写法 | 200px | 220px | 260px | 284px | 300px | 420px | 520px |
|---|---|---|---|---|---|---|---|
| 改之前（无 wrap + 4.5/5.5rem） | 溢 406px | — | — | 溢 322px | 溢 306px | — | — |
| 只有 `flex-wrap`（输入框仍 4.5/5.5rem） | — | — | — | 0 | 0 | 0 | 0 |
| **`flex-wrap` + 3.2rem（现在）** | 溢 10~24px※ | 0~4px※ | **0** | **0** | **0** | **0** | **0** |

### ⚠️ 为什么这两格写的是区间

不同的人量出来差几像素（前端开发者量 200px 溢 10px / 220px 溢 0；
我量 200px 溢 12~24px / 220px 溢 0~8px）。**不是谁错了，是探针的还原度不同**：

- 容器 `clientWidth` 算不算 padding（300px 卡片 → 284 还是 266）
- 有没有把 `--text-ewb-label: 12px` / `--text-ewb-meta: 13px` 这两个字号 token 填进去
- 中文文本的字体回退（`--dsw-font-family` 链子长短会改宽度）
- 「次，间隔」「毫秒」两段文字是不是真的与源码一字不差

**所以在这类手工复刻的探针里，几像素的差没有意义**。要看的是**量级**：
改之前溢 300px 以上（整块内容跑到卡片外），改之后 300px 起为 0。

※ **200/220px 那点残余不是重试块带来的**。对照实验：把重试块整个删掉、
只留「失败处理 + 三选一」，200px 下**一样溢**（我量 12px、前端开发者量 10px）—— 是三个中文按钮
（「停止流程 / 继续跑 / 走失败分支」nowrap 加起来约 194px）本身装不下。
260px 起就完全 0。**这条另记，不在本次范围**（要修得改三选一的设计，
比如窄时只显图标 —— 那是它自己的取舍）。

### 代价：`flex-wrap` 修好了溢出，但**吃了参数区的高度**（2026-10-19 实测）

`flex-wrap: wrap` 不是免费的 —— 装不下时它把内容折成 2~3 行，
`.footBar` 从 44px 长到 66px（默认宽）/ **122px**（窄节点）。
而 `.inlineEditor` 是**定高**的（`max-height: var(--ewb-editor-h, 220px)`），
里面**只有 `.block` 能滚** → footBar 每长高 1px，参数区就少 1px。

真 Chrome 实测（参数内容固定 600px，展开区上限 220px + 边框 = 227px）：

| 情形 | footBar 高 | **参数区可见高** | 参数要滚多少 |
|---|---|---|---|
| 改之前（无 wrap，会溢出） | 44px | **170px** | 430px |
| 现在，节点 300px（默认） | 66px | **148px** | 452px |
| 现在，节点 220px | **122px** | **92px** | 508px |
| 现在，节点 200px（滑块最左） | 122px | **92px** | 508px |

**读法**：默认宽度下参数区从 170px 掉到 148px（−22px，还能接受）；
但**把节点拖窄到 220px 时只剩 92px** —— 那时改一个超时要滚 508px。
这不是 bug（溢出确实修好了），是**这个修法的代价**，写在这里免得下次又以为「wrap 一下就好了」。

**若哪天有人抱怨「窄节点里参数区太矮」**，可选的路（都没做）：
① 重试那两个框折进「高级参数」，不占贴底那一栏；
② 窄节点下把「失败后重试」整块隐藏，只在设置里给；
③ 给 `.footBar` 一个 `max-height` + 自己滚（会让贴底那栏也滚，与「贴底是为了不被滚走」的初衷冲突，**不推荐**）。

```powershell

console.log('footBar :', pick('footBar'));

```

更直观的做法：**在应用里把节点宽拖到 300px，看「失败处理」那一栏的右边**
—— 内容不该越过卡片边界。

### ③ 用 DevTools 精确量

1. 打开画布，展开任一节点
2. F12 → Elements → 选中贴底那一栏
3. 在 Console 里：

```js
const bar = $0;                                   // 选中那个元素
console.log('可见', bar.clientWidth, '内容', bar.scrollWidth);
[...bar.children].forEach(el => {
  const o = Math.round(el.getBoundingClientRect().right - bar.getBoundingClientRect().right);
  if (o > 0) console.log('溢出', o, 'px →', el);
});
```

`scrollWidth > clientWidth` 就是溢出。

## 为什么没进 `npm test`（t25 的判断）

**不进。** 理由三条：

1. **jsdom 量不到**：`offsetWidth` / `scrollWidth` 在 jsdom 里恒为 0，
   断言永远「不溢出」→ 假绿。要真量必须起真浏览器。
2. **真浏览器不是无条件的**：本机 playwright 的 chromium 二进制
   **没装**（`npx playwright install` 没跑过）。实测只有系统 Chrome 可用。
   把这个塞进 `npm test`，等于让「环境缺件」变成红 ——
   现有先例（`douyin-download-live.mjs`）的做法是**缺件就 `process.exit(0)` 跳过**，
   而「总是被跳过」的断言等于没有。
3. **它守的是「视觉」不是「逻辑」**：这类问题的判据是「看着难不难看」，
   而套件里的断言应该守「行为对不对」。混进去会让「红了」这件事贬值。

**代价要说清**：所以这条**只能手测**。改 `.footBar`（或任何定宽 flex 行）之后，
按上面 ② / ③ 量一次。这个代价是我认下的。

## 同型陷阱（写样式时先想这三条）

1. **flex 行里放定宽子项 → 必须先想「装不下怎么办」**。
   要么给容器 `flex-wrap: wrap`，要么让子项能缩（`min-width: 0` + `flex: 1 1 0`）。
   两个都不做 = 溢出。
2. **`width: 100%` 的表单控件不能直接放进 flex 行**。
   它会让每个控件都想占满 → 行被撑爆。给它单独一个类写死宽度。
3. **容器没有 `overflow: hidden` 时，溢出是真的画在外面**。
   别指望「反正会被裁掉」—— 这张卡片恰恰没裁。

## 一个会让探针骗你的坑（第一次就踩了）

**用「当前产物」的 CSS 去验「改之前」的行为，等于用新规矩判旧案子。**

第一版探针这么写：把产物里现在的 `.footBar` 规则套到「旧结构」上量 ——
而那条规则**已经含 `flex-wrap: wrap`** 了，于是旧结构也不溢出（假阴性）。

正确做法：**把要验的那条声明从规则里删掉**再量。

```js
const footBarNow = pick('footBar');
const footBarOld = footBarNow.replace(/flex-wrap:[^;]*;?/, '');  // ← 回到改之前
```

同型错误在 t11 也发生过（「量到的配置与被测的配置不是一回事」，被复评打回）。

## 第二个会让探针骗你的坑：**CSS 特异性抄少了**

同一件事的第二天，我又踩了一次。

`node-form.module.css` 里真实的规则是**带前缀的**：

```css
.footBar .retryNum { width: 3.2rem; flex: 0 0 auto; }   /* 特异性 0-2-0 */
```

而 `.input` 是 `width: 100%`（特异性 0-1-0）。**前缀就是特异性**，
少了 `.footBar ` 那一层，`width: 100%` 会赢。

我第一版探针写成：

```js
'.' + retryNum.cls + ' { ' + retryNum.body + ' }'        // ← 错：凭空少了 .footBar
```

量出来的结果是「**7 行、192px 高**」—— 完全不是真机的形状，
而当时我还以为是「折行算错了」。

**正确写法**（照着产物里的选择器一字不差抄）：

```js
'.fb .' + retryNum.cls + ' { ' + retryNum.body + ' }'
```

### 可操作的判据

手工搭探针时，**每次从产物里抠规则，都要连选择器一起抠**，别只抠 `{...}` 里的声明体。
抠之前先在产物里搜一眼真实选择器长什么样：

```powershell
node -e "const fs=require('fs');const b=fs.readFileSync('lib/client.js','utf8');
const m=/[^{}]*retryNum[^{}]*\{[^}]*\}/g;let r;while((r=m.exec(b))!==null)console.log(r[0].slice(0,140));"
```

产物里的类名是**前缀 + 原名**（`REe6wW_footBar .REe6wW_retryNum`），
所以「原名 + 原名」这么拼是对的 —— 但**层级关系必须保留**。

### 顺带：手工探针本来就会差几像素

同一个页面，三个人量出三个略不同的数（字体回退、字号 token 有没有填、
容器 `clientWidth` 算不算 padding、文本有没有一字不差）。
**这类探针只适合判「量级对不对」**（300px 还是 0），
不适合判「差 2px 是谁的问题」。真要精确，得在真应用里用 DevTools 量（见上面 ③）。
