# 并行改仓库：一个在改、一个在读，结果谁都不可信（2026-10-25）

> 主题：**同一份工作区里，有人为了自证临时改文件，同时另一个人在跑测试。**
> 表现不是报错，而是**同一个结论跑两次给出相反答案** —— 最容易被误判成「测试本身坏了」。

## 现场

内容板块收尾那一轮，我（lead）派了执行角色 BJ 干活，同时派校核做独立复验。
校核为了判「`.find()` 改回后为什么真板块断言不红」，在 `src/client/workbench/boards.ts` 里
临时把 `{ id: 'canvas', …, keepMounted: true }` 改成去掉 `keepMounted` 的版本。

**它做了两轮破坏**：第一轮跑完立刻还原了；第二轮（受控实验：看全量会不会假绿）
**留了一段时间没还原就去跑全量了**。我在这期间跑测试，于是：

| 我跑的 | 那一刻文件状态 | 结果 |
| --- | --- | --- |
| 全量 `run-tests.mjs` | 恰好是**还原后**的干净状态 | `全部 107 个通过 ✓` |
| 单跑 `run-tests.mjs board-registry` | 恰好是**改过**的状态 | `✗ boards.ts 的 content 声明里画布那格标了 dynamic + keepMounted` |

**同一份 HEAD、同一条断言、相隔几分钟，一次绿一次红。**

**归因（当事人自己给的准话）：两件事都有，主因是第二件。**
① 并行撞车 —— 它改我读，谁都不可信；
② **自证窗口内留了脏文件** —— 破坏自证必须「改完立即还原 + 核 hash」，不能靠记忆，不能拖到「我先把实验做完再还原」。

## 我当时差点得出的错误结论

「全量能给出假绿，以后不能只信全量。」

**这是错的。** 真相是两次跑的不是同一份工作区内容。
如果不查清就按那个结论改流程，会把「全量是准的」这个正确前提推翻掉，
后面所有验收都失去基准 —— 代价远大于这次多花的十几分钟。

**反证也做了**：故意留一份脏 `boards.ts`（sha `0e0638fc8b97df87`），先在单跑、再跑全量，
两次都红（`board-registry.mjs` 1 条），跑完 `sha` 仍是 `0e0638fc8b97df87` —— 没有被任何测试改回去。
机制上也排除了：`scripts/run-tests.mjs` 是 `for` + `spawnSync` **串行、直接跑真文件、无拷贝无缓存无快照**。

## 怎么确认是「人为改动」而不是「测试写文件」

按顺序排除了三件：

1. `git status --short` 在跑测试**前后**各看一次 —— 干净进、干净出，说明没有测试写源文件；
2. 全仓搜 `writeFileSync` + `git checkout` + `git restore` —— 没有任何测试对 `src/**` 做写或还原；
3. 受控实验（上面那段）：留脏跑全量，跑完 sha 不变 → 测试不会改文件。

⚠️ **这里我犯过一个错，写下来免得下次重犯**：我一开始拿 `mtime` 当证据，说「`boards.ts` 最后改动是 20:51，
比任何测试都早，所以不是测试改的」。**方向对，但结论下早了** —— `mtime` 只说明「最后一次被写的时刻」，
**不能说明文件现在是不是脏的**。判「脏不脏」只有一个可靠办法：

```
git hash-object <文件>  与  git rev-parse HEAD:<文件>  是否相等
```

`mtime` 还会被「用备份覆盖还原」这种方式**保留成备份的时间**，看时间会以为没还原。

## 规矩（写下来为了下次直接照做）

1. **执行角色任何在仓库里改文件的动作（包括为自证临时改坏）都必须先报，并写明「改了哪个文件、什么时刻还原」。**
   不是不信它，是因为**同一时刻可能有人在读**。
2. **lead 跑全量/构建前先看 `git status`；跑完再看一次。** 两次不一致 → 这次结果作废，重跑。
3. **看到「同一结论两次相反」，第一件事查文件状态与 mtime，不要先怀疑测试。**
   归因顺序：文件状态 → 时间线 → 测试逻辑。反过来会把「并发」误判成「测试坏了」。
4. **只读角色（校核）不许改 `src/` `tests/` `scripts/`。** 需要靠改代码才能判的事，
   说清「想验什么」交给 lead 另派 —— 它有权限，且它跑的时候没有别人在改。
5. **还原动作本身可能失败。** 实测：`git checkout -- <文件>` 会被安全机制拦住，
   于是改的人退回「用破坏前的备份覆盖」。这条路是可行的，**但必须补两步**：
   ① 覆盖完核 `git hash-object <文件>` 与 `git rev-parse HEAD:<文件>` 是否相同（不看 mtime，
   备份覆盖会保留备份的 mtime，光看时间会以为没还原）；② 备份留在 `$DSH_HOME/tmp/` 里，
   事后能靠它的时间戳还原「谁在什么时候改过什么」。

## 一并记下：判断破坏自证「红在哪一条」，要看行为走的是哪份声明

同一轮里踩到的第二个坑。验「真双板块」那段测试时，有人改 `boards.ts` 去掉 `keepMounted`，
只红了 1 条；改**测试自己抄的那份 `tabs` 副本**，红了 3 条。

原因：那段测试 `registerBoard` 传的是**它自己抄的一份 `tabs`**，行为全走抄本；
`boards.ts` 只被「声明一致性」那条断言读源码比对。所以：

| 改哪里 | 红几条 | 红的是什么 |
| --- | --- | --- |
| `boards.ts`（真实声明） | 1 | 「抄本与源码不一致」—— **不是行为** |
| 测试里那份抄本 | 3 | **真的行为断言**（`切走之后内容画布那个节点还在` 等） |
| 骨架 `keptTabsOf`（`.filter` → `.find`） | 2 | 真的行为断言，但**只有假板块那 2 条**；真双板块全绿 |

第三行那个「真双板块全绿」不是漏洞，是**该红的本来就只有假板块**：`content` 与 `workflow`
各只有一个 `keepMounted` 格，`.find()` 与 `.filter()` 对它们结果相同。多格能力由假板块守，
真双板块守的是「声明 → `keepsMounted` → `panes` 过滤 → 常驻」这条链（改骨架 `keepsMounted`
会红 7 条，全是行为断言）。

**教训**：破坏自证要「红在你想要的那条断言上」，否则**红了也不算验到**。
改之前先问两句：① 这段测试的行为到底读的是哪份数据？② 红的那条，是不是我想验的那条？


## 症状之一：跑测试报 `Parse error … dom-render.mjs:1:1`（2026-10-26 第二次踩）

**这不是语法错，是那个文件此刻正在被写。** tsx 读到半截文件 → 报**第 1 行**解析失败。

真事：`工作台·工作流` 在核 `run-tests.mjs` 的过滤规则时，跑 `dom-render content-canvas` 5 次红 2 次，
报的就是 `Parse error ... dom-render.mjs:1:1`；而 `工作台·界面` 正在写那个文件（`LastWriteTime` 同时变、
`git status` 里出现 `M tests/dom-render.mjs`）。等 45 秒、`node --check` 通过后复跑 2/2 绿。

**判据**：报错行号是 **1:1** 而文件明明有几千行 → 先看 `git status` 与 `LastWriteTime`，别去翻第 1 行。

**它的正确处置（可照抄）**：把 `scripts/run-tests.mjs` 先 stash 掉、跑同样两条，5/5 绿 → 排除自己的改动。
**并且它主动把这条写进交付**：以后跑测试前先看 `LastWriteTime` 与 `git status`，不在别人的编辑窗口里判定。

⚠️ **lead 自己也要守**：我在同一时段跑全量，也吃到一次 `dom-render` 红。
`run-tests.mjs` 是**串行跑真文件**（本文件上面已证），所以**任何一个执行角色在写任何一个测试文件，
全量结果就作废**。跑全量前先确认没有人正在改 `tests/`。

## 症状之二：别人的改动被卷进你的提交（2026-10-28，**lead 自己犯的**）

比「一个改一个读」更隐蔽的一种并行撞车：**`git commit` 提交的是整个索引，不是「你刚 add 的那些」。**

### 真事

工作台·前端在票 46 里改完 8 个文件并 `git add` 好，准备提交时被告知「没有已暂存的改动」。
查下来：那 8 个文件被卷进了我（lead）紧跟着写的一笔踩坑提交里 ——
我当时的命令是

```bash
git add "pitfalls/假防线-看着写了其实不生效.md" && git commit -m "..."
```

看起来只提交了一个文件。**但它 `add` 之前，索引里已经有别人暂存的 8 个文件**，
`git commit` 把索引里**全部**内容一起提交了，我那一个文件只是其中之一。

### 为什么「只按路径逐个 add」挡不住

那条规矩挡的是 **`git add -A` 会把工作区里别人的未提交改动扫进来**。
它**挡不住**「索引里本来就有别人 add 好的东西」—— 你的 `add` 是往上叠，不是替换。

### 判据：提交前先看索引

```bash
git diff --cached --stat    # 这一步「将要提交什么」必须只有你自己的文件
```

或者用**只提交指定路径**的写法，它读工作区、不读索引里别的东西：

```bash
git commit -- <路径1> <路径2>
```

⚠️ 首选用 `git diff --cached --stat` 先看 —— 它不管随后用哪种写法都能拦住，
是最便宜的一道闸。

### 已经卷进去了怎么修（本次实测流程）

⚠️ **先做一件判据性的事：确认别人的文件「有没有丢」**。

```bash
for f in <别人的文件...>; do
  git diff --quiet HEAD -- "$f" && echo "一致 $f" || echo "已变动 $f"
done
```

- **全部「一致」** = 别人的改动完整进了库、工作区也没有后续未提交内容 → **不用拆，只需在交付里记一笔**
- 有「已变动」= 别人正在往上叠加新改动 → 拆之前必须先问那个人

**多数时候结论是第一行**：卷进去的文件一个字没坏，坏的只是「提交说明与实际内容不符」。
而拆历史有风险（会动到别人的暂存状态），收益只是让说明好看 —— **不值得为一个说明去改历史**。

真的必须拆（比如别人明确要求），前提是**没推送**：

```bash
git reset --soft <混合提交>^     # 回到混合提交之前，索引里保留全部改动
git reset                        # 清空索引，改动全留在工作区
git add <A 的文件...> && git commit -m "<A 的信息>"    # 先提别人的
git add <我的文件...>  && git commit -m "<我的信息>"   # 再提自己的
git diff <混合提交> HEAD --stat   # ← 必须为空：说明拆完内容一字节没变
```

最后那一步是**拆分唯一可靠的自证**：与拆分前的提交逐字节比对，为空即无损。

⚠️ **`git diff --cached --stat` 也有窗口期**（2026-10-28 第二次踩，方向反过来）。
票 50 那次：跑 `git diff --cached --stat` 时只有自己的 2 个文件，随后**同一个回合里**
执行 `git commit`，而在这两条命令之间另一个角色把它的 4 个文件 `add` 了进去 —— 于是照样被卷走。

**两个闸都不能只靠「看过一眼」**：
1. `git diff --cached --stat` 看完**立刻**提交，中间不插任何别的命令
2. 提交后**马上** `git show --stat HEAD` 复核一遍「实际进去的是不是刚才看到的那些」

第 2 条是兜底 —— 前一条只能在窗口小的时候靠运气，后一条能把每一次都验到。

### 真正治本的办法：`git commit -- <路径>`

**索引整个仓库只有一份**，两个人同时 `add`，谁先 `commit` 就把另一个人的内容一起带走。
逐路径 `add`、`git diff --cached --stat` 都只是**缩小窗口**，挡不住结构性冲突。

**根治写法**（2026-10-28 在本仓库实测过）：

```bash
git commit -m "…" -- <路径1> <路径2>
```

带路径的 `commit` **忽略索引里其它已暂存的内容**，只记录点名的那些文件的当前内容。
实测：我先 `add a.txt`、另一个人 `add b.txt`，索引里两个都有；
执行 `git commit -m x -- a.txt` 之后，HEAD 只含 `a.txt`，**`b.txt` 原封不动留在索引里**，
那个人后续提交照常。

⚠️ **两个限制，实测确认**：

1. **新文件（未跟踪）不能直接点名** —— 报 `pathspec '…' did not match any file(s) known to git`。
   新文件要先 `git add <它>`，然后再用带路径的 `commit` 点名。
   ⚠️ 那一次 `add` 仍然会短暂地把新文件放进共享索引 —— **这是唯一还剩的窗口**，
   所以要紧接着提交，中间不插别的命令。
2. **已删除的文件可以点名** —— 删除操作直接 `git commit -- <被删的路径>` 就行。

### 拆完之后的自证：比树哈希，不是比 diff

```bash
git rev-parse <重排前的最后提交>^{tree}    # 拆之前先记下来
…重排…
git rev-parse HEAD^{tree}                   # 拆完与它比
```

**两者相同 = 内容一字节未变**。比 `git diff <旧> HEAD --stat` 为空更强：
树哈希相同意味着**每一个文件的内容都逐一相同**，而不只是「没有增删」。

⚠️ **注意比的对象**：本次我先记的是 `f3f108d`（混合提交）的树，
但重排时我把它**之上**的另一笔也一起重排了 —— 正确的对照是**重排前的 HEAD（`4a45530`）**，
不是那个混合提交。比错对象会得出「不一致」的假警报。

### 教训

- **并行期间，「提交」不是私有动作** —— 它作用在一个所有人在共用的索引上
- 派活单里除了「不许 `git add -A`」，还要加两句：**提交前 `git diff --cached --stat`、提交后 `git show --stat HEAD` 复核**
- 出事后**先看索引，别先怪别人用了 `-A`**（两次都不是 `-A`：一次是我叠在别人的暂存上，一次是别人叠在我的）
- **卷进去了不等于内容坏了**：先跑上面那个「一致 / 已变动」检查，别第一反应就动历史
